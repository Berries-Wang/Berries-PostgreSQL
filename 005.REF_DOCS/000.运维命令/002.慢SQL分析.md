# 慢 SQL 分析

> 分析路径：① 定位慢 SQL（日志 / pg_stat_statements）→ ② 看执行计划（EXPLAIN ANALYZE）→ ③ 对症优化（索引 / SQL 改写 / 参数）。以下以 PG13~16 为准（`*_exec_time` 字段，PG12 及之前叫 `total_time`）。

## 1. 记录慢查询日志

`postgresql.conf`：

```ini
# 超过 1 秒的语句记录到服务器日志（按业务定阈值，生产常用 500ms~2000ms；-1 关闭）
log_min_duration_statement = 1000

# 日志输出配置（如尚未开启）
logging_collector = on
log_directory = 'log'
log_line_prefix = '%m [%p] %u@%d '        -- 时间 [pid] 用户@库

# 附加推荐：记录慢 SQL 的执行计划（auto_explain，PG13+）
# shared_preload_libraries 里加上 auto_explain
shared_preload_libraries = 'pg_stat_statements,auto_explain'
auto_explain.log_min_duration = '3s'      # 只对超过 3s 的 SQL 记录计划
auto_explain.log_analyze = on             # 真实执行（注意本身有开销，阈值别设太低）
```

```shell
sudo systemctl reload postgresql
# 日志位置：
sudo -u postgres psql -c "SHOW log_directory;"
```

日志中一条慢查询形如：

```log
2026-09-24 10:12:03.456 CST [12345] star_router@shopfi_saas LOG:  duration: 2310.512 ms  statement: SELECT * FROM t_order WHERE ...
```

## 2. pg_stat_statements — 慢 SQL 统计（首选）

```sql
-- 前提：postgresql.conf 中 shared_preload_libraries = 'pg_stat_statements' 并重启
SHOW shared_preload_libraries;

-- 在目标库启用
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```

```sql
-- 总耗时 TOP 10（优化收益最大）
SELECT round(total_exec_time::numeric, 1)   AS total_ms,
       round(mean_exec_time::numeric, 1)    AS avg_ms,
       calls,
       round((total_exec_time / calls)::numeric, 1) AS per_call_ms,
       rows,
       left(query, 80)                      AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- 单次平均耗时 TOP（用户体感最差）
SELECT round(mean_exec_time::numeric, 1) AS avg_ms, calls, rows, left(query, 80) AS query
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- 临时文件大户（磁盘排序溢出，直接关联磁盘空间问题，参见 001 文档）
SELECT round(temp_blks_written*8/1024.0, 1) AS temp_mb,
       calls, left(query, 80) AS query
FROM pg_stat_statements
WHERE temp_blks_written > 0
ORDER BY temp_blks_written DESC;

-- IO 大户（缓存未命中读盘多的）
SELECT shared_blks_hit, shared_blks_read,
       round(100.0*shared_blks_hit/NULLIF(shared_blks_hit+shared_blks_read,0),1) AS hit_pct,
       left(query, 80) AS query
FROM pg_stat_statements
ORDER BY shared_blks_read DESC
LIMIT 10;

-- 重置统计（做优化前后对比时用）
SELECT pg_stat_statements_reset();
```

## 3. EXPLAIN — 看执行计划

```sql
-- 只看计划（不改数据，任何语句可跑）
EXPLAIN SELECT * FROM t_order WHERE user_id = 42;

-- 真实执行并统计（SELECT/DDL 可用；注意 DML 会真的执行）
EXPLAIN (ANALYZE, BUFFERS, VERBOSE) 
SELECT o.id, o.amount, u.name
FROM t_order o
JOIN t_user u ON u.id = o.user_id
WHERE o.created_at > '2026-09-01'
ORDER BY o.amount DESC
LIMIT 20;
```

读计划的关注点（从里往外、从上往下找最贵的节点）：

| 现象 | 含义 | 优化方向 |
|---|---|---|
| `Seq Scan` 大表 + Filter | 全表扫描 | 加索引 / 改写条件 |
| `rows=1000000` 估算与实际差一个量级 | 统计信息过期 | `ANALYZE 表名`；必要时调 default_statistics_target |
| `Nested Loop` 带大行集 | 关联方式不佳 | 确认连接列有索引；调大 work_mem 让优化器敢用 Hash Join |
| `Sort Method: external merge (Disk)` | 排序溢出到磁盘 | 调大 work_mem（会话级 `SET work_mem='64MB'`）或让 ORDER BY 走索引 |
| `Buffers: shared read=99999` | 大量读盘 | 数据未缓存 / 缺索引；关注 shared_buffers |
| `Index Only Scan` 但 `Heap Fetches` 很高 | visibility map 不全，回表太多 | `VACUUM` 该表 |

## 4. 索引检查

```sql
-- 走全表扫描最多的表（大概率缺索引）
SELECT relname, seq_scan, seq_tup_read, idx_scan,
       pg_size_pretty(pg_relation_size(relid)) AS size
FROM pg_stat_user_tables
ORDER BY seq_tup_read DESC
LIMIT 15;

-- 某索引是否被用过（覆盖一个完整业务周期再判断）
SELECT relname, indexrelname, idx_scan, idx_tup_read
FROM pg_stat_user_indexes
WHERE relname = 't_order';

-- 重复/冗余索引：列完全相同的重复索引，或 (a) 被 (a,b) 包含的前缀冗余索引
WITH idx AS (
    SELECT i.indexrelid::regclass AS index_name,
           i.indrelid::regclass   AS table_name,
           (SELECT string_agg(a.attname, ',' ORDER BY k.ord)
            FROM unnest(i.indkey) WITH ORDINALITY AS k(attnum, ord)
            JOIN pg_attribute a ON a.attrelid = i.indrelid AND a.attnum = k.attnum) AS cols
    FROM pg_index i
    JOIN pg_class c ON c.oid = i.indrelid
    JOIN pg_namespace n ON n.oid = c.relnamespace
    WHERE n.nspname = 'public'
)
SELECT a.table_name,
       a.index_name AS redundant_index,
       b.index_name AS superset_index,
       a.cols
FROM idx a
JOIN idx b
  ON a.table_name = b.table_name
 AND a.index_name <> b.index_name
 AND b.cols LIKE a.cols || ',%';   -- a 的列是 b 的前缀 → a 冗余

-- 不确定时先看全量索引定义人工核对
SELECT tablename, indexname, indexdef FROM pg_indexes WHERE schemaname='public' ORDER BY tablename;

-- 建索引不锁写（PG11+）
CREATE INDEX CONCURRENTLY idx_t_order_user_created ON t_order (user_id, created_at DESC);

-- 表达式/部分索引（对特定慢查询往往立竿见影）
CREATE INDEX CONCURRENTLY idx_t_order_pending ON t_order (created_at) WHERE status = 'PENDING';
```

## 5. 锁等待 / 卡住的会话

```sql
-- 谁在等谁（wait_event_type='Lock' 即被阻塞；blocking 列显示阻塞者 pid）
SELECT pid, usename, state, wait_event_type, wait_event,
       now() - query_start AS running_for,
       pg_blocking_pids(pid) AS blocked_by,
       left(query, 60) AS query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
   OR state = 'active'
ORDER BY running_for DESC;

-- 处置：取消 SQL（温和） / 断开连接（强硬）
SELECT pg_cancel_backend(<pid>);
SELECT pg_terminate_backend(<pid>);

-- 锁详情：哪条 SQL 持有什么锁、是否等待
SELECT l.pid, l.locktype, l.relation::regclass, l.mode, l.granted, a.query
FROM pg_locks l
JOIN pg_stat_activity a ON a.pid = l.pid
WHERE l.relation IS NOT NULL
ORDER BY l.granted, l.relation;

-- 死锁排查：日志中出现 DEADLOCK DETECTED 时，开详细锁等待信息
SET deadlock_timeout = '500ms';
SET log_lock_waits = on;
```

## 6. 常用优化参数（会话级可试，生效快）

```sql
-- 单条大 SQL 的排序/哈希内存（默认 4MB 偏小；只对当前会话生效，重启连接失效）
SET work_mem = '64MB';

-- 查询成本上限保护（超时自动取消，防止失控 SQL 拖垮库；按业务定）
SET statement_timeout = '30s';

-- 随机 IO 成本（SSD 上可调低，让优化器更倾向走索引；全局需改 postgresql.conf）
SET random_page_cost = 1.1;

-- 更新统计信息目标后重新收集（估算行数不准时）
ALTER TABLE t_order ALTER COLUMN status SET statistics 500;
ANALYZE t_order;
```

## 7. 排查流程小结

```
用户反馈慢/发现磁盘涨
  │
  ├─ pg_stat_activity        → 有没有卡住/等锁的会话？先 pg_cancel_backend 止血
  ├─ 慢日志 / pg_stat_statements → 定位到具体 SQL（按 total 或 mean 排）
  ├─ EXPLAIN (ANALYZE, BUFFERS) → 全表扫描？排序溢出？行数估算失真？
  ├─ 索引检查                → 缺索引建 CONCURRENTLY；冗余索引删
  └─ 参数/统计信息            → work_mem / ANALYZE / default_statistics_target
```
