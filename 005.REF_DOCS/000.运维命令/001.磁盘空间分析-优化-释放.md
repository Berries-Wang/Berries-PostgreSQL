# 磁盘空间分析 / 优化 / 释放

> 核心思路：先定位「空间去哪了」（库 → 表 → 索引/WAL/日志），再决定怎么释放。
> PostgreSQL 的 MVCC 机制决定了 DELETE/UPDATE 不会真正归还磁盘空间给操作系统，需要 VACUUM 体系处理。

## 1. 操作系统层面定位

```shell
# 数据目录在哪
sudo -u postgres psql -c "SHOW data_directory;"
sudo -u postgres psql -c "SHOW config_file;"   # 配置文件同目录下就是 pg_hba.conf

# 看数据目录下各子目录占用，快速判断是"数据"、"WAL"还是"日志"撑爆的
sudo du -sh /var/lib/postgresql/*/main/* | sort -rh | head -20
# 常见大目录：
#   base/        业务数据文件
#   pg_wal/      WAL 预写日志（归档/备库卡住会堆积）
#   log/         服务器日志（logging_collector=on 时）

# WAL 和日志目录也可以直接问数据库
sudo -u postgres psql -c "SHOW wal_directory;"  -- PG15+；更早版本用 data_directory 再拼 pg_wal
sudo -u postgres psql -c "SHOW log_directory;"
```

## 2. 数据库 / 表 / 索引大小分析

```sql
-- 所有数据库大小排序
SELECT datname,
       pg_size_pretty(pg_database_size(datname)) AS size,
       pg_database_size(datname)                AS size_bytes
FROM pg_database
ORDER BY size_bytes DESC;

-- 单库大小
SELECT pg_size_pretty(pg_database_size('shopfi_saas'));

-- 当前库中最大的 20 张表（pg_total_relation_size = 表数据 + 索引 + TOAST）
SELECT schemaname,
       relname                          AS table_name,
       pg_size_pretty(pg_total_relation_size(relid))            AS total_size,
       pg_size_pretty(pg_relation_size(relid))                  AS table_only,
       pg_size_pretty(pg_indexes_size(relid))                   AS indexes_only,
       pg_size_pretty(pg_total_relation_size(reltoastrelid))    AS toast_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 20;

-- 最大的索引 TOP 20（找出又大又没用的索引，见下文"未使用索引"）
SELECT schemaname,
       relname        AS table_name,
       indexrelname   AS index_name,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
       idx_scan                                    AS 使用次数
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 20;

-- 按 schema 汇总占用
SELECT schemaname,
       pg_size_pretty(sum(pg_total_relation_size(schemaname || '.' || relname))) AS total_size
FROM pg_stat_user_tables
GROUP BY schemaname
ORDER BY sum(pg_total_relation_size(schemaname || '.' || relname)) DESC;

-- 表内行数 Top（估算值，不需全表扫描）
SELECT relname, n_live_tup
FROM pg_stat_user_tables
ORDER BY n_live_tup DESC;

-- 指定表的总大小
SELECT pg_size_pretty(pg_total_relation_size('public.t_order'));
```

## 3. 膨胀（bloat）分析 — 空间为什么释放不掉

```sql
-- 死元组统计：n_dead_tup 大说明有大量已删/旧版本行未被回收
SELECT relname,
       n_live_tup,
       n_dead_tup,
       round(n_dead_tup*100.0/NULLIF(n_live_tup+n_dead_tup,0),1) AS dead_pct,
       last_vacuum,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;

-- 精确分析单表膨胀（需要扩展；全表扫描，大表挑低峰跑）
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT * FROM pgstattuple('public.t_order');
-- 关注 free_percent / dead_tuple_percent（可回收空间占比）
-- 大表用近似版更快（基于 visibility map，不全表扫）：
SELECT * FROM pgstattuple_approx('public.t_order');

-- autovacuum 是否被长期欠账（阈值：默认 dead tuples > 表行数*0.2 + 50 才触发）
SHOW autovacuum;
SHOW autovacuum_vacuum_threshold;
SHOW autovacuum_vacuum_scale_factor;

-- 常见的膨胀根因之一：长事务/废弃复制槽持有 xmin，VACUUM 无法清理新版本之后的死行
-- ① 找长事务
SELECT pid, state, xact_start, backend_xmin, query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY xact_start ASC;
-- ② 查复制槽（废弃槽会导致 pg_wal 无限堆积；wal_status 为 unreserved/lost 说明槽已拖住 WAL）
SELECT slot_name, slot_type, active, restart_lsn, wal_status
FROM pg_replication_slots;
```

## 4. 释放空间

### 4.1 VACUUM 体系（最常用）

```sql
-- 普通 VACUUM：回收死元组空间供表内复用，【不归还操作系统】，不锁表，可并发
VACUUM (ANALYZE) t_order;         -- 顺便更新统计信息
VACUUM;                           -- 全库

-- VACUUM FULL：物理重写整表、归还操作系统空间
-- ⚠️ 对表加 ACCESS EXCLUSIVE 锁（读写全阻塞），且需要等量的临时磁盘空间，业务表慎用，挑维护窗口
VACUUM (FULL, ANALYZE, VERBOSE) t_order;

-- PG12+ 支持仅索引清理（无死堆 tuples 高水位时可快速回收索引空间）
VACUUM (INDEX_CLEANUP ON) t_order;
```

```shell
# 命令行方式全库 VACUUM（配合维护窗口）
sudo -u postgres vacuumdb -d shopfi_saas --analyze-in-stages -j 4
sudo -u postgres vacuumdb -d shopfi_saas --full --table 'public.t_order'   -- 等价 VACUUM FULL，锁表
```

> 生产上想在线整理表空间（不锁表）用 `pg_repack` 扩展，原理是触发器 + 影子表换名，效果等同 VACUUM FULL。

### 4.2 autovacuum 调优（治本）

```sql
-- 大表按比例触发太迟时，按表收紧阈值（表级参数）
ALTER TABLE t_order SET (autovacuum_vacuum_scale_factor = 0.02);   -- 死元组达 2% 即清理
ALTER TABLE t_order SET (autovacuum_vacuum_threshold = 1000);

-- 频繁更新的表：每次批量写入后手动收尾
VACUUM (ANALYZE) t_order;
```

### 4.3 索引空间

```sql
-- 重建索引释放膨胀（PG12+ CONCURRENTLY 不锁写）
REINDEX INDEX CONCURRENTLY idx_order_user_id;

-- 重建某库全部索引
REINDEX DATABASE shopfi_saas;

-- 直接删掉"从未使用"的索引（先观察 idx_scan 覆盖一个完整业务周期）
SELECT schemaname, relname, indexrelname, pg_size_pretty(pg_relation_size(indexrelid)) AS size, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT IN (   -- 排除约束/主键在用的索引
      SELECT conname FROM pg_constraint WHERE contype IN ('p','u','f')
  )
ORDER BY pg_relation_size(indexrelid) DESC;
-- 确认后再:  DROP INDEX CONCURRENTLY idx_xxx;
```

### 4.4 WAL / 归档堆积

```sql
-- 复制槽导致的 WAL 堆积：删掉不用的槽（不用的备库/订阅槽最常见）
SELECT * FROM pg_replication_slots;
SELECT pg_drop_replication_slot('废弃槽名');

-- 兜底：限制单个槽最多保留的 WAL 量（防止再次撑爆磁盘）
ALTER SYSTEM SET max_slot_wal_keep_size = '20GB';
SELECT pg_reload_conf();

-- 归档卡住时检查归档进程状态
SELECT * FROM pg_stat_archiver;
```

```shell
# 手动清理已归档/已备份的 WAL 文件（确认备库/归档都已消费后再删！）
sudo -u postgres pg_archivecleanup /var/lib/postgresql/16/main/pg_wal 0000000100000000000000A0
```

### 4.5 日志与临时文件

```sql
-- 日志保留：log_rotation_age / log_rotation_size + log_truncate_on_rotation
SHOW log_rotation_size;          -- 单文件上限
SHOW log_truncate_on_rotation;

-- 临时文件（大排序/大哈希溢出产生，在 base/pgsql_tmp）
SHOW temp_file_limit;            -- 限制单会话临时文件量（如 '10GB'），超限报错，防止排序拖爆磁盘
SHOW log_temp_files;             -- 设为 0 可记录所有临时文件，定位大排序 SQL
```

```shell
# 服务器日志裁剪（保留最近 14 天）
sudo find /var/log/postgresql -name "*.gz" -mtime +14 -delete
```

### 4.6 大对象（bytea / large object）

```shell
# vacuumlo 是命令行工具（非 SQL 扩展）：清理已无引用的 large object
# 删过 lo 对象的库定期跑一遍，否则 pg_largeobject 不会自动收缩
sudo -u postgres vacuumlo -v shopfi_saas
```

### 4.7 整表释放

```sql
-- TRUNCATE：瞬间清空整表并归还空间（不触发 VACUUM 的问题）
TRUNCATE TABLE t_log_202501;

-- 分区表按分区直接 DROP，是大数据量表最干净的空间管理方式
-- 例：t_log 按月 RANGE 分区，删掉历史分区（瞬时完成并归还空间）
DROP TABLE t_log_202501;
```

## 5. 空间优化建议（预防）

1. 大表上分区（按时间 RANGE 分区 + 定期 DROP 老分区），空间管理变成"删文件"而不是"VACUUM"。
2. 监控 `n_dead_tup` 与长事务，避免 xmin 被顶住导致膨胀。
3. 定期复查 `pg_stat_user_indexes` 中 `idx_scan=0` 的大索引。
4. `pg_stat_statements` 里 `temp_blks_written` 大的 SQL，优化排序/加索引，减少临时文件。
5. 设置 `max_slot_wal_keep_size`，杜绝复制槽撑爆 WAL。
