## 1. 全景：一条 SQL 的生命周期

PostgreSQL 采用 **进程模型**：每个客户端连接对应一个独立的后端进程（backend，fork 自 postmaster），SQL 的一切处理都发生在该进程内。一条 SQL 从文本到结果经过 6 个阶段，数据结构演变如下：

```text
SQL 文本:  SELECT id, name FROM t WHERE id > 10 ORDER BY name;
   │
   │ ① 词法+语法分析   raw_parser()                      parser/parser.c:42
   ▼
List<RawStmt> ──── 原始语法树 (节点 SelectStmt, 纯语法还原)
   │
   │ ② 语义分析       transformStmt()                   parser/analyze.c:312
   ▼
Query ──────────── 查询树 (rtable / targetList / jointree->quals / sortClause)
   │
   │ ③ 查询重写       QueryRewrite()                    rewrite/rewriteHandler.c:4635
   ▼
Query (重写后) ─── 视图/规则在此展开, 本例原样返回
   │
   │ ④ 查询规划       planner() → create_plan()         optimizer/plan/planner.c:300
   ▼
PlannedStmt ────── 计划树 (本例: Sort ← SeqScan)
   │
   │ ⑤ Portal 封装   PortalStart() → ExecutorStart()   tcop/pquery.c:434
   ▼
QueryDesc / PlanState / EState ── 执行器初始化完成
   │
   │ ⑥ 执行          ExecutePlan() 火山模型             executor/execMain.c:1660
   ▼
TupleTableSlot 流 ──▶ 经 DestReceiver 发回客户端
```

| 阶段 | 职责 | 产出 | 核心代码位置 |
|---|---|---|---|
| ① 词法+语法分析 | SQL 文本 → 语法树 | `List<RawStmt>` | `parser/parser.c:42`、`parser/gram.y` |
| ② 语义分析 | 语法树 → 查询树，补全语义 | `Query` | `parser/analyze.c:312` |
| ③ 查询重写 | 应用规则/视图 | `Query` | `rewrite/rewriteHandler.c:4635` |
| ④ 查询规划 | 查询树 → 物理计划 | `PlannedStmt` | `optimizer/plan/planner.c:300` |
| ⑤ Portal 封装 | 选择执行策略 | `Portal` | `tcop/pquery.c:210,434` |
| ⑥ 执行器 | 火山模型逐元组执行 | `TupleTableSlot` | `executor/execMain.c:1660` |

## 3. 逐阶段代码走读

### 3.1 总调度：exec_simple_query()

`src/backend/tcop/postgres.c:1012`。核心调用链就三行（`postgres.c:1190-1194`）：

```c
parsetree_list = pg_parse_query(query_string);            /* ① 词法+语法分析 (L1065) */
...
querytree_list = pg_analyze_and_rewrite_fixedparams(      /* ②③ 语义分析+重写 (L1190) */
                    parsetree, query_string, NULL, 0, NULL);
plantree_list = pg_plan_queries(querytree_list, query_string,   /* ④ 生成计划 (L1193) */
                    CURSOR_OPT_PARALLEL_OK, NULL);
```

随后（`postgres.c:1216-1279`）创建 Portal → `PortalStart()` → `PortalRun()` 执行，最后 `PortalDrop()` + `EndCommand()`。

### 3.2 阶段① 词法 + 语法分析（SQL 文本 → 原始语法树）

- **入口**：`pg_parse_query()` — `tcop/postgres.c:604`，内部调 `raw_parser()` — `parser/parser.c:42`
- **词法**：`src/backend/parser/scan.l`（flex 源码，编译产物为 `scan.c`）——把文本切成 token；关键字表在 `src/include/parser/kwlist.h`
- **语法**：`src/backend/parser/gram.y`（bison 源码，编译产物为 `gram.c`）——LALR 归约生成语法树

> **Debug 提示**：断点打在 `raw_parser()` 返回处，`p *parsetree_list` 可以看到 `RawStmt`。gram.y 中与 SELECT 相关的规则：`SelectStmt:` 在 `gram.y:12823`，`simple_select:` 在 `gram.y:12935`。

**本例产出**（一个 `SelectStmt` 节点，还原 SQL 用）：

```c
SelectStmt {
  targetList: [ ResTarget(id), ResTarget(name) ],   /* SELECT 列表, 仅文本还原 */
  fromClause: [ RangeVar("t") ],                    /* FROM, 仅语法层 */
  whereClause: [ A_Expr(">") (ColumnRef id, Const 10) ],
  sortClause: [ SortBy(name) ]
}
```

注意：此阶段**纯语法**，`id` 是列还是函数参数、`t` 是表还是视图一概不知。

### 3.3 阶段② 语义分析（原始语法树 → 查询树 Query）

- **入口**：`parse_analyze_fixedparams()`（由 `pg_analyze_and_rewrite_fixedparams()` — `postgres.c:666` 调用）
- **分发**：`transformStmt()` — `parser/analyze.c:312`，按语句类型分发。SELECT 分支（`analyze.c:367-378`）：

```c
case T_SelectStmt:
    {
        SelectStmt *n = (SelectStmt *) parseTree;
        if (n->valuesLists)
            result = transformValuesClause(pstate, n);      /* SELECT 1,2 */
        else if (n->op == SETOP_NONE)
            result = transformSelectStmt(pstate, n);        /* 普通SELECT */
        else
            result = transformSetOperationStmt(pstate, n);  /* UNION等集合操作 */
    }
```

- **`transformSelectStmt()`** — `parser/analyze.c:1389`，子步骤：

| 子步骤 | 函数 | 位置 | 职责 |
|---|---|---|---|
| FROM 子句 | `transformFromClause()` | `parse_clause.c:112` | 打开表（`table_openrv`，加 `AccessShareLock`），建 `RangeTblEntry`(rtable) |
| 目标列 | `transformTargetList()` | `parse_target.c:121` | 解析列引用，生成 `TargetEntry` |
| WHERE | `transformWhereClause()` | `parse_clause.c:1854` | 表达式语义化，产出 `qual` |
| HAVING | `transformWhereClause()` | 同上 | 同上 |
| ORDER BY | `transformSortClause()` | `parse_clause.c:2732` | 生成 `SortGroupClause` |
| 表达式 | `transformExpr()` | `parse_expr.c:119` | 递归把 `A_Expr/ColumnRef` 等变成带类型的表达式树 |

**产物 `Query`**（定义在 `src/include/nodes/parsenodes.h`）核心字段：

```c
Query {
  commandType:   CMD_SELECT,
  rtable:        [ RangeTblEntry("t") ],   /* 范围表: 涉及哪些表 */
  jointree:      { fromlist, quals: id > 10 },  /* 连接树+过滤条件 */
  targetList:    [ TargetEntry(id), TargetEntry(name) ],
  sortClause:    [ SortGroupClause → name ],
  hasAggs / hasSubLinks / ...
}
```

此阶段会做：列名/表名解析（查系统目录 `pg_class`/`pg_attribute`）、类型推导与隐式转换、权限检查（`pg_class.relacl`）。

### 3.4 阶段③ 查询重写（Query → Query）

- **`pg_rewrite_query()`** — `tcop/postgres.c:799`
- **`QueryRewrite()`** — `src/backend/rewrite/rewriteHandler.c:4635`
- **`RewriteQuery()`** — `rewriteHandler.c:3947`（递归处理规则动作）

职责：应用 `pg_rewrite` 系统表中定义的规则。**视图就是通过该阶段展开的**（`_RETURN` 规则把视图名替换为视图定义）。本例无视图，Query 原样返回。

### 3.5 阶段④ 查询规划（Query → PlannedStmt）

优化器是"路径搜索 + 代价模型"两段式：

```c
/* tcop/postgres.c:971 */  pg_plan_queries() → pg_plan_query() (L883)
/* optimizer/plan/planner.c:300 */  planner()   /* 允许插件 hook, 默认进 standard_planner :316 */
/* planner.c:664 */  subquery_planner()        /* 主要优化工作: 子查询上拉、谓词下推等 */
/* planner.c:1567 */  grouping_planner()       /* 处理 GROUP/ORDER/LIMIT; L1700 调 preprocess_targetlist */
/* optimizer/path/allpaths.c:175 */  make_one_rel()  /* 生成访问路径: seqscan/indexscan/join 顺序... */
/* planner.c:3586 */  standard_qp_callback()   /* 排序/分组路径的路径键 */
```

- **Path → Plan 转换**：`create_plan()` — `optimizer/plan/createplan.c:337`（`create_scan_plan()` :559、`create_seqscan_plan()` :2910）
- 代价模型：`optimizer/path/costsize.c`（`cost_seqscan`、`cost_index`、`cost_sort`…）

**本例产出 `PlannedStmt`**（`parsenodes.h`）：

```text
PlannedStmt { planTree:
  Sort (ORDER BY name)               ← 节点定义 src/include/nodes/plannodes.h
   └─ SeqScan { filter: id > 10, target: t }
}
```

用 `EXPLAIN SELECT ...` 看到的就是这棵树的摘要。

### 3.6 阶段⑤ Portal：执行策略选择

- **`CreatePortal()`** — `utils/mmgr/portalmem.c:175`，**`PortalStart()`** — `tcop/pquery.c:434`
- **`ChoosePortalStrategy()`** — `tcop/pquery.c:210`，按计划树顶层节点决定策略：

| 策略 | 触发条件 | 执行方式 |
|---|---|---|
| `PORTAL_ONE_SELECT` | 纯 SELECT | 逐元组拉取，可部分执行（游标） |
| `PORTAL_ONE_MOD_WITH` | DML 带 CTE（`pquery.c:234`） | 同上 |
| `PORTAL_ONE_RETURNING` | DML 带 RETURNING | 执行完缓存结果集 |
| `PORTAL_MULTI_QUERY` | 其余（无 RETURNING 的 DML、DDL） | 一次性跑完，不返回元组 |

SELECT 命中 `PORTAL_ONE_SELECT` 后，`PortalStart()` 里会创建 `QueryDesc`（`CreateQueryDesc()` — `pquery.c:68`）并调用 **`ExecutorStart()`**（`executor/execMain.c:122` → `standard_ExecutorStart()` :141）初始化执行状态（`EState`）和 `PlanState` 树（`ExecInitNode()` — `executor/execProcnode.c:142`）。

> 注意区分：DDL / BEGIN / COMMIT 等不走优化器，在 `PortalRunMulti()`（`pquery.c:1185`）里进入 `ProcessUtility()`（`tcop/utility.c:499` → `standard_ProcessUtility()` :543）。SELECT/UPDATE/DELETE/INSERT 都走执行器。

### 3.7 阶段⑥ 执行：火山模型（Volcano / 迭代器模型）

**`PortalRun()`**（`pquery.c:685`）→ **`PortalRunSelect()`**（`pquery.c:864`）→ **`ExecutorRun()`**（`execMain.c:297` → `standard_ExecutorRun()` :307）→ **`ExecutePlan()`**（`execMain.c:1660`）：

```c
/* execMain.c:1660 ExecutePlan() 核心循环 (火山模型) */
for (;;)
{
    slot = ExecProcNode(planstate);   /* 向计划树要一条元组 */
    ...
    if (TupIsNull(slot)) break;       /* 取完 */
    /* 经 DestReceiver 发给客户端 */
}
```

`ExecProcNode()` 是 `src/include/executor/executor.h:310` 的内联函数：每个 `PlanState` 节点维护一个函数指针，首次调用经 `ExecProcNodeFirst()`（`execProcnode.c:448`）切换到具体实现，之后每次调用只做一次间接跳转——这就是火山模型的"向上逐条吐元组"。

**本例的执行树与数据流**（`SeqScan` 在下、`Sort` 在上，Sort 第一次被要数据时会拉空整个子树做外部排序，之后一次性吐出）：

```text
ExecutePlan()  execMain.c:1660        ← 火山模型驱动层
   │  slot = ExecProcNode(planstate)
   ▼
[Sort 节点]
   ExecInitSort()  nodeSort.c:221 / ExecSort() :50
   首次被要数据 → 递归拉空子节点全部元组 → tuplesort 外排 → 之后逐条吐出
   ▲
   │ 拉取
[SeqScan 节点]
   ExecInitSeqScan()  nodeSeqscan.c:207
   PG18 按 qual/projection 选择执行变体:
     ExecSeqScan :110 / WithQual :130 / WithProject :150 / WithQualProject :171
   │  SeqNext()  nodeSeqscan.c:51  → table_scan_getnextslot()
   ▼
[Heap 表访问方法 (Table AM)]
   heap_beginscan()  heapam.c:1104  ← 以 estate->es_snapshot 打开扫描 (MVCC 快照)
   heap_getnextslot()  access/heap/heapam.c:1388
     └─ heapgettup_pagemode()  :1010  (逐条模式走 heapgettup() :900)
     └─ MVCC 可见性: HeapTupleSatisfiesMVCC()  heapam_visibility.c:960 (判定流程见 §4.3)
   ▼
[缓冲区管理]
   ReadBufferExtended()  storage/buffer/bufmgr.c:805
     └─ ReadBuffer_common()  :1184   磁盘块 → shared_buffers
   ▼
TupleTableSlot 返回上层 → 客户端
```

### 3.8 收尾

`PortalRun` 返回后（`postgres.c:1281-1337`）：`receiver->rDestroy()` → `PortalDrop()` → `finish_xact_command()` → `EndCommand()` 向客户端发送 `CommandComplete`。异常时经 `PG_CATCH` → `AbortCurrentTransaction()`（同文件错误恢复块）。

## 4. MVCC 机制基础（SELECT / UPDATE / DELETE 共用）

> UPDATE / DELETE 各自的 MVCC 实现细节见 `001.Postgresql-Update流程.md` §4 / `002.Postgresql-Delete流程.md` §4。

### 4.1 多版本与元组头

MVCC 核心：UPDATE/DELETE **不覆盖旧数据**，每次修改产生新版本；每个版本用 `xmin`（插入它的事务）和 `xmax`（删除/锁定它的事务）描述生命周期，读操作按快照自行挑选可见版本，**读写互不阻塞**。

元组头 `HeapTupleHeaderData`（`src/include/access/htup.h:21`，字段定义 `src/include/access/htup_details.h`）：

| 字段 | 位置 | 含义 |
|---|---|---|
| `t_xmin` | htup_details.h:124 | 插入该版本的事务 ID |
| `t_xmax` | htup_details.h:125 | 删除/锁定该版本的事务 ID（0 = 未被删） |
| `t_cid` | htup_details.h:129 | 事务内命令 ID（配合快照 curcid 区分同事务内先后） |
| `t_ctid` | htup_details.h:161 | 本条或更新版本的 TID —— **版本链指针** |
| `t_infomask` | htup_details.h | 提交状态提示位等标志 |

版本链示意：

```text
(插入事务 100)              (事务 200 UPDATE)           (事务 300 再 UPDATE)
HeapTuple v1                HeapTuple v2                HeapTuple v3
t_xmin = 100                t_xmin = 200                t_xmin = 300
t_xmax = 200 ─────────────▶ t_xmax = 300 ─────────────▶ t_xmax = 0 (现行版本)
t_ctid → v2 的 TID          t_ctid → v3 的 TID          t_ctid → 自身
```

提交/回滚状态缓存在 **hint bits**（`t_infomask`，`htup_details.h:204-208`：`HEAP_XMIN_COMMITTED` / `HEAP_XMIN_INVALID` / `HEAP_XMAX_COMMITTED` / `HEAP_XMAX_INVALID` / `HEAP_XMIN_FROZEN`），首次判定时写入避免反复查 CLOG；状态未知时查提交日志：`TransactionIdDidCommit()` — `access/transam/transam.c:126`（CLOG SLRU 本体在 `access/transam/clog.c`）。

### 4.2 快照 (Snapshot)

快照 = "某一时刻哪些事务已提交"的集合描述。`SnapshotData`（`src/include/utils/snapshot.h:138`）核心字段：

```text
xmin   : 所有 < xmin 的事务已完成, 对快照可见     (snapshot.h:154)
xmax   : 所有 >= xmax 的事务对快照不可见          (snapshot.h:155)
xip[]  : [xmin, xmax) 之间仍在进行中的事务列表 (不可见)
curcid : 命令 ID, 可见本事务中"本命令之前"产生的元组
```

快照在 SELECT 主线中的建立与下发（对应 §2 流程图两处标注）：

```text
exec_simple_query() 语句循环内                       tcop/postgres.c:1161
  analyze_requires_snapshot(parsetree)
    → PushActiveSnapshot(GetTransactionSnapshot())   postgres.c:1163
        GetTransactionSnapshot()                     utils/time/snapmgr.c:271
          ├─ READ COMMITTED : 每条语句取新快照
          │     GetSnapshotData()  storage/ipc/procarray.c:2175
          └─ REPEATABLE READ / SERIALIZABLE : 首次取得后整个事务复用
                (IsolationUsesXactSnapshot() 分支, snapmgr.c:315)

standard_ExecutorStart()                             executor/execMain.c:245
  estate->es_snapshot = RegisterSnapshot(queryDesc->snapshot)
扫描时携带快照:  heap_beginscan()                     access/heap/heapam.c:1104
收尾注销:        UnregisterSnapshot()                 execMain.c:507
```

> 这解释了 READ COMMITTED 下同一事务内两条 SELECT 可能看到不同结果：每条语句重新取快照。

### 4.3 可见性判断流程（SELECT 读路径）

`HeapTupleSatisfiesMVCC()` — `access/heap/heapam_visibility.c:960`：

```text
HeapTupleSatisfiesMVCC(元组, 快照, buffer)
   │
   ├─ t_xmin 状态?
   │    ├─ 已回滚 / 进行中且非本事务           → 不可见
   │    ├─ 本事务但 cid > curcid              → 不可见 (未来命令插入的)
   │    └─ 已提交且 < snapshot.xmin           → 看 t_xmax ▼
   │        (状态未知: 查 CLOG transam.c:126, 回写提示位 SetHintBits() visibility.c:114)
   │
   └─ t_xmax 状态?
        ├─ 无 xmax / 已回滚                   → 可见
        ├─ 本事务 cid > curcid                → 可见 (删除发生在未来命令)
        ├─ 已提交且 >= snapshot.xmin 或在 xip[] → 不可见 (已被删/更新的旧版本)
        └─ 已提交且 < snapshot.xmin           → 对本快照不可见
```

同族判定函数（同文件，不同用途）：

| 函数 | 行号 | 用途 |
|---|---|---|
| `HeapTupleSatisfiesSelf` | visibility.c:170 | 无快照场景（DDL、单用户模式） |
| `HeapTupleSatisfiesAny` | visibility.c:340 | 全部可见（SnapshotAny，VACUUM 扫描用） |
| `HeapTupleSatisfiesDirty` | visibility.c:743 | 脏读语义（未提交版本也返回） |
| `HeapTupleSatisfiesUpdate` | visibility.c:458 | UPDATE/DELETE 判定目标行状态，返回 `TM_Result`（见 001 文档 §4.1） |
| `HeapTupleSatisfiesMVCC` | visibility.c:960 | SELECT 的标准 MVCC 判定 |

> **PG 18 变化**：旧版快照结构里的 `snapshot->satisfies` 函数指针已移除，扫描统一经分发函数 `HeapTupleSatisfiesVisibility()`（`heapam_visibility.c:1776`）按 `snapshot->snapshot_type` 路由到上表对应实现。
>
> **注意**：UPDATE/DELETE 的**修改**阶段不用本函数，而是走 `HeapTupleSatisfiesUpdate()`（返回 `TM_Result` 多态结果）；但它们的**找行**子计划扫描时仍走 `HeapTupleSatisfiesMVCC`，详见 `001.Postgresql-Update流程.md` §4 / `002.Postgresql-Delete流程.md` §4 引言。

## 6. SELECT / UPDATE / DELETE 三阶段对照表

详细流程见 `001.Postgresql-Update流程.md` / `002.Postgresql-Delete流程.md`。

| 阶段 | SELECT | UPDATE | DELETE |
|---|---|---|---|
| 语法规则 gram.y | `SelectStmt:` :12823 | `UpdateStmt:` :12497 | `DeleteStmt:` :12427 |
| 语义分析 analyze.c | `transformSelectStmt` :1389 | `transformUpdateStmt` :2472 | `transformDeleteStmt` :553 |
| 表锁 | `AccessShareLock`（FROM 表） | `RowExclusiveLock` | `RowExclusiveLock` |
| 计划顶层节点 | `Sort` / `SeqScan` 等普通节点 | `ModifyTable(CMD_UPDATE)` | `ModifyTable(CMD_DELETE)` |
| targetList 特殊列 | 正常列 | junk 列 `ctid`（定位旧行） | junk 列 `ctid` |
| Portal 策略 | `PORTAL_ONE_SELECT` | `PORTAL_ONE_RETURNING` / `PORTAL_ONE_MOD_WITH` / `PORTAL_MULTI_QUERY` | 同 UPDATE |
| 执行节点 | `ExecSeqScan`（nodeSeqscan.c:110） | `ExecModifyTable` → `ExecUpdate` :2461 | `ExecModifyTable` → `ExecDelete` :1572 |
| 堆操作 | 只读（可见性判断） | `heap_update` :3321 追加新版本 | `heap_delete` :2828 标记 xmax |
| 行锁 | 无 | 元组级锁 + `EvalPlanQual` | 元组级锁 + `EvalPlanQual` |
| WAL | 无 | `XLOG_HEAP_UPDATE` | `XLOG_HEAP_DELETE` :3204 |

> 补充：INSERT 同框架，走 `ExecInsert()`（`nodeModifyTable.c:850`）→ `heap_insert()`（`heapam.c:2081`，WAL 写点 :2248）。
