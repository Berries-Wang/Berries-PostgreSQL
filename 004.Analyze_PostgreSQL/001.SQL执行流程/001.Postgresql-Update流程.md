# PostgreSQL UPDATE 执行流程分析

> **源码版本**：PostgreSQL 18.6
> **源码根目录**：`000.SOURCE_CODE/002.PostgreSQL-18.6/postgresql-18.6`
> 下文所有 `文件:行号` 均以该源码树为准（2026-10 核对）。
> 公共流程（词法→语法→语义分析→重写→规划→Portal 入口）见同目录 `000.Postgresql-Select流程.md`，本文只讲 UPDATE 的差异部分。DELETE 见 `002.Postgresql-Delete流程.md`。

---

## 1. 与公共路径的关系

UPDATE 与 SELECT 共享完全相同的前半段（通信入口、词法/语法分析、语义分析框架、重写、规划框架、Portal、ExecutorStart/Run 入口），差异从**语法规则**开始，核心差异集中在三点：

1. **语义分析**：要确定目标表（`resultRelation`）并以 `RowExclusiveLock` 打开它；
2. **计划树**：顶层是 `ModifyTable` 节点，子计划负责找行，targetList 里的 **junk 列 ctid** 用于定位旧行；
3. **执行**：不是纯读——逐行 BEFORE 触发器 → 写堆（追加新版本、加行锁、写 WAL、更新所有索引）→ 并发冲突走 `EvalPlanQual` 重试 → AFTER 触发器 / RETURNING。

## 4. UPDATE 中的 MVCC 实现

> 快照、元组头、提示位、可见性判定等公共基础见 `000.Postgresql-Select流程.md` §4。

UPDATE 流程中有**两个不同的可见性检查点**，容易混淆：

**检查点 1 —— 找行阶段（子计划 SeqScan）**：带着执行器 MVCC 快照（`estate->es_snapshot`，`SNAPSHOT_MVCC` 类型）扫描，判定最终落到 `HeapTupleSatisfiesMVCC()`：

```text
pagemode (默认路径):
   heapgettup_pagemode()   heapam.c:1010
     └─ heap_prepare_pagescan()    调用点 :1050, 定义 :556
          └─ page_collect_tuples()  heapam.c:506
               └─ HeapTupleSatisfiesVisibility()   heapam.c:531
逐条模式:
   heapgettup()  heapam.c:900
     └─ HeapTupleSatisfiesVisibility()             heapam.c:955

HeapTupleSatisfiesVisibility()  access/heap/heapam_visibility.c:1776
   └─ 按 snapshot->snapshot_type 分发
        SNAPSHOT_MVCC → HeapTupleSatisfiesMVCC()  (visibility.c:960)
   (PG18 已移除旧版 snapshot->satisfies 函数指针, 统一走此分发函数)
```

**检查点 2 —— 修改阶段（heap_update）**：改用 `HeapTupleSatisfiesUpdate()`（见 §4.1）。为什么不复用 MVCC 判定？修改阶段要回答的不是"这行对快照是否可见"（bool），而是"**这行被谁动过**"——自己哪个 cid？别的事务？提交了没有？——并以 `TM_Result` 多态结果驱动等待、重试和 EvalPlanQual；且扫描返回元组到真正改行之间行可能已被并发修改，必须在页上重新判定，不能沿用扫描时的结论。

### 4.1 并发判定与行锁等待（heap_update 内部）

`heap_update()`（`access/heap/heapam.c:3321`）取到目标行后，用 `HeapTupleSatisfiesUpdate()`（`access/heap/heapam_visibility.c:458`，调用点 `heapam.c:3554`）判定该行并发状态，返回 `TM_Result` 枚举（定义在 `src/include/access/tableam.h:74`）：

```text
TM_Ok             无冲突, 直接更新
TM_Invisible      行对本快照不可见 (不该发生, 报错)
TM_SelfModified   被本事务改过 (按 cid 判断能否继续)
TM_Updated        已被别的事务更新 (含跨分区移动)   ┐
TM_Deleted        已被别的事务删除                  ├→ 进入等待/重评估
TM_BeingModified  正在被别的事务修改 (未提交)       ┘
```

等待路径（`heapam.c:3321` 起）：

```text
TM_BeingModified / TM_Updated / TM_Deleted
   ├─ 对方是单个事务:
   │    heap_acquire_tuplock()   heapam.c:3627   (持 LockTupleExclusive 元组锁)
   │    → XactLockTableWait(xwait, ..., XLTW_Update)   heapam.c:3632
   │          (实现: storage/lmgr/lmgr.c:663, 阻塞等对方事务结束,
   │           等待期间由 storage/lmgr/deadlock.c 做死锁检测)
   ├─ 对方是多事务 (multixact): MultiXactIdWait 路径   (heapam.c:3715 附近)
   └─ 等待结束后重读该行:
        仍是最新可见版本且 WHERE 仍满足 → 以新版本重试更新
        WHERE 不再满足 → 放弃该行
        ("重评估"由上层 EvalPlanQual() 完成, 见 §4.2)
```

### 4.2 EvalPlanQual：冲突后的重评估

```text
heap_update 返回 TM_Updated / TM_Deleted (对方已提交)
   → ExecUpdate 收到 → EvalPlanQual()            executor/execMain.c:2653
       ├─ EvalPlanQualBegin()   :2936   重置 EPQ 执行状态
       ├─ EvalPlanQualSlot()    :2781   把"最新版本元组"放进测试槽
       └─ 用原计划树(只读模式)对新元组重新求值 WHERE / JOIN
            ├─ 仍满足 → ExecUpdate 以新版本重试
            └─ 不满足 → 该行跳过 (窗口期内被别人改掉了)
```

### 4.3 版本链与索引

- 更新成功后新版本写入堆，旧版本 `t_ctid` 指向新版本形成链（示意见 000 文档 §4.1）
- **非 HOT 更新**：所有索引都要插入指向新版本的条目（`ExecInsertIndexTuples` 驱动）；满足 HOT 条件（索引列未变且新版本在同页）时走 HOT 链，不新增索引项
- 旧版本仍保留：对已取快照的事务可见，提交后成为死元组，由页内剪枝（`heap_page_prune_opt()` — `access/heap/pruneheap.c:193`）或 VACUUM（`lazy_scan_heap()` — `access/heap/vacuumlazy.c:1200`）回收

## 5. Debug 实战指南（UPDATE 专项）

### 5.1 断点清单

```text
parser/analyze.c:2472        transformUpdateStmt
executor/nodeModifyTable.c:4656 ExecInitModifyTable
executor/nodeModifyTable.c:4175 ExecModifyTable        # 每行停一次
executor/nodeModifyTable.c:2461 ExecUpdate
access/heap/heapam.c:3321    heap_update               # 看并发判定/版本链
access/heap/heapam.c:3554    HeapTupleSatisfiesUpdate
executor/execMain.c:2653     EvalPlanQual              # 并发冲突重试
```

> 注意：`ExecModifyTable` / `ExecUpdate` / `heap_update` 会在**每一行**上命中，大表调试前先 `LIMIT` 或用小表。`heap_update` 内部在拿到缓冲区锁后调用，此时单步跟踪要小心（持有 buffer content lock）。

### 5.2 复现并发冲突（EvalPlanQual）

```text
会话 A                                会话 B
BEGIN;
UPDATE t SET name='a' WHERE id=10;
                                      UPDATE t SET name='b' WHERE id=10;  -- 阻塞等行锁
COMMIT;
                                      -- B 拿到锁后:
                                      -- heap_update 里 HeapTupleSatisfiesUpdate()
                                      -- 返回 HeapTupleUpdated,
                                      -- 走 EvalPlanQual (execMain.c:2653) 重评估,
                                      -- 条件仍满足则以新版本重试更新
```

在 `heap_update()`（`heapam.c:3554`）处断点可看到 `HeapTupleBeingUpdated` / `HeapTupleUpdated` 分支；两窗口分别 attach 同一后端或用条件断点区分会话。

### 5.3 观察 junk 列与计划

```sql
EXPLAIN (VERBOSE) UPDATE t SET name='x' WHERE id > 10;
-- 输出里 SeqScan 节点会看到 ctid 被加入输出列 (JunkFilter 的来源)
```
