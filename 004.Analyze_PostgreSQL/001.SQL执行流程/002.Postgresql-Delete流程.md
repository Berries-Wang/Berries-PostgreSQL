# PostgreSQL DELETE 执行流程分析

> **源码版本**：PostgreSQL 18.6
> **源码根目录**：`000.SOURCE_CODE/002.PostgreSQL-18.6/postgresql-18.6`
> 下文所有 `文件:行号` 均以该源码树为准（2026-10 核对）。
> 公共流程（词法→语法→语义分析→重写→规划→Portal 入口）见同目录 `000.Postgresql-Select流程.md`，UPDATE 见 `001.Postgresql-Update流程.md`。

---

## 1. 与公共路径的关系

DELETE 与 SELECT/UPDATE 共享完全相同的前半段（通信入口、词法/语法分析、语义分析框架、重写、规划框架、Portal、ExecutorStart/Run 入口），差异从**语法规则**开始，核心差异集中在三点：

1. **语义分析**：确定目标表（`resultRelation`）并以 `RowExclusiveLock` 打开它；
2. **计划树**：顶层是 `ModifyTable(CMD_DELETE)` 节点，子计划负责找行，targetList 里的 **junk 列 ctid** 用于定位要删的行；
3. **执行**：逐行 BEFORE 触发器 / 外键检查 → `heap_delete` 把旧元组**标记删除**（`xmax`）、写 WAL → 并发冲突走 `EvalPlanQual` 重试 → AFTER 触发器 / RETURNING。

与 UPDATE 相比，DELETE 少了"追加新版本 + 更新所有索引"两步，其余框架一致。

## 4. DELETE 中的 MVCC 实现

> 快照、元组头、提示位、可见性判定等公共基础见 `000.Postgresql-Select流程.md` §4；UPDATE 侧的判定/等待/EvalPlanQual 细节见 `001.Postgresql-Update流程.md` §4，两者同构。

DELETE 流程中有**两个不同的可见性检查点**，容易混淆：

**检查点 1 —— 找行阶段（子计划 SeqScan）**：带着执行器 MVCC 快照（`estate->es_snapshot`，`SNAPSHOT_MVCC` 类型）扫描，判定最终落到 `HeapTupleSatisfiesMVCC()`：

```text
pagemode (默认路径):
   heapgettup_pagemode()   heapam.c:1010
     └─ heap_prepare_pagescan()    调用点 :1050, 定义 :556
          └─ page_collect_tuples()  heapam.c:506
               └─ HeapTupleSatisfiesVisibility()   heapam.c:531
逐条模式:
   heapgettup()  heapam.c:900
     └─ HeapTupleSatisfiesVisibility()             heapam.c:955

HeapTupleSatisfiesVisibility()  access/heap/heapam_visibility.c:1776
   └─ 按 snapshot->snapshot_type 分发
        SNAPSHOT_MVCC → HeapTupleSatisfiesMVCC()  (visibility.c:960)
   (PG18 已移除旧版 snapshot->satisfies 函数指针, 统一走此分发函数)
```

**检查点 2 —— 修改阶段（heap_delete）**：改用 `HeapTupleSatisfiesUpdate()`（见 §4.1）。原因：修改阶段要回答的不是"这行对快照是否可见"（bool），而是"**这行被谁动过**"，并以 `TM_Result` 多态结果驱动等待、重试和 EvalPlanQual；且扫描返回元组到真正删行之间行可能已被并发修改，必须在页上重新判定。

### 4.1 并发判定与行锁等待（heap_delete 内部）

`heap_delete()`（`access/heap/heapam.c:2828`）对目标行调用 `HeapTupleSatisfiesUpdate()`（`access/heap/heapam_visibility.c:458`，调用点 `heapam.c:2902`），返回 `TM_Result`（枚举定义 `src/include/access/tableam.h:74`：`TM_Ok` / `TM_Invisible` / `TM_SelfModified` / `TM_Updated` / `TM_Deleted` / `TM_BeingModified`）。

等待路径（与 UPDATE 同构，`heapam.c:2828` 起）：

```text
TM_BeingModified / TM_Updated / TM_Deleted
   ├─ heap_acquire_tuplock()            heapam.c:2988   (LockTupleExclusive)
   ├─ 对方是单事务:
   │    XactLockTableWait(xwait, ..., XLTW_Delete)   heapam.c:2990
   │      (实现: storage/lmgr/lmgr.c:663; 等待期间做死锁检测)
   ├─ 对方是多事务 (multixact): MultiXactIdWait()    heapam.c:2951
   └─ 等待后重读行 → EvalPlanQual() 重评估            execMain.c:2653
        WHERE 仍满足 → 重试删除; 不满足 → 跳过
```

### 4.2 标记删除的语义（无冲突路径）

- `heap_delete` 无冲突时只把旧元组的 `t_xmax` 置为当前事务 ID（提交时 `t_infomask` 置 `HEAP_XMAX_COMMITTED`）——**行数据原地不动，不覆写**
- 对**已打开旧快照**的事务仍可见（可见性按各快照自己的 xmin/xmax 规则判断，见 000 文档 §4.3）；对新快照不可见
- 索引项**同样不删除**，仅随之成为死元组，VACUUM 时才清理索引条目
- 因此高频 DELETE 的表空间不会自动缩小，回收依赖两级机制：

```text
死元组回收两级路径
   ├─ 页内剪枝 (HOT prune): heap_page_prune_opt()          access/heap/pruneheap.c:193
   │    读写触到该页时顺带清理同链死元组
   │    (heap_page_prune_and_freeze() :350, 实际改页 heap_page_prune_execute() :1561)
   └─ VACUUM: heap_vacuum_rel()                            access/heap/vacuumlazy.c:615
        lazy_scan_heap() :1200 逐页扫描死元组 + 索引清理
        配合可见性位图 visibilitymap.c: 全可见页可跳过
```

## 5. Debug 实战指南（DELETE 专项）

### 5.1 断点清单

```text
parser/analyze.c:553         transformDeleteStmt
executor/nodeModifyTable.c:4656 ExecInitModifyTable
executor/nodeModifyTable.c:4175 ExecModifyTable        # 每行停一次
executor/nodeModifyTable.c:1572 ExecDelete
access/heap/heapam.c:2828    heap_delete               # 看并发判定/标记删除
access/heap/heapam.c:2902    HeapTupleSatisfiesUpdate
access/heap/heapam.c:3204    XLogInsert(XLOG_HEAP_DELETE)
executor/execMain.c:2653     EvalPlanQual              # 并发冲突重试
```

> 注意：`ExecModifyTable` / `ExecDelete` / `heap_delete` 会在**每一行**上命中，大表调试前先 `LIMIT` 或用小表。

### 5.2 观察

```sql
EXPLAIN (VERBOSE) DELETE FROM t WHERE id > 10;
-- 输出里 SeqScan 节点会看到 ctid 被加入输出列 (JunkFilter 的来源)

-- DELETE 前后对比行版本: 先查当前 ctid/xmin/xmax
SELECT ctid, xmin, xmax, id FROM t WHERE id > 10;
DELETE FROM t WHERE id = 10;
-- 同一事务内/新事务再查: xmax 被置为删除事务的 xid
```

### 5.3 复现并发冲突（EvalPlanQual）

双会话复现步骤与 UPDATE 相同（见 `001.Postgresql-Update流程.md` §5.2），把 UPDATE 换成 DELETE 即可；断点位置为 `heap_delete()`（`heapam.c:2902` 处的 `HeapTupleSatisfiesUpdate()` 判定）与 `EvalPlanQual()`（`execMain.c:2653`）。
