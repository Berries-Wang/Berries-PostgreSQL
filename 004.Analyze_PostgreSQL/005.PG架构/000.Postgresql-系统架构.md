## 2. "每个查询都单独一个进程"是怎么一回事

**准确说法：每个【客户端连接】一个进程（process-per-connection），不是每个 SQL 一个进程。** 一个连接存活期间，里面的所有查询都在同一个后端进程里**串行**执行；真正"一条查询用多个进程"的场景只有并行查询（§2.4）。PG 至今不用线程池——一个进程崩了不会带崩别的连接，这是 PG 稳定性口碑的来源，代价是连接数大时进程多、内存开销高（所以生产上用 pgbouncer 等连接池挡在前面）。

### 2.1 一个连接的一生（时序图）

```text
 客户端                postmaster                          后端进程(新fork)            
   │  connect(5432)        │                                    │                     
   │ ─────────────────────▶│ ServerLoop 事件循环醒来             │                     
   │                       │ AcceptConnection(pqcomm.c:794)     │                     
   │                       │ canAcceptConnections 检查          │                     
   │                       │  (状态/超限? postmaster.c:1812)     │                     
   │                       │ BackendStartup(postmaster.c:3518)  │                     
   │                       │ AssignPostmasterChildSlot          │                     
   │                       │ postmaster_child_launch            │                     
   │                       │   fork_process                     │                     
   │                       │   (launch_backend.c:246) ──fork──▶ │ (子进程拿到同一个       │
   │                       │                                    │  客户端 socket)       │
   │                       │   父进程登记 pid 后继续监听           │ BackendMain           │
   │                       │                                    │ (backend_startup.c:76)│
   │ ◀── 认证握手 ─────────────────────────────────────────────│ ProcessStartupPacket  │
   │    (startup packet/SSL/scram)        :295                 │ pg_hba.conf 认证      │
   │ ◀── ReadyForQuery ─────────────────────────────────────── │ InitPostgres(挂共享内存│
   │                       │                                    │  加载数据库)          │
   │  send QUERY "SELECT …"│                                    │ PostgresMain 主循环    │
   │ ─────────────────────────────────────────────────────────▶ (tcop/postgres.c:4188)│
   │ ◀── 结果行/命令标签 ───────────────────────────────────────│  ReadCommand:481→:4702│
   │                       │                                    │  解析→优化→执行→回包   │
   │  send 下一条查询…       │                                    │  (循环, 直到客户端断开) │
   │  close ──────────────▶│ 收到子进程退出                       │ exit(0)               │
   │                       │ 从 BackendList 摘除, 回收槽位         │                       │
   └───────────────────────┴────────────────────────────────────┴───────────────────────┘
 关键点: postmaster 只在 fork 时"接线", 之后客户端和后端进程直接对话;
        postmaster 继续守在 accept() 上等下一个连接。
```

- 后端主循环 `PostgresMain`（tcop/postgres.c:4188）：`for(;;)` 里 `ReadCommand`（:481，:4702 调用）→ 分发 simple/extended protocol → 回结果 → 循环。每条 SQL 之间还会上报统计（pgstat_report_stat，:4626）。
- 子进程入口统一走 `child_process_kinds[child_type].main_fn`（launch_backend.c:290）；普通连接的入口是 `BackendMain`（tcop/backend_startup.c:76），认证通过后调 `PostgresMain`（backend_startup.c:124）。
- Windows（EXEC_BACKEND）没有 fork，走 `internal_forkexec`（launch_backend.c:306）重新 exec 自身 `--forkchild=…`，再由 `main.c:214 → SubPostmasterMain`（launch_backend.c:598）汇合到同一条路。Linux/macOS 直接 fork 共享内存**已经继承**，无需重新挂载。

### 2.2 进程家族全景（谁拉起谁）

PG 18 把所有子进程类型收进 `BackendType` 枚举（miscadmin.h:337-375）和 `child_process_kinds` 分发表（launch_backend.c:179-209）——这张表就是 PG 的"全家户口本"：

```text
 postmaster (PostmasterMain, postmaster.c:494)
 │
 ├─ 启动时直接 fork (每个最多 1 个, 有 PGPROC 但不连具体数据库)
 │   ├─ StartupProcess        ── StartupProcessMain   startup.c:216     崩溃恢复(§WAL文档 §9)
 │   ├─ Checkpointer          ── CheckpointerMain     checkpointer.c:182
 │   ├─ BackgroundWriter      ── BackgroundWriterMain bgwriter.c:88     (刷脏数据页)
 │   │                            └─ BgBufferSync      bufmgr.c:3643
 │   ├─ WalWriter             ── WalWriterMain        walwriter.c:88    (刷 WAL)
 │   ├─ WalSummarizer(PG17+)  ── WalSummarizerMain    walsummarizer.c:223 (增量备份摘要)
 │   ├─ Archiver(archive_mode=on 才有) ── PgArchiverMain pgarch.c:218
 │   ├─ SysLogger(logging_collector=on 才有) ── SysLoggerMain syslogger.c:165
 │   │      (唯一无 PGPROC、不连共享内存的进程, launch_backend.c:207)
 │   └─ IoWorker × N (PG18, io_method=worker 时) ── IoWorkerMain method_worker.c:386
 │          (异步 I/O 打工人: AIO 提交的读写由他们执行, guc io_method :5444)
 │
 ├─ 有连接/任务才 fork
 │   ├─ 后端进程 × max_connections  ── BackendMain(tcop/backend_startup.c:76)→PostgresMain
 │   ├─ WalSender(物理/逻辑复制)    ── 先以普通后端出生, 复制认证后"变身",
 │   │                                无法直接 launch (launch_backend.c:188-192 注释)
 │   ├─ AutoVacuum Launcher        ── AutoVacLauncherMain autovacuum.c:368
 │   │     └─ 按 need 派生 Worker × N ── AutoVacWorkerMain (do_start_worker :1090, :557 派生)
 │   ├─ 逻辑复制 Launcher          ── ApplyLauncherMain launcher.c:1132 (走 bgworker 机制 :947)
 │   │     └─ 每个订阅一个 Apply Worker
 │   └─ SlotSyncWorker(PG17+)      ── ReplSlotSyncWorkerMain slotsync.c:1457
 │
 └─ 并行查询 worker (查询级, §2.4) ── ParallelWorkerMain parallel.c:1299
      (leader 后端通过 bgworker API 注册拉起, parallel.c:611)
```

> 书 §7.1.1 列的六个辅助进程（Logger/BgWriter/WalWriter/PgArch/AutoVacuum/PgStat）里，**PgStat 在 PG15 起已取消独立进程**——统计改为共享内存 `pgstat.c`，后端自己写、任何人可读（书 §7.1.8 的描述按旧版本理解）。PG18 又新增 IoWorker 和 WalSummarizer。

### 2.3 后端进程内部长什么样（一条 SQL 在进程里怎么走）

```text
 后端进程 (一个连接) — tcop/postgres.c
 ┌──────────────────────────────────────────────────────────────────────┐
 │ PostgresMain (:4188) 主循环                                           │
 │  ┌─────────────────────────────────────────────────────────────┐    │
 │  │ for(;;) {                                                     │    │

 │  │   ReadCommand (:481, 调用 :4702) ── 从 socket 读一条 SQL/协议包 │    │
 │  │        │                                                      │    │
 │  │        ▼                    【本地内存, 进程私有】               │    │
 │  │   解析器  parser/    gram.y→parse_analyze (生成 Query 树)       │    │
 │  │   重写    rewriter/  视图展开/规则                              │    │
 │  │   优化器  optimizer/ planner.c 生成计划树                       │    │
 │  │   执行器  executor/  execMain.c 扫表/改行 (用到 work_mem)       │    │
 │  │        │                                                      │    │
 │  │        ▼  改数据页时: XLogInsert → WAL 缓冲(共享内存) ──┐        │    │

 │  │ } (循环到客户端断开)                                            │    │
 │  └─────────────────────────────────────────────────────────────┘    │
 │  本地内存层级 (mcxt.c:352 MemoryContextInit 建 TopMemoryContext):     │
 │    TopMemoryContext ── 进程终身存活(连接级)                           │
 │      ├─ MessageContext ── 一条查询一清                               │    │
```

（书 §7.1.10 讲的"本地内存三件套：临时缓冲区/work_mem/maintenance_work_mem"对应上图；work_mem 是**每个排序/哈希节点各一份**，不是连接总额。）

## 3. 后台进程各自在干什么（对照视频右侧那列）

| 进程 | 视频里叫法 | 职责（一句话） | 关键源码 | 相关 GUC |
|---|---|---|---|---|
| Checkpointer | Checkpointer | 周期性把所有脏页刷盘+写 checkpoint 记录，划定恢复起点 | checkpointer.c:182 → CreateCheckPoint xlog.c:6929 | checkpoint_timeout / max_wal_size |
| BackgroundWriter | Background Writer | 在 checkpointer 之间**提前**把脏数据页写出去（只 write 不 fsync），让 checkpoint 更轻松 | bgwriter.c:88，核心 BgBufferSync bufmgr.c:3643 | bgwriter_delay / bgwriter_lru_maxpages |
| WalWriter | WAL Writer | 把 WAL 缓冲里的记录提前写到段文件（写+按条件 fsync），异步提交的兜底 | walwriter.c:88 → XLogBackgroundFlush xlog.c:2968 | wal_writer_delay / wal_writer_flush_after |
| Archiver | （视频未画） | 把写满的 WAL 段用 archive_command 复制到归档库 | pgarch.c:218/:381 | archive_mode / archive_command / archive_timeout |
| SysLogger | Logger | 收集各进程 stderr 写日志文件 | syslogger.c:165 | logging_collector |
| AutoVacuum Launcher/Worker | AutoVacuum | 自动 VACUUM/ANALYZE，回收死元组、刷新统计 | autovacuum.c:368/:1090 | autovacuum_* 系列 |
| StartupProcess | （视频未画） | 崩溃/归档恢复时重放 WAL，恢复完退出 | startup.c:216 → StartupXLOG xlog.c:5467 | recovery_* 系列 |
| WalSummarizer | （PG17+） | 生成 WAL 摘要，供增量备份 (pg_basebackup --incremental) 用 | walsummarizer.c:223 | summarize_wal |
| IoWorker | （PG18） | io_method=worker 时替各进程执行异步文件 I/O | method_worker.c:386 | io_method / io_workers |
| 逻辑复制 Launcher/Apply、SlotSync | （视频未画） | 发布订阅与逻辑槽同步 | launcher.c:1132、slotsync.c:1457 | max_sync_workers_per_subscription |

分工记忆法：**数据页的"洗"分两班**（bgwriter 平时写、checkpointer 收尾），**WAL 的"洗"也分两班**（后端提交时自己刷关键的，walwriter 平时刷剩下的），Archiver 只管"写满的段"搬运。

## 4. 共享内存里到底有什么

书 §7.1.9 说"共享内存主要用作数据块缓冲区，WAL 缓冲区和 CLOG 缓冲区也在其中，另存进程信息、锁信息、全局统计信息"——源码里这就是 `CalculateShmemSize()`（ipci.c:89）把各子系统申请的大小逐项相加（:115-152），`CreateSharedMemoryAndSemaphores()`（:200）启动时一次建齐：

## 5. 磁盘上长什么样（$PGDATA）

书 §7.2.3 列了数据目录的配置文件与子目录——PG 18.6 的实际清单来自 initdb 的 `subdirs[]`（initdb.c:231-254）：

```text
 $PGDATA/
 ├─ postgresql.conf      主配置        ├─ postgresql.auto.conf  ALTER SYSTEM 写这里
 ├─ pg_hba.conf          客户端认证     ├─ pg_ident.conf         认证用户映射
 ├─ PG_VERSION           版本号         ├─ postmaster.opts       上次启动命令行
 │
 ├─ base/                默认表空间: base/<数据库OID>/<关系OID>.N
 │                          N=段号: 每段 1GB (RELSEG_SIZE, pg_config.h.in:648,
 │                          公式 configure.ac:302; 超过就切下一段 md.c:49-55)
 │                          同名兄弟文件: rel_fsm(空闲空间) rel_vm(可见性映射)
 ├─ global/              集群级系统表(pg_database…) + pg_control ★
 ├─ pg_wal/              WAL 段文件 (16MB, 名字=TLI+Log+Seg)
 │   ├─ archive_status/  归档标记 *.ready / *.done
 │   └─ summaries/       WAL 摘要 (PG17+)
 ├─ pg_xact/             CLOG: 每事务 2bit 提交状态 (PG10 前叫 pg_clog)
 ├─ pg_multixact/        多事务ID (members/ offsets/)
 ├─ pg_subtrans/ pg_commit_ts/ pg_twophase/ pg_snapshots/
 ├─ pg_tblspc/           表空间符号链接 → 自定义目录
 ├─ pg_replslot/         复制槽
 ├─ pg_logical/          逻辑解码 (snapshots/ mappings/)
 ├─ pg_notify/           LISTEN/NOTIFY 数据
 ├─ pg_stat/ pg_stat_tmp/ 统计持久文件 (PG15 前临时统计在这, 现已并入共享内存)
 ├─ pg_dynshmem/         动态共享内存文件 (EXEC_BACKEND/调试用)
 └─ pg_control 隐藏于 global/ 内: 实例"身份证"+最近 checkpoint (见 WAL 文档 §2.4)
```

数据页内部的页头/元组结构不在此展开，见 `../002.MVCC/` §2 与书 §10.3.2/§10.3.3。

## 6. 一次查询里，各进程怎么配合（把视频的图串起来）

以 `UPDATE t SET ... WHERE id=1` 为例，标出每个进程在这一刻的角色：

```text
 ┌──────────┐  UPDATE  ┌─────────────┐
 │ 客户端应用 │ ───────▶ │  后端进程    │ ① 读计划、扫共享缓冲区找 t 的页
 └──────────┘          │  (你的连接)  │ ② 改页 → 写 WAL 记录进 WAL缓冲区
                       └──────┬──────┘ ③ COMMIT → 自己把 WAL 刷到段文件并 fsync
                              │              (XLogFlush, WAL 文档 §6)
              改的是共享内存里的页 │
                              ▼
        ┌────────────────────────────────────────────┐
        │                共 享 内 存                   │
        │  共享缓冲区: t 的页变脏(还没人写盘)            │
        │  WAL缓冲区: 已被后端 fsync 清空               │
        └──────┬──────────────────┬──────────────────┘
               │                  │
     ④ bgwriter: 有点脏了,我    ⑤ walwriter: 顺手把别人
        提前把这页写出去           没刷完的 WAL 写掉
       (BgBufferSync)            (XLogBackgroundFlush)
               │                  │
               ▼                  ▼
        ┌────────────────────────────────────────────┐
        │                    磁 盘                    │
        │  base/… 数据页(脏页落盘)   pg_wal/ 段文件     │
        └────────────────────────────────────────────┘
               ▲
     ⑥ checkpointer: 周期到了/或 WAL 量到 max_wal_size ——
        把【全部】脏页刷盘 + 写 CHECKPOINT 记录 → 之前的 WAL 可回收
     ⑦ (若 archive_mode=on) pgarch: 写满的 WAL 段 → 归档存储
 后端进程崩溃? ⑧ postmaster 发现 → 杀掉所有子进程 → startup 进程
    从最近 checkpoint 重放 WAL → 数据回到崩溃前状态 (WAL 文档 §9)
```

这就是视频里那张图隐含的全部协作：**后端进程干"活"（执行 SQL、写 WAL），后台进程干"洗"（把内存里的脏东西分批搬去磁盘），postmaster 干"管"（派进程、收尸体、崩了重来）**。

## 8. 架构专项断点

| 想观察 | 断点 | 看什么 |
|---|---|---|
| 连接进来 | `postmaster.c:3518`（BackendStartup）、`launch_backend.c:246`（fork） | 一个连接=一次 fork；父/子进程各自走向 |
| fork 后子进程干什么 | `launch_backend.c:290`（main_fn 分发） | child_type 与对应的 Main 函数 |
| 认证流程 | `tcop/backend_startup.c:295`（ProcessStartupPacket） | startup packet、SSL/scram 协商 |
| 后端主循环 | `tcop/postgres.c:4702`（ReadCommand 调用点） | 每条 SQL 循环一次；MessageContext 反复重置 |
| 后台进程启动顺序 | 实例启动日志 + `postmaster.c` ServerLoop | 各 Main 函数入口逐一命中 |
| 并行查询 | `parallel.c:1299`（ParallelWorkerMain） | worker 进程数、DSM attach |
| postmaster 收尸 | 实例日志 "server process was terminated by signal" | 之后全部子进程重启+恢复 |

技巧：`SELECT * FROM pg_stat_activity;` 的 `backend_type` 列就是 `BackendType` 的人类可读版；`SELECT * FROM pg_backend_memory_contexts;` 能看到当前连接的内存上下文树（§2.3）。
