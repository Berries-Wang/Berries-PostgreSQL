## 1. MVCC 核心思想

**问题**：数据库要同时满足"读写并发"和"一致性读"。传统方案用读锁/写锁互斥，读写互相阻塞。

**方案（MVCC, Multi-Version Concurrency Control）**：修改数据时**不覆盖旧版本，而是产生新版本**；每个版本用两个事务 ID 描述生命周期——`xmin`（谁插入的）、`xmax`（谁删除/锁定的）。读操作拿着"快照"自行挑选可见版本，于是：

```text
传统锁模型                          MVCC 模型
┌─────────────────────┐            ┌─────────────────────┐
│ 读 ←─互斥→ 写        │            │ 读旧版本 ←─并行─→ 写新版本
│ 读 ←─互斥→ 读        │            │ 读读并行, 读写并行     │
└─────────────────────┘            └─────────────────────┘
```

**PostgreSQL 的实现特点**（与 Oracle/InnoDB 的 undo 表空间方案对比）：旧版本就放在**表堆里**，新版本追加写入同一张表；旧版本何时可物理删除由"还有没有更老的快照需要它"决定，由 VACUUM 事后回收。这带来 PG 特有的三个副产品：表膨胀、需要 VACUUM、事务 ID 需要防回卷（见 §3.3）。

两条技术路线的代价对比：PG 的**事务回滚可以立即完成**——无论事务改了多少数据，回滚只是改一下 CLOG 里的状态位（§3.2），不还原任何数据；也不存在回滚段空间耗尽的问题（Oracle 经典的 ORA-1555 "snapshot too old"）。代价则是：旧版本要靠 VACUUM 清理（§8），且查询可能需要扫过更多含死元组的数据块。

## 2. 元组结构与版本链

### 2.1 元组头（HeapTupleHeaderData）

每行数据前面有一个约 23 字节的头部，MVCC 的全部状态就在这里：

| 字段 | 位置 | 含义 |
|---|---|---|
| `t_xmin` | `include/access/htup_details.h:124` | 插入该版本的事务 ID |
| `t_xmax` | `include/access/htup_details.h:125` | 删除/锁定该版本的事务 ID（0 = 未被删） |
| `t_cid` | `include/access/htup_details.h:129` | 事务内命令 ID（区分同一事务内多条语句） |
| `t_ctid` | `include/access/htup_details.h:161` | 本条或更新版本的物理位置（TID）——**版本链指针** |
| `t_infomask` | `include/access/htup_details.h` | 提交状态提示位（hint bits）等标志 |
| `t_infomask2` | `include/access/htup_details.h:167` | 属性个数 + HOT 标志等 |

结构体定义：`typedef struct HeapTupleHeaderData`（`include/access/htup.h:21`，实际字段布局在 `htup_details.h`）。

### 2.2 提示位（hint bits）与关键 infomask 位

事务的提交/回滚状态本应查 CLOG（提交日志），但每次可见性判断都查一次太慢——首次判定后把结果**写回元组头**，之后的判断只看本地位。关键位定义（`include/access/htup_details.h`）：

| 位 | 位置 | 含义 |
|---|---|---|
| `HEAP_XMIN_COMMITTED` | :204 | 插入事务已提交 |
| `HEAP_XMIN_INVALID` | :205 | 插入事务已回滚 |
| `HEAP_XMIN_FROZEN` | :206 | = COMMITTED\|INVALID，已冻结（见 §3.3） |
| `HEAP_XMAX_COMMITTED` | :207 | 删除事务已提交 |
| `HEAP_XMAX_INVALID` | :208 | 删除事务已回滚（或只是行锁） |
| `HEAP_HOT_UPDATED` | :295 | 该元组被 HOT 更新过（t_infomask2） |
| `HEAP_ONLY_TUPLE` | :296 | HOT 链中的堆内元组（无索引指向） |

提示位的写入：`SetHintBits()` — `access/heap/heapam_visibility.c:114`。

### 2.3 版本链

```text
(事务 100 INSERT)          (事务 200 UPDATE)           (事务 300 再 UPDATE)
HeapTuple v1               HeapTuple v2                HeapTuple v3
t_xmin = 100               t_xmin = 200                t_xmin = 300
t_xmax = 200 ────────────▶ t_xmax = 300 ────────────▶ t_xmax = 0 (现行版本)
t_ctid → v2 的 TID          t_ctid → v3 的 TID          t_ctid → 自身
   [页 5 块 3]                 [页 5 块 3 或其他页]         [任意页]

一条逻辑行的多个物理版本通过 t_ctid 串成链;
索引始终指向"插入时的那个版本", 读时可能要沿链找到对快照可见的版本
(HOT 优化可以避免走链, 见 §6.5)
```

## 3. 事务 ID（XID）与 CLOG

### 3.1 XID 的分配时机：只读事务不占 XID

```text
BEGIN;                       ← 还没有 XID
SELECT ...;                  ← 仍然没有 XID (虚拟ID为准, 见下)
UPDATE t SET ...;            ← 第一次真正修改时才分配
     └─ AssignTransactionId()      access/transam/xact.c:635
          └─ GetTopTransactionId() xact.c:426 (顶层事务)
               └─ GetNewTransactionId()  access/transam/varsup.c:77
                    (从 nextXid 全局推进, 同步推进 CLOG/ MULTIXACT 等SLRU)

无 XID 的事务用 VirtualTransactionId (backendID + localXID) 标识, 不写堆
```

这是 PG 的一个重要设计：**纯 SELECT 不消耗 XID**，否则高只读负载下 XID 会飞速耗尽。

### 3.2 CLOG（提交日志）

XID 的提交/中止/进行中状态记录在 CLOG（SLRU 缓冲的位图，每事务 2 bit）：SLRU 实现在 `access/transam/clog.c`；对外查询接口 `TransactionIdDidCommit()` — `access/transam/transam.c:126`（注意：PG 18 中这组 API 已从 clog.c 移到 transam.c，`clog.c` 只剩 SLRU 本体）。可见性判定状态未知时查它，查完回写提示位（§2.2）。

每个 XID 在 CLOG 中的四种状态（`include/access/clog.h:27-30`）：

| 状态 | 值 | 含义 |
|---|---|---|
| `TRANSACTION_STATUS_IN_PROGRESS` | 0x00 | 事务进行中 |
| `TRANSACTION_STATUS_COMMITTED` | 0x01 | 已提交 |
| `TRANSACTION_STATUS_ABORTED` | 0x02 | 已回滚 |
| `TRANSACTION_STATUS_SUB_COMMITTED` | 0x03 | 子事务已提交（子事务状态另由 pg_subtrans 记录） |

CLOG 数据文件位于数据目录 **`pg_xact/`** 下（PG 10 之前叫 `pg_clog`，老资料/老书沿用旧名）。

### 3.3 XID 回卷（wraparound）与 Freeze

```text
事务 ID 只有 32 位, 约 42 亿个, 会用完 ──▶ "回卷" (老XID反而显得是未来事务)

        0 ──────────────────────────────────────────────▶ 2^32
        ▲                                                │
   FirstNormalTransactionId              FrozenTransactionId(2) / BootstrapTransactionId(1)

对策: Freeze(冻结) —— 把"足够老且已提交"的元组 xmin 清成 FrozenXID(2),
     这些元组对所有快照永久可见, 相当于"出生即已提交"

heap_prepare_freeze_tuple()   access/heap/heapam.c:7316   (VACUUM 逐元组决策)
heap_freeze_tuple()           access/heap/heapam.c:7664   (执行改写)
触发时机: autovacuum_freeze_max_age (默认2亿) 前必须对整库做 aggressive vacuum,
         否则 PG 强制停库保护 (到达 20 亿左右拒绝分配新 XID)
```

**回卷后如何比较两个 XID 的新旧**：PG 约定普通 XID 用"模减"比较——`NormalTransactionIdPrecedes(id1, id2)` 宏（`include/access/transam.h:147`）实现为：

```c
#define NormalTransactionIdPrecedes(id1, id2) \
    ((int32) ((id1) - (id2)) < 0)
```

利用 int32 有符号溢出，把"回绕距离不超过 2^31"的两个 ID 转换成正确的新旧关系——这正是"任意两个正常事务的年龄差最多 2^31"这一约束的来源。

同表的 xmax 也有类似机制（MultiXactId 回卷），多锁场景见 §6.6。

## 4. 快照（Snapshot）

### 4.1 快照结构

快照 = "某一时刻哪些 XID 已提交"的集合描述，核心结构 `SnapshotData`（`include/utils/snapshot.h:138`）：

```text
┌─ SnapshotData ─────────────────────────────────────────────┐
│ snapshot_type  : SNAPSHOT_MVCC 等 (snapshot.h:46 枚举)      │
│ xmin           : 所有 < xmin 的事务已完成, 对快照可见  (:154)│
│ xmax           : 所有 >= xmax 的事务对快照不可见       (:155)│
│ xip[]          : [xmin, xmax) 之间"仍在进行中"的 XID 列表    │
│ curcid         : 命令ID, 本事务中"本命令之前"的变更可见       │
│ (PG18 已无 satisfies 函数指针, 用 snapshot_type 分发, §5.1)  │
└────────────────────────────────────────────────────────────┘

判定规则 (对元组的 t_xmin/t_xmax 逐个套用):
   XID < xmin                → 已结束, 查提示位/CLOG 定论
   XID >= xmax               → 视为进行中, 不可见
   xmin <= XID < xmax        → 在 xip[] 里 = 进行中(不可见); 不在 = 已提交
   XID == 当前事务           → 用 curcid 区分本事务内先后
```

### 4.2 快照的采集：GetSnapshotData

```text
GetSnapshotData(snapshot)              storage/ipc/procarray.c:2175
   扫描 ProcArray (所有活跃后端共享的 PGPROC 数组):
     xmin  = 所有活跃事务中最小的 xid (并考虑已持锁/复制槽的 xmin horizon)
     xmax  = nextXid (下一个将分配的 xid)
     xip[] = 收集所有进行中的 xid
xmin 是 MVCC 的"下界锚点": 只要老快照还活着, 它的 xmin 之前的死元组就不能回收
(这正是长事务导致表膨胀的根源)
```

### 4.3 快照的获取与隔离级别

```text
GetTransactionSnapshot()               utils/time/snapmgr.c:271
   ├─ READ COMMITTED (默认, xact.c:78 DefaultXactIsoLevel):
   │     每次调用都重新 GetSnapshotData() ──▶ 每条语句看到不同结果(不可重复读)
   └─ REPEATABLE READ / SERIALIZABLE:
         IsolationUsesXactSnapshot() 分支 (snapmgr.c:315)
         事务内首次获取后作为 FirstXactSnapshot 固定复用 ──▶ 整个事务一个快照

使用点 (SELECT 主线, 详见 ../001.SQL执行流程/000 文档 §4.2):
   exec_simple_query L1161 analyze_requires_snapshot
     → PushActiveSnapshot(GetTransactionSnapshot())   snapmgr.c:680 (Pop :773)
   ExecutorStart: estate->es_snapshot = RegisterSnapshot(...)  execMain.c:245
```

### 4.4 各隔离级别下 MVCC 的工作原理

先给一个源码级的一句话总结（`include/access/xact.h:42-45` 的官方注释）：

> *"We implement three isolation levels internally. The two stronger ones use one snapshot per database transaction; the others use one snapshot per statement. Serializable uses predicate locks in addition to snapshots."*

即：SQL 标准四个级别，PG 内部只实现**三档**——`XACT_READ_UNCOMMITTED`(0) 与 `XACT_READ_COMMITTED`(1) 行为完全相同（READ UNCOMMITTED 只是别名，PG 不可能脏读，见下）；RR 和 SERIALIZABLE 用**事务级快照**；SERIALIZABLE 再叠加**谓词锁**。整套机制由两个宏驱动（`xact.h:51-52`）：

```c
#define IsolationUsesXactSnapshot() (XactIsoLevel >= XACT_REPEATABLE_READ)  /* 事务级快照? */
#define IsolationIsSerializable()   (XactIsoLevel == XACT_SERIALIZABLE)     /* 再叠加SSI?   */
```

| 异常 | READ COMMITTED | REPEATABLE READ | SERIALIZABLE |
|---|---|---|---|
| 脏读 | 不可能（MVCC 天然排除） | 不可能 | 不可能 |
| 不可重复读 | **可能**（每语句新快照） | 不可能（事务级快照） | 不可能 |
| 幻读 | 可能 | 不可能（快照含全部可见行） | 不可能（SSI 进一步防写倾斜） |
| 实现机制 | 语句级快照 | 事务级快照 | 快照 + SSI 谓词锁（`storage/lmgr/predicate.c`） |

#### 4.4.1 快照策略：一语句一快照 vs 一事务一快照

```text
READ COMMITTED                           REPEATABLE READ / SERIALIZABLE
─────────────────────                    ─────────────────────────────
BEGIN                                    BEGIN
语句1 → GetTransactionSnapshot()          语句1 → 首次获取, 注册为 FirstXactSnapshot
          每次调 GetSnapshotData()                  (snapmgr.c:315 IsolationUsesXactSnapshot 分支)
          取全新快照                     语句2 → 直接复用 FirstXactSnapshot
语句2 → 又取全新快照                      语句3 → 仍复用
语句N → ...                              COMMIT → 快照随事务释放

(RC 下同一事务内两条 SELECT 可看到不同结果 ← §4.3 时序;
 RR/SER 下永远看到事务开始时的一致性视图)
```

SERIALIZABLE 的差异仅在首次获取时换用 SSI 版本：`GetSerializableTransactionSnapshot()`（调用点 `snapmgr.c:319`，实现 `storage/lmgr/predicate.c:164`）——快照内容相同，但**注册进 SSI 的谓词锁体系**。

#### 4.4.2 READ COMMITTED：读用新快照，写做"逐行重评估"

**读**：每条语句从 `GetSnapshotData()` 拿新快照（`procarray.c:2175`），所以只能保证语句内一致。

**写**是 RC 最精妙的部分——找行用语句快照，但**改行前以最新版本重新判定 WHERE**。分歧点就在 `ldelete` 的 `TM_Updated` 分支（`executor/nodeModifyTable.c:1695-1742`，`lupdate` 同构 :2625 附近）：

```text
子计划扫描(语句快照) 命中行 R
   → heap_update/heap_delete 返回 TM_Updated (R 已被事务T改过并提交)
   → nodeModifyTable.c:1700  if (IsolationUsesXactSnapshot())
   │      → 为假 (RC): 继续 ▼
   │
   ├─ EvalPlanQualBegin()                      :1709
   ├─ table_tuple_lock(..., TUPLE_LOCK_FLAG_FIND_LAST_VERSION)
   │      :1713-1718   沿版本链找到 R 的最新版本并加行锁
   ├─ EvalPlanQual()                           :1724
   │      对最新版本重新求值 WHERE
   │      ├─ 满足 → goto ldelete 重试          :1742
   │      └─ 不满足 → 该行跳过
   └─ 为真 (RR/SER) → 直接报 40001 (见 4.4.3)
```

语义：**WHERE 条件基于"最新已提交数据"重新评估**——这是防丢失更新的关键（你不会基于过时的行值做修改），但语句间的重复读没有保证。

#### 4.4.3 REPEATABLE READ：读一致性最强，写冲突直接报错

**读**：事务级快照，不可重复读和幻读都消失。

**写**：同样走到上面的 `TM_Updated` 分支，但 `IsolationUsesXactSnapshot()` 为真——**不做 EvalPlanQual，直接报错**（`nodeModifyTable.c:1700-1703`）：

```c
if (IsolationUsesXactSnapshot())
    ereport(ERROR,
            (errcode(ERRCODE_T_R_SERIALIZATION_FAILURE),      /* SQLSTATE 40001 */
             errmsg("could not serialize access due to concurrent update")));
```

为什么 RC 重试而 RR 报错？EvalPlanQual 要"以最新版本重判"，这本质上**违反了事务级快照的一致性视图**（等于用事务开始后发生的数据影响本事务），所以 RR 宁可失败也不破坏语义。`40001` 是**可重试错误**，应用层应重试整个事务（§7.3 场景三就是这条路径的完整时序）。

同理，`ExecCheckTupleVisible()`（`nodeModifyTable.c:362`，ON CONFLICT / MERGE 等路径用）在非 RC 隔离下发现"扫到的行对事务快照不可见"时也报同样的 40001（:387-389）。

#### 4.4.4 SERIALIZABLE：RR 快照 + SSI 谓词锁

RR 仍防不住**写倾斜**（write skew）：两个事务各自读对方的写入范围、各写不相交的行，单看每个事务都满足约束，合起来破坏不变量（经典例子：值班医生表，两个事务各自检查"至少有一人在值班"然后把自己排上，结果两人都退出）。SERIALIZABLE 在 RR 快照之上叠加 **SSI（Serializable Snapshot Isolation）**：

```text
① 读操作登记谓词锁 (SIReadLock): 记录"我读过哪些页/键范围"
     实现见 storage/lmgr/predicate.c (谓词锁哈希表)
② 写操作与他人的读范围构成 rw-antidependency 边,
     SSI 在这些边上检测"危险结构" (两条连续边成环的两个先读后写事务)
③ 提交前判定: 若存在危险结构 → 中止其中一个事务 (同样报 40001)
   (不是串行执行, 而是"检测到可能不串行 → 主动失败一个")
```

代价：谓词锁内存开销、`pg_locks` 里可见的 `SIReadLock`、冲突多的负载下大量 40001 重试。收益：RR 防不住的写倾斜/读-写环被堵死。

#### 4.4.5 三档机制总结表

| 机制 | READ COMMITTED (含别名 RU) | REPEATABLE READ | SERIALIZABLE |
|---|---|---|---|
| 快照粒度 | 每语句新快照（`GetSnapshotData`） | 事务级（`FirstXactSnapshot`，`snapmgr.c:315,324`） | 同 RR + SSI 注册（`snapmgr.c:319`） |
| 读语义 | 语句内一致 | 事务内一致 | 事务内一致 |
| 写冲突处理 | 等待 → `EvalPlanQual` 逐行重评估重试（`nodeModifyTable.c:1700-1742`） | 直接报 40001（`:1700-1703`），应用重试整个事务 | 同 RR，另外 SSI 还会因 rw-conflict 主动中止 |
| 源码开关 | `IsolationUsesXactSnapshot()` = 假 | 真 | 真 + `IsolationIsSerializable()` = 真 |
| 附加开销 | 无 | 无 | 谓词锁内存与检测（`predicate.c`） |
| 防住的异常 | 脏读 | + 不可重复读、幻读 | + 写倾斜（串行化等价） |

> PG 没有"脏读"实现：`HeapTupleSatisfiesDirty`（visibility.c:743）仅供内部工具用，SQL 层无脏读；这就是 READ UNCOMMITTED 可以直接当 RC 用的原因。

### 5.2 HeapTupleSatisfiesMVCC 完整判定树

```text
HeapTupleSatisfiesMVCC(htup, snapshot, buffer)          visibility.c:960
│
├─【第一段: 插入者 t_xmin 决定"这个版本我能不能看见"】
│    hint 位说 xmin 已提交?  (HEAP_XMIN_COMMITTED, htup_details.h:204)
│    │
│    ├─[xmin 已提交]────────────────────────────────┐
│    │    │  提示位没有定论? 查 CLOG (transam.c:126)  │
│    │    │  并回写提示位 SetHintBits() :114          │
│    │    ▼                                        │
│    │  xmin < snapshot.xmin ?                     │
│    │    ├─ 否 → XidInMVCCSnapshot() (snapmgr.c:1870) 再查:
│    │    │     在 xip[] 中(进行中) → 不可见         │
│    │    │     否则 → 看作已提交 → 继续 ▼          │
│    │    └─ 是 → 继续 ▼                           │
│    │                                           │
│    ├─[xmin 已回滚 HEAP_XMIN_INVALID]              │ → 不可见
│    │                                            │
│    ├─[xmin 进行中, 且是"我自己的事务"]              │
│    │    cid == curcid? (本命令之前插入的)          │
│    │    ├─ 是 → 继续 ▼                          │
│    │    └─ 否 → 不可见 (未来命令插的)              │
│    │                                            │
│    └─[xmin 进行中, 别人的事务] ────────────────────│ → 不可见
│                                                 ▼
├─【第二段: 删除者 t_xmax 决定"它还没被删掉吧"】
│    t_xmax == 0 (没被删/锁)?
│    ├─ 是 → ★ 可见 ★
│    ├─[xmax 是我自己] cid == curcid? → 可见 : 不可见
│    ├─[xmax 已回滚 HEAP_XMAX_INVALID] → 可见
│    ├─[xmax 已提交] 对本快照可见吗? (同第一段逻辑)
│    │    → 可见 = 删除还没被我看见 → 旧版本仍可见
│    │    → 不可见 = 删除已生效 → 不可见
│    └─[xmax 进行中(别人的)] → 可见 (对方还没提交, 我看不到删除)
│
└─【返回 bool: 元组对本快照是否可见】
```

### 5.3 快照判定的三种时区示意

```text
时间轴 ─────────────────────────────────────────────────────────▶
   T1: 事务10 INSERT行X(未提交)      T3: 事务10 COMMIT
   T2: 事务20 开始, 取快照           T4: 事务20 SELECT 查X

事务20 在 T2 取的快照: xmin/xmax 覆盖 10 (10 ∈ xip[] 或 > xmax)
   T4 时事务10虽已提交, 但 10 在 T2 的快照里是"进行中"
   → 行X对事务20不可见        ← 这就是一致性读

READ COMMITTED 下每条语句重取快照, 所以 T5 再查就能看见了;
REPEATABLE READ 下沿用 T2 快照, 永远看不见 —— 直到事务结束
```

## 6. 写操作的多版本行为

### 6.1 三种写操作对元组的影响

```text
INSERT (heap_insert, heapam.c:2081;  WAL写点 XLogInsert :2248)
   新元组: xmin=当前事务, xmax=0            ← 旧表无任何变化
DELETE (heap_delete, heapam.c:2828;  WAL :3204 XLOG_HEAP_DELETE)
   目标元组: xmax=当前事务 (标记删除)        ← 行数据原地不动, 索引不删
UPDATE (heap_update, heapam.c:3321)
   旧行: xmax=当前事务; 新行: xmin=当前事务   ← 一条UPDATE = 删旧+插新(逻辑上)
   t_ctid 链接新旧版本; 所有索引新增指向新版本的条目(非HOT时)
   (物理上可能一行都没"删除", 全是追加, 这就是表膨胀的来源)
```

### 6.2 修改前的并发判定：TM_Result

写操作与读不同：不能只问"可不可见"，要问"这行被谁动过"，答案驱动后续动作。判定函数 `HeapTupleSatisfiesUpdate()`（`access/heap/heapam_visibility.c:458`），返回枚举 `TM_Result`（`include/access/tableam.h:74`）：

```text
TM_Ok             : 无冲突, 直接改
TM_Invisible      : 行对快照不可见 (不该发生 → 报错)
TM_SelfModified   : 被本事务改过 (按 cid 细分)
TM_Updated        : 被别的事务更新过 (含跨分区移动)  ┐
TM_Deleted        : 被别的事务删除过                  ├→ 等待 → 重评估
TM_BeingModified  : 正在被别的事务修改 (未提交)       ┘
```

### 6.3 行锁与等待

```text
heap_update (heapam.c:3321) / heap_delete (heapam.c:2828) 冲突分支:
   ① 元组锁: heap_acquire_tuplock()  :3627 (update) / :2988 (delete)
        LockTupleExclusive, 记录在内存锁表 (storage/lmgr/lock.c)
   ② 等待对方事务结束:
        单事务: XactLockTableWait()   调用点 heapam.c:3632 (update, XLTW_Update)
                                             heapam.c:2990 (delete, XLTW_Delete)
                 实现: storage/lmgr/lmgr.c:663
                 (事务结束锁在 xact 的 pgxactoff 上, 等待中由 deadlock.c 检测死锁)
        多事务: MultiXactIdWait()     heapam.c:2951 (delete) / :3715 附近 (update)
   ③ 等待后重读该行 → 回到 ExecUpdate/ExecDelete 重试或放弃
        (重评估由 EvalPlanQual 完成, 见 §6.4)
```

### 6.4 EvalPlanQual：冲突后的重评估

```text
扫描返回行 R (对快照可见) ──▶ heap_update 发现 R 已被事务 T 提交修改
   │
   ▼
EvalPlanQual()                    executor/execMain.c:2653
   ├─ EvalPlanQualBegin()  :2936  重置 EPQ 执行状态
   ├─ EvalPlanQualSlot()   :2781  沿版本链取"R 的最新版本"放入测试槽
   │      (沿链用 heap_hot_search_buffer heapam.c:1718 等)
   └─ 用原计划树(只读模式) 对新版本重新求值 WHERE/JOIN
        ├─ 仍满足 → ExecUpdate/ExecDelete 以新版本重试
        └─ 不满足 → 该行跳过 (窗口期内被别人改走了)

语义: READ COMMITTED 下 "WHERE 条件以最新版本重新评估",
     避免基于过时数据做修改 (丢失更新的一种防护)
```

### 6.5 HOT（Heap-Only Tuple）：绕过索引的更新

非 HOT 更新要为**每个索引**插入新条目，代价高。满足两个条件时走 HOT：

```text
HOT 判定 (heap_update 内部):
   HeapDetermineColumnsInfo()   heapam.c:4598
     条件1: 被修改的列都不在任何索引里 (汇总位图比对)
     条件2: 新版本能放进同一页 (PG 尝试同页空间, 放不下则填页触发 prune)
   满足 → 新元组打 HEAP_HOT_UPDATED / HEAP_ONLY_TUPLE 标志 (htup_details.h:295,296)

HOT 链示意:
   索引 → v1 ──(t_ctid, 同页)──▶ v2 ──▶ v3     索引只指向 v1!
   读时: 索引命中 v1 → 沿链 heap_hot_search_buffer() (heapam.c:1718)
        找到对快照可见的版本
   收益: 索引零新增条目; 且同页死元组可被页内剪枝即时回收 (§7.1)
```

### 6.6 MultiXact：多个事务"共享"一行时

行不仅会被 UPDATE/DELETE 独占锁定，还会被 `SELECT ... FOR SHARE/FOR UPDATE`、外键检查等加共享锁——多个事务同时持有时，单个 xmax 放不下，就打包成 **MultiXactId** 写进 xmax：`MultiXactIdCreate()`（`access/transam/multixact.c:479`）、`MultiXactIdExpand()`（`:532`）。判定时把 MultiXact 展开，对每个成员事务分别判断提交状态（这也是为什么 heap_update/delete 里有单独的 `MultiXactIdWait` 路径）。

## 7. 读写并发时序（把一切串起来）

### 7.1 场景一：SELECT 与 UPDATE 互不阻塞

```text
会话A (READ COMMITTED)                会话B
BEGIN; SELECT ...;  ← 快照 s1
                                      UPDATE t SET ... WHERE id=10;  ← 立即执行
                                      (B: 行上锁, 写新版本, 旧版 xmax=B的xid)
SELECT * FROM t WHERE id=10;
  扫描: HeapTupleSatisfiesMVCC
    旧版本: xmax=B(进行中) → 对快照s1仍可见 → 返回旧值
  ★ A 不等 B, 读到一致性旧值
                                      COMMIT;
SELECT * FROM t WHERE id=10;          (READ COMMITTED: 新快照, xmax已提交
  → 返回新值                            → 旧版本不可见 → 返回新值)
```

### 7.2 场景二：两个 UPDATE 抢同一行

```text
会话A                                 会话B
UPDATE t SET v=1 WHERE id=10;  ✓
                                      UPDATE t SET v=2 WHERE id=10;
                                        → HeapTupleSatisfiesUpdate 返回 TM_Updated
                                        → XactLockTableWait 等 A (heapam.c:3632)
COMMIT;
                                        → 拿到锁, EvalPlanQual 重评估
                                        → WHERE id=10 对新版本仍满足
                                        → 以最新版本重试更新 → v=2 生效
```

### 7.3 场景三：REPEATABLE READ 下的同样的竞争

```text
会话A (RR): BEGIN; SELECT;  快照固定
会话B: UPDATE id=10; COMMIT;
会话A: UPDATE id=10;
   heap_update → TM_Updated → 等B → 重评估时发现"新版本对本事务快照不可见"
   → 视为序列化冲突: ERROR: could not serialize access
   (RR 不做 EvalPlanQual 重试 —— 保证可重复读语义, 由应用重试整个事务)
```

## 8. 死元组回收

MVCC 的代价是旧版本堆积，靠两级机制回收：

```text
死元组 (dead tuple): 对所有可能还活着的快照都不可见的旧版本

┌─ 第一级: 页内剪枝 (HOT prune) ── 读写触到该页时顺带执行, 廉价
│    heap_page_prune_opt()              access/heap/pruneheap.c:193
│      └─ heap_page_prune_and_freeze()  :350   (单遍完成: 剪枝+冻结)
│           判定依据: heap_prune_satisfies_vacuum() :917
│                → HeapTupleSatisfiesVacuumHorizon() visibility.c:1205
│           执行改页: heap_page_prune_execute() :1561
│    特点: 只清"同页内 xmin/xmax 都已终结"的简单链, 不跨页
│    (PG18 亮点: pagemode 扫描时顺带剪枝并确定可见偏移, §5.1 链路)
│
└─ 第二级: VACUUM ── 后台/手动, 全表扫描, 可跨页可清索引
     heap_vacuum_rel()                   access/heap/vacuumlazy.c:615
       └─ lazy_scan_heap()               :1200
            死元组判定: HeapTupleSatisfiesVacuum()  visibility.c:1171
            (OldestXmin 由 GlobalVisState 机制提供,
             procarray.c:167 定义, 实例 :297-299)
            清理: 堆元组 → 索引死条目 → FSM 还页
     附加收益: 冻结老元组 (§3.3), 更新统计信息(analyze)
```

**可见性位图（VM）**：`access/heap/visibilitymap.c`，每页 2 bit（all-visible / all-frozen）。VACUUM 后设置；全可见页让 IndexOnlyScan 免查堆、让 VACUUM/剪枝快速跳页。

**谁在拖后腿**：长事务（老快照不释放 → OldestXmin 卡住 → 什么都不能回收）。诊断：`pg_stat_activity` 的 `backend_xid/backend_xmin`、`pg_stat_user_tables` 的 `n_dead_tup`。
