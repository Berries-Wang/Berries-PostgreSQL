# 优化器干预手段（对应 MySQL 007 篇：索引提示）

## 结论先行

**PG 没有原生的 `USE/FORCE/IGNORE INDEX`**——这是社区二十多年的刻意哲学（"hint 是把优化器的错误固化成 SQL 文本，统计变化后就过期"）。但干预手段并不缺，按"侵入性"从低到高：

| 手段 | 侵入性 | 适用 |
|---|---|---|
| `EXPLAIN (ANALYZE, BUFFERS)` 定位误判 | 无 | 一切的第一步 |
| 代价参数（random_page_cost / effective_cache_size） | 会话级，全局无害 | 硬件换代（SSD）后优化器观念没跟上 |
| `enable_*` 开关 | 会话级 | 试验/诊断"去掉某路径它会选什么" |
| `join_collapse_limit` / `geqo_threshold` | 会话级 | 多表 join 顺序失控 |
| `plan_cache_mode` | 会话级 | 预编译语句的通用计划选错 |
| **pg_hint_plan 扩展** | SQL 文本内注释 | 真的需要"逼"优化器时（生产慎用） |
| 物理手段：改索引（partial/表达式/INCLUDE）、drop 坏索引 | 持久 | 根治 |

## 原理：PG 优化器的决策链与每个干预点的位置

```text
 SQL → 解析 → 改写(prepjointree/subselect) → 生成路径(indxpath/joinpath) → 代价比较(costsize) → 最优计划
                                            ▲            ▲                ▲
    pg_hint_plan:      注释里指定索引/join顺序 ┘            │                │
    enable_*:          关掉某类路径(如 enable_seqscan=off) ─┘                │
    代价参数:           random_page_cost/effective_cache_size 改变公式输入 ───┘
    join_collapse_limit: 限制 join 重排搜索范围(from_collapse_limit 同理)
    geqo_threshold:     join 表数超过阈值(默认12)→ 换遗传算法搜索(geqo_main.c:72)

 enable_* 是【软】开关: 关掉 enable_seqscan 只是把顺序扫描代价乘 1e10,
 不是禁止——如果没有任何其他路可走, 优化器仍会用它(与 FORCE 语义差异)。
 开关定义: guc_tables.c QUERY_TUNING_METHOD 组 (enable_seqscan :803 等)
```

## SQL 示例

```sql
-- 场景: SSD 上优化器仍按机械盘观念嫌"堆随机取"贵, 不肯用索引
SET random_page_cost = 1.1;        -- 默认 4.0 是机械盘磁头寻道代价 (guc_tables.c:3894)
SET effective_cache_size = '24GB'; -- 告诉优化器 OS 缓存实际很大 (guc_tables.c:3716)
-- 生效点: cost_index 的堆页代价模型 (costsize.c:889 index_pages_fetched 用它估缓存命中)

-- 场景: 试验"不走某索引优化器会怎么选"
SET enable_indexscan = off; SET enable_bitmapscan = off;
EXPLAIN SELECT ...;  -- 看它退到哪条路, 反推原计划的代价构成
RESET ALL;

-- 场景: 12+ 表 join, 计划生成慢/顺序差
SET join_collapse_limit = 1;   -- 禁止重排, 按书写顺序 join (1=完全听话)
SET from_collapse_limit = 1;

-- 场景: 真要 hint (pg_hint_plan 扩展, 需 shared_preload_libraries)
/*+ IndexScan(t idx_a) BitmapScan(t2) Leading((t t2)) */
SELECT ...;
```

## 预编译语句的计划缓存陷阱（PG 特有）

```text
 PREPARE/扩展协议里的参数化语句, PG 前几次用 custom plan(代入实际参数估),
 第 5 次起换 generic plan(通用参数估) —— choose_custom_plan (plancache.c:1166)
 ⚠️ 若数据分布倾斜(如 90% 行都是 status=1), generic 计划可能对特定参数很糟:
 SET plan_cache_mode = force_custom_plan;  -- (guc_tables.c:5385)
```

## 与 MySQL 对照

| | MySQL | PG 18.6 |
|---|---|---|
| 索引 hint | USE/FORCE/IGNORE INDEX（原生） | 无原生；pg_hint_plan 扩展 |
| 开关 | optimizer_switch 各位 | enable_* 家族（语义是"代价×10000"而非禁止） |
| 代价参数 | 少 | random_page_cost/effective_cache_size/seq_page_cost/cpu_*_cost 全套 |
| join 顺序干预 | STRAIGHT_JOIN | join_collapse_limit / Leading()（扩展） |
| 计划缓存 | 无此问题（每句现算） | plan_cache_mode（custom vs generic） |
| 哲学 | hint 是一等公民 | 信任代价模型，hint 交给扩展生态 |
