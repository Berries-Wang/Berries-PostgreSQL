## 1. 最根本的差异：PG 没有"存储引擎层"

你 MySQL 笔记 README 的核心是「Server 层 / 存储引擎层」分界线与跨层的三个昂贵动作。**PostgreSQL 没有这一刀**：优化器直接生成完整的计划树，执行器直接驱动索引访问方法（AM）和堆存储——中间没有 handler 接口、没有"引擎返回行给 Server"这个动作。

```text
 MySQL 8.0                                  PostgreSQL 18.6
 ┌──────────────────────────┐               ┌────────────────────────────────────┐
 │ Server: 优化器 best_access_path│               │ 优化器: indxpath.c/costsize.c       │
 │          执行器迭代器树        │               │  生成【完整计划树】(含用哪个索引、     │
 └──────────┬───────────────┘               │  走位图还是索引序、谁先谁后 join)     │
            │ handler 接口 ◀── 一切优化的战场   │            │ 直接函数调用, 无接口层   │
 ┌──────────▼───────────────┐               ▼                                     │
 │ InnoDB: B+树/buffer pool/  │               │ 执行器节点树:                        │
 │ 回表(引擎内部, Server不感知) │               │  IndexScan/BitmapHeap/HashJoin...   │
 └──────────────────────────┘               │  └─ 每个节点直接调索引AM + 堆        │
                                            │  (索引定位是 AM 的事, 过滤/连接/      │
                                            │   排序全是执行器的事, 同一进程内)      │
                                            └────────────────────────────────────┘
```

**后果**：MySQL 的优化词「下推」「回表」「跨层传输」在 PG 里要重新定义。三个昂贵动作的 PG 版：

| MySQL 的昂贵动作 | PG 的对应物 | 削减手段 |
|---|---|---|
| ① Server↔引擎逐行传输+格式转换 | 不存在（无跨层）；代价变成执行器节点间的元组流 | 减少扫描量（选择性/过滤） |
| ② 二级索引→聚簇索引回表 | **索引→堆的逐行随机取**（index → TID → heap fetch），代价 = `堆页数 × random_page_cost`（costsize.c:560 cost_index） | **Index Only Scan**（001 篇）、**位图扫描**（004 篇）、HOT（008 篇） |
| ③ Server 物化（filesort/临时表） | **执行器物化节点**：Sort（同 filesort）、HashAggregate、Memoize | 索引即序（002 篇）、避免无序聚合（007 篇） |

## 3. 为什么 PG 优化器"敢"这么设计：代价模型一瞥

PG 每个计划节点都有代价公式（`optimizer/path/costsize.c`），决策=各路径代价取最小。理解这些公式，"优化器为什么这么选"就不再是玄学：

```text
 顺序扫描  cost_seqscan (costsize.c:295)
   cost ≈ 页数 × seq_page_cost(默认1.0) + 行数 × cpu_tuple_cost(0.01)

 索引扫描  cost_index (costsize.c:560)
   cost ≈ 索引页×seq + 堆页×random_page_cost(默认4.0!) + cpu
              ▲ 核心变量: 堆页数 = 匹配行在堆上的"聚集程度"走 index_pages_fetched 模型
              ▲ 缓存友好度用 effective_cache_size 估算 (costsize.c:889 注释)

 ⇒ 匹配 80% 的行: 堆页≈全表 → 索引输给顺序扫描 (你的 MySQL 008 篇场景一, PG 完全同款)
 ⇒ 匹配 0.1% 的行: 索引完胜
 ⇒ 中间地带: 位图扫描登场 (004 篇): 堆访问从"逐行随机"变"按块顺序"
```

```text
 三种扫描方式的选择空间 (行数 × 选择性 → 计划形态)

 匹配行数:  0 ──────── 少 ──────────────── 中 ──────────────── 多 ──── 全表
 计划:    IndexScan ───────────▶ BitmapHeapScan ───────────▶ SeqScan
          (逐行: 索引定位+堆取)    (先建位图再按块顺序取堆)          (顺序读)
          排序需求场景保留          ICP+MRR 的合体                   大部分行都要时最快
```

## 4. 排查工具链（对照你 MySQL 笔记的 EXPLAIN/optimizer_trace）

| 工具 | MySQL 对应 | 用法 |
|---|---|---|
| `EXPLAIN` | EXPLAIN | `EXPLAIN SELECT ...` 看计划树 |
| `EXPLAIN (ANALYZE, BUFFERS)` | EXPLAIN ANALYZE | **真执行**并报告每节点实际行数/时间/缓冲区命中（explain.c:494 ExplainOnePlan）——`rows` 估算 vs `actual rows` 的偏差是所有排查的起点 |
| `auto_explain` 扩展 | 无直接对应 | 慢查询自动记录计划 |
| `pg_stat_statements` | performance_schema | 累计 SQL 耗时/行数排行 |
| `SET enable_seqscan=off` 等试验 | optimizer_switch | 干预开关（005 篇） |

## 5. DBA 心智模型（PG 版三问）

```text
 Q1 堆访问多少?      EXPLAIN (ANALYZE, BUFFERS) 里 Buffers: read (堆页随机读)
                    → 001 覆盖索引/004 位图/008 HOT 在救这个
 Q2 有没有物化?      计划树里的 Sort / HashAggregate / (Memoize 反而是好物化)
                    → 002 索引即序 / 007 聚合策略 在救这个
 Q3 估算准不准?      rows vs actual rows 差一个数量级?
                    → 006 ANALYZE / 008 扩展统计 在救这个
```
