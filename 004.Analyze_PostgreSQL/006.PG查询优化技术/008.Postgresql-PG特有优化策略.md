# PG 特有的查询优化策略（MySQL 笔记之外的补充）

> 这些是 PG 有、MySQL（无对应/对应很弱）的优化。每条都回答同一个问题：**为什么能这么优化**。

## 1. 半连接/反连接：EXISTS 与 IN 的自动改写

```text
 WHERE EXISTS (SELECT 1 FROM o WHERE o.uid=u.id):
  planner 把子查询改写成 Semi Join —— u 有匹配即输出 u, 不去重不重复输出
  subselect.c:1452 convert_EXISTS_sublink_to_join
 WHERE uid IN (SELECT id FROM o):     同样改写 (subselect.c:1335 convert_ANY_sublink_to_join)
 WHERE NOT EXISTS (...):              Anti Join —— 无匹配才输出

 为什么快: 语义上"存在性判断"不需要物化子查询结果, 可以按 join 代价自由选
           NestLoop/Hash/Merge —— 甚至子查询里用位图扫描;
 优化器还能在 join 顺序里把"小表驱动大表"自动安排出来 (你 MySQL 手工改写 EXISTS/IN 的事, PG 自动做)
 ⚠️ NOT IN (子查询) 遇 NULL 语义陷阱(永远 UNKNOWN)且无法改写成 Anti Join —— 一律用 NOT EXISTS
```

## 2. 子查询上拉与视图内联

`SELECT * FROM (SELECT ... WHERE ...) s WHERE s.x=1` → 子查询条件与外层**合并成一个查询**再优化（`pull_up_subqueries`，optimizer/prep/prepjointree.c:1104）。原理：早一层过滤=早少一行，合成单层后 join/索引选择空间更大。派生表带 LIMIT/窗口函数时不能上拉（语义不变是底线）。

## 3. MIN/MAX 自动索引化

```sql
SELECT max(created) FROM orders;   -- orders.created 有 btree 索引
-- 计划: Result → InitPlan: Limit(1) → Index Scan Backward  (只碰一棵树的一端!)
```
原理：有序结构的极值在两端，`build_minmax_path`（optimizer/plan/planagg.c:317）把聚合改写成"反向扫 1 行"——O(树高)。无索引时才全表扫。**MIN/MAX 慢 = 忘建索引**，在 PG 里是可自检的。

## 4. HOT 更新 + fillfactor：更新不碰索引

```text
 heap_update (access/heap/heapam.c:3321) 时若:
   ① 所有索引列都没变  ② 新元组能放进同一页
 → 走 HOT: HeapTupleSetHotUpdated (heapam.c:4239)
   新版本堆内链上, 旧索引条目继续有效(同页 TID 链可见性判断)
 ⇒ 索引零写入、零膨胀、WAL 也更少; 顺带免了索引维护的随机 I/O
 fillfactor(表存储参数): 预留页内空间给 HOT (高频更新的表设 70~80)
 深入: access/heap/README.HOT (PG 源码自带的设计文档)
```

为什么重要：MySQL 聚簇索引下任何更新都会连锁维护所有二级索引；PG 非聚簇 + HOT 让"只改非索引列"的更新几乎零索引代价——高频 UPDATE 场景 PG 的结构性优势。

## 5. 部分索引：索引"小而准"

```sql
CREATE INDEX ON orders (created) WHERE status = 'pending';  -- 只索引未完成订单
```
原理：索引代价 ≈ 索引页数；planner 证明查询谓词蕴含索引谓词（predtest.c 推理）才会选用。热点查询只占数据 1% 时，索引缩小 100 倍→页全驻内存。书 §11.4.2。

## 6. 扩展统计：修相关列的估算失真

```sql
CREATE STATISTICS s_city_age (dependencies, mcv) ON city, age FROM users;
ANALYZE users;
```
原理：单列统计假设独立，`city AND age` 相关时选择性相乘错得离谱。扩展统计在 `src/backend/statistics/` 实现三种模型：函数依赖 dependencies.c（city 决定省份→选择性取 max 而非乘积）、MCV mcv.c（组合值频次）、ndistinct mvdistinct.c（组合基数）。**行数估准 → join 顺序/算法才选得对**——这是 PG 优化器一切决策的输入。

## 7. 并行查询

```text
 Gather (nodeGather.c:137) / GatherMerge (nodeGatherMerge.c:183, 保序收集)
   ├─ worker 1 ──┐
   ├─ worker 2 ──┼── 共享内存队列 ──▶ leader 汇总
   └─ worker N ──┘   worker 们分工读不同页段/分区/哈希桶
 支持: 并行顺序扫/索引扫/位图扫/Hash Join/HashAgg/排序...
 度: max_parallel_workers_per_gather (guc_tables.c:3628, 默认2)
 为什么: 单线程 CPU 瓶颈的纯扫描/聚合几乎线性加速;
 代价: 每个真 worker = 一个进程(见 005.PG架构), 小查询进程启动开销>收益
       → planner 用 parallel_setup_cost/parallel_tuple_cost 权衡
 书 §11.10
```

## 8. Memoize（PG14）：嵌套循环的"重复参数缓存"

```text
 NestLoop: 外层 1000 行, 内层按 u.dept_id 查部门 —— dept_id 只有 10 个不同值!
 普通NestLoop: 内层扫 1000 次
 Memoize:     内层结果按参数键缓存在哈希表 → 同参数第二次直接命中
              (nodeMemoize.c:697 ExecMemoize; EXPLAIN 里 Hits/Misses/Evictions)
 为什么: 参数重复率高(内层参数基数≪外层行数)时, 把 1000 次内层访问变 10 次真扫+990 次哈希命中
       —— 这就是 MySQL BKA/块缓存想解决的问题, PG 用"缓存"而非"批量排序"解法
```

## 9. 分区裁剪：三层裁剪

```text
 ① 计划期: WHERE created < '2024-01-01' → 只生成命中分区的子计划
    (partitioning/partprune.c:225 make_partition_pruneinfo)
 ② 执行初始化期: 参数在执行开始才确定(如 join 条件) → 初始化时跳过分区的初始化
 ③ 执行期: 每行才确定的参数 → 运行时逐分区判断 (executor/execPartition.c:265 ExecFindPartition)
 为什么: 分区表按键划分, 谓词能"整分区"地排除 → I/O 与内存零浪费;
        配合每个分区的独立索引(小索引=高缓存命中)
```

## 10. CTE 物化控制（PG12+）

```sql
WITH hot AS MATERIALIZED (SELECT ... )   -- 旧语义: 只算一次, 多处引用(可能全表物化)
WITH hot AS NOT MATERIALIZED (SELECT ...) -- 内联进主查询, 可上拉可加条件(默认: 只引用一次时)
```
原理：内联后优化器能看到全部条件（回到第 2 条子查询上拉）；物化则保证"只算一次"（有副作用的场景需要）。

## 11. JIT（表达式编译）

原理：长表达式逐行解释求值 → `jit_above_cost`（guc_tables.c:3961）以上时 LLVM 编译成机器码。**大扫描+复杂表达式**（分析查询）收益明显；OLTP 点查会被编译耗时反噬（设 `jit=off` 或调高阈值）。

## 12. B-tree 维护优化：去重与自底向上删除（PG13/14）

```text
 插入重复键(如 user_id,created 大量重复): _bt_dedup_pass (nbtdedup.c:58)
   —— 同键多 TID 压成一个"posting list"元组 → 索引页密度上升, 膨胀变慢
 UPDATE 造成的死索引条目: _bt_bottomupdel_pass (nbtdedup.c:307)
   —— 插入时顺手在页内删除"已死且不会再用"的旧版本条目, 不必等 vacuum 清索引
 为什么: 索引页密度 = 缓存命中率 = 一切索引访问的成本基数
```

## 13. 索引类型选型（书 §11.4.3-6）

| 类型 | 为什么快 | 适用 |
|---|---|---|
| B-tree | 有序→范围/排序/唯一 | 默认 |
| GIN | 倒排：一个键→TID 集合 | 全文检索、数组/JSONB 包含、pg_trgm 模糊匹配（`%ABC%` 的解药） |
| GiST | 泛化平衡树：按"距离/包含"分叉 | 地理位置(KNN)、范围类型 |
| BRIN | 只存每块区间的 min/max，极小 | 追加型大表（日志/时序），块内物理聚集时效率高 |
| SP-GiST | 空间分区树 | 点数据/前缀树 |
