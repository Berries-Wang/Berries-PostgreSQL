# 位图扫描（对应 MySQL 004 篇 MRR + 006 篇索引合并）

## 结论先行

MySQL 需要两个独立优化开关才能拿到的东西——**MRR（随机堆访问→顺序）** 和 **索引合并（多索引 AND/OR）**——在 PG 里是**同一个机制的两个侧面：位图扫描（Bitmap Scan）**，而且是优化器基于代价自动选择、无需任何开关：

- **Bitmap Heap Scan** ≈ MRR：先扫索引收集 TID → 位图天然按块号有序 → 堆按块顺序访问。
- **BitmapAnd / BitmapOr** ≈ 索引合并 union/intersect：多个索引各自建位图后做位运算。

## 概念：位图扫描的两阶段

```text
 阶段① Bitmap Index Scan (建图)                    阶段② Bitmap Heap Scan (取堆)
 ┌──────────────────────────┐                     ┌──────────────────────────────┐
 │ 扫索引(任意顺序):           │   TIDBitmap         │ 按【块号升序】处理位图:          │
 │  索引条件就地评估            │ ──────────────▶     │  块7 → 块13 → 块41 → ...      │
 │  匹配 → TID 置位            │  (按块号有序!)       │  每页: 一次读入, 页内顺序扫      │
 │  不匹配 → 不进位图          │                     │  recheck(见下) → 返回行        │
 └──────────────────────────┘                     └──────────────────────────────┘
 EXPLAIN:                                         EXPLAIN:
  Bitmap Index Scan on idx_x                        Bitmap Heap Scan on t
    Index Cond: ...                                    Recheck Cond: ...
                                                       Buffers: shared read=...
```

**为什么快（对应你 MySQL 004 篇的三条总结）：**

1. **随机 I/O → 顺序 I/O**：索引扫描出来 TID 乱序（索引序≠堆序），位图按 TID 聚合后**天然按块号排序**——堆访问变成从低块号到高块号的单向推进，等价于 MRR 的"按 rowid 排序回表"，但不需要 read_rnd_buffer 和额外排序（位图本身就是排序结构）。
2. **覆盖索引时无收益**——同你笔记的结论：没有堆访问环节，位图无处发力（planner 也不会选它）。
3. **页只取一次**：同一页上 100 个匹配行只触发 1 次页读取（普通 IndexScan 会为每行做一次 TID→堆，同页反复命中缓冲）。

## 原理一：exact 与 lossy——work_mem 的角色

```text
 匹配行稀疏(分布在少数页):  exact 模式: 位图记录精确 TID → 页内精确跳行, recheck 少
 匹配行太密/work_mem 太小:  lossify (nodes/tidbitmap.c:1359 tbm_lossify):
                            整页整页地"摊平"成页级标记 → 页内不能跳行
                            → 全页 recheck (nodeBitmapHeapscan.c:149)  ← EXPLAIN 里 Recheck Cond
 EXPLAIN (ANALYZE, BUFFERS) 可见: Heap Blocks: exact=1000 lossy=200
 调优: work_mem 大一点可减少 lossy (代价是每个连接各一份位图内存)
```

## 原理二：BitmapAnd / BitmapOr——PG 版"索引合并"

```sql
-- union (OR): 两列各有一个索引
EXPLAIN SELECT * FROM t WHERE a = 1 OR b = 2;
-- BitmapOr
--   ->  Bitmap Index Scan on idx_a (a=1)
--   ->  Bitmap Index Scan on idx_b (b=2)

-- intersect (AND): 两列各有一个索引
EXPLAIN SELECT * FROM t WHERE a = 1 AND b = 2;  -- 若无 (a,b) 联合索引
-- BitmapAnd
--   ->  Bitmap Index Scan on idx_a
--   ->  Bitmap Index Scan on idx_b
```

```text
 BitmapOr:  位图A | 位图B  (按位或, 天然去重)
 BitmapAnd: 位图A & 位图B  (按位与, 即 MySQL 的 intersect, 不要求两边 ROR!)
 ── MySQL 索引合并的 intersect 要求两边都是 rowid 有序扫描(ROR), 条件苛刻;
    PG 位图本来就按 TID 排序, 位与/位或都是 O(位图大小) 的整数运算, 通用得多。
 多索引各自的选择性差(一个 1% 一个 50%)时, BitmapAnd 的代价由 cost_bitmap_tree_node
 (costsize.c:1122) 逐层估计位图大小与选择性, 只有"都便宜"才会生成这个节点。
```

局限也与 MySQL 006 篇一致：**只合并单表的多个索引**（跨表靠 JOIN）；位图要花内存与建图时间，**匹配行很少时反而不如普通 IndexScan**（planner 用 `cost_bitmap_heap_scan` costsize.c:1023 与索引扫描代价比较后取舍）。

## 与 MySQL 对照

| | MySQL | PG 18.6 |
|---|---|---|
| 随机→顺序回表 | MRR（`optimizer_switch=mrr`，read_rnd_buffer 排序） | Bitmap Heap Scan（位图天然有序，无开关） |
| 多索引 AND | index merge intersect（要求 ROR） | BitmapAnd（无条件限制） |
| 多索引 OR | union / sort_union | BitmapOr（天然去重） |
| 决策 | optimizer_switch + 代价 | 纯代价比较（costsize.c:1023） |
| 溢出 | read_rnd_buffer_size | work_mem（lossify 机制） |
