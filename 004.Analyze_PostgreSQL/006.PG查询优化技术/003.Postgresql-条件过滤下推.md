# 条件过滤的下推（对应 MySQL 003 篇：ICP 索引下推）

## 结论先行

**MySQL ICP 解决的问题在 PG 里不存在**——因为 PG 没有"引擎把行交给 Server 过滤"这条边界：优化器在**生成计划时**就把条件分好类，能帮索引定位的（indexqual）直接下给索引 AM 做范围定位；不能的（filter）在执行器里、**取回堆元组之后**评估。真正等价于 ICP 收益（"不匹配的行不付堆取"）的，是 PG 的两个机制：

1. **Index Only Scan**：连 filter 都直接在索引元组上评估，堆完全不碰；
2. **Bitmap Index Scan**：索引条件在建位图阶段就消化掉，不匹配的 TID 根本进不了位图。

## 概念：PG 计划里条件的两个位置

沿用你 MySQL 003 篇的例子（联合索引 (zip_code, last_name, first_name)）：

```sql
SELECT * FROM people
WHERE zip_code = '95054'
  AND last_name LIKE '%etrunia%'
  AND address LIKE '%Main Street%';
```

```text
 PG 的 IndexScan 节点内部 (EXPLAIN VERBOSE 可见两个条件列表)
 ┌────────────────────────────────────────────────────────────────────┐
 │ Index Scan using idx_people on people                               │
 │   Index Cond: zip_code = '95054'::text        ← indexqual: 交给索引   │
 │                                                 AM 定位扫描区间        │
 │   Filter: last_name ~~ '%etrunia%' AND        ← filter(qpqual):      │
 │             address ~~ '%Main Street%'           取回堆元组【之后】     │
 │                                                  由执行器评估           │
 └────────────────────────────────────────────────────────────────────┘
 关键差别(MySQL 无 ICP 时): InnoDB 回表后才轮到 Server 过滤 → 白回表;
 PG: filter 白付的只是"这一次堆取", 不存在"跨层传输"的二次浪费;
     且 planner 会尽量把 zip+last_name 能用的部分都塞进 Index Cond
```

**那 ICP 的收益 PG 怎么拿？看下面两种节点。**

## 原理一：Index Only Scan 把 filter 也"下"到索引上

```text
 SELECT zip_code, last_name FROM people WHERE zip_code='95054' AND last_name LIKE '%etrunia%';
 建索引 (zip_code, last_name) → 全部条件+查询列都被索引覆盖:

 Index Only Scan:
   索引元组(在缓冲里) ──▶ 就地评估 LIKE '%etrunia%'   ← filter 在索引上跑!
        │ 不匹配 → 下一条索引元组 (零堆访问, 零浪费)
        └ 匹配 → VM 全可见? 直接返回 : 退化取堆
 执行节点: executor/nodeIndexonlyscan.c:62 IndexOnlyNext
```

这就是 MySQL ICP 的完全体：**过滤发生在堆访问之前、发生在索引数据本身上**——只是 PG 不叫"下推"，因为它本来就"在下面"（没有上层）。

## 原理二：Bitmap Index Scan 建图时过滤（详见 004 篇）

```text
 Bitmap Heap Scan:
   ① Bitmap Index Scan: 扫索引, 每条索引元组评估可下推条件
        匹配 → 位图对应 TID 置 1; 不匹配 → 不进位图
   ② Bitmap Heap Scan: 按块号顺序取堆页 → 页内逐行 → recheck 后返回
 不匹配行: 连堆页都不用多取(页级粒度), 更不会返回给上层
```

## 与 MySQL ICP 逐项对照

| | MySQL ICP | PG |
|---|---|---|
| 问题根源 | Server/引擎分层，WHERE 默认在 Server | 无分层；条件在计划生成时分配 |
| 条件何时评估 | 引擎扫索引时（`row_search_idx_cond_check`） | indexqual→AM 定位时；filter→执行器取堆后 |
| "不匹配不回表" | ICP_MATCH/NO_MATCH 分支 | **Index Only Scan**（连堆都不碰）/ **Bitmap 建图过滤** |
| 开关 | `optimizer_switch=index_condition_pushdown` | 无开关（恒定行为）；`enable_indexonlyscan/enable_bitmapscan` 可试验 |
| EXPLAIN 标志 | `Using index condition` | 节点名本身（Index Only Scan / Bitmap Heap Scan）+ Index Cond / Filter 两行 |
