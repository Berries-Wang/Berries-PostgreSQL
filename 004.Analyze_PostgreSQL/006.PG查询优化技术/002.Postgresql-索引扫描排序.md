# 用索引扫描来排序（对应 MySQL 002 篇：索引扫描排序）

## 结论先行

- **PG 完全同概念**：B-tree 索引的键序就是数据序，优化器若发现 ORDER BY 恰是某索引键序的前缀，直接出 `Index Scan`，计划树里**不出现 Sort 节点**（MySQL 的 `Using filesort` 对应 PG 的 Sort 节点）。
- PG 在此之上多两件 MySQL 没有的武器：**Incremental Sort**（前缀有序时只补排剩余部分）和 **Top-N heapsort**（ORDER BY+LIMIT 时只维护 N 行的堆）。
- 反向扫描 `Backward Index Scan` 两者都有；PG 还可以**建 DESC / NULLS FIRST 索引**精确匹配排序需求。

## 概念：pathkey——优化器怎么知道"索引即序"

```text
 索引 idx(a,b) 的扫描路径天然携带排序性质: (a,b) 升序
 优化器把每个扫描路径的"输出序"记成 pathkey 列表
   ORDER BY a, b 的需求也记成 pathkey 列表
   pathkeys_contained_in(需求, 路径能力) == 0  →  该路径满足排序, 不用 Sort
   (optimizer/util/pathkeys.c:343 pathkeys_contained_in)

 满足: WHERE a=1 ORDER BY b          → (a=1) 固定, 输出按 b 有序 ✓
 满足: ORDER BY a                    → 索引序前缀 ✓
 满足: ORDER BY a DESC               → btree 支持反向扫描 ✓
 不满足: WHERE b=1 ORDER BY a        → a 不连续(最左前缀), 必须 Sort
 不满足: ORDER BY a, c               → c 不在索引里
```

## SQL 示例（沿用你 MySQL 002 篇的 buy_log）

```sql
CREATE TABLE buy_log(id bigint GENERATED ALWAYS AS IDENTITY, user_id int, buy_date date);
CREATE INDEX idx_uid_date ON buy_log (user_id, buy_date);

-- ① 索引即序 + 反向扫描:
EXPLAIN SELECT * FROM buy_log WHERE user_id = 1 ORDER BY buy_date DESC LIMIT 3;
-- Index Scan using idx_uid_date  (无 Sort 节点; 倒序由 btree 反扫完成)
-- 对比 MySQL 的 "Backward index scan; Using index"

-- ② 强制破坏序 → 出现 Sort (对应 MySQL 的 Using filesort):
SET enable_indexscan = off;  -- 试验手段, 见 005 篇
EXPLAIN SELECT * FROM buy_log WHERE user_id = 1 ORDER BY buy_date DESC LIMIT 3;
-- Seq Scan ... Sort (实际中用 force 的等价物是 drop 掉 idx_uid_date)

-- ③ ORDER BY + LIMIT 无索引时: Top-N heapsort (只维护 3 行的小顶堆):
EXPLAIN SELECT * FROM buy_log ORDER BY buy_date DESC LIMIT 3;
-- Sort (top-N heapsort)  ← 不再全量排序!

-- ④ 前缀有序 → Incremental Sort:
CREATE INDEX idx_a ON buy_log (user_id);
EXPLAIN SELECT * FROM buy_log ORDER BY user_id, buy_date LIMIT 100;
-- Incremental Sort: user_id 分组内补排 buy_date, 不必全量 Sort
```

## 为什么能这么优化（原理）

### 原理一：排序消失 = 物化消失（跨过 MySQL 的 filesort 成本台阶）

```text
 全量 Sort:  所有匹配行取齐 → 排序内存(或落盘外排, O(N logN)) → 才能吐第一行
 索引序扫描: 索引定位 → 直接吐第一行, 流式输出; LIMIT N 时取 N 行即停
             ✔ 无排序内存  ✔ 首行延迟低  ✔ 行数少时 I/O 也少
```

### 原理二：Top-N heapsort（PG 特有）

```text
 Sort 节点初始化时若上层是 Limit: nodeSort.c:124 tuplesort_set_bound(bound=N)
 → 排序器只保留当前最小的 N 行(top-N heapsort, tuplesort.c:2550 的计划名):
    内存 O(N) 而非 O(全部匹配行), 100 万行取前 3 也只花 3 行的内存
```

### 原理三：Incremental Sort（PG13+）

```text
 输入已按 user_id 有序(索引/上一节点), ORDER BY user_id, buy_date:
   不用全量排序, 只在"每个 user_id 组"内对 buy_date 补排:
   [1,(3,1,2)] [2,(2,5)] ... 组与组之间天然有序
 cost: cost_incremental_sort (costsize.c:2000); 执行: ExecIncrementalSort (nodeIncrementalSort.c:495)
 适用: 排序键前缀被索引满足, 且组数多(每组小)时收益最大
```

## 什么时候"索引即序"会失效（与 MySQL 002 篇同款）

1. 最左前缀被破坏（`WHERE b=1 ORDER BY a`）；
2. 排序列混合方向且索引方向不匹配（可建 `(a ASC, b DESC)` 表达方向的索引解决——PG 支持每列独立指定 ASC/DESC/NULLS FIRST/LAST）；
3. collation 不匹配：非 C collation 的 text 列，`ORDER BY col` 的序与索引序一致（同 opfamily）没问题，但**模式匹配查询**要 `text_pattern_ops`（见 006 篇）。

## 源码锚点

| 环节 | 位置 |
|---|---|
| "索引序满足 ORDER BY"判定 | `pathkeys_contained_in` optimizer/util/pathkeys.c:343（indxpath.c 生成索引路径时带上 pathkeys） |
| btree 正/反向扫描 | executor/nodeIndexscan.c:80 `IndexNext`（方向由扫描键 `ScanKey` 的 strategy 决定） |
| Top-N | nodeSort.c:124 `tuplesort_set_bound`；计划名 "top-N heapsort" utils/sort/tuplesort.c:2550 |
| Incremental Sort | `cost_incremental_sort` costsize.c:2000；`ExecIncrementalSort` nodeIncrementalSort.c:495 |
| Sort 代价 | `cost_sort` costsize.c:2144 |

## 与 MySQL 对照

| | MySQL 8.0 | PG 18.6 |
|---|---|---|
| 判定函数 | `test_if_order_by_key` / `test_if_cheaper_ordering` | pathkey 机制（pathkeys.c:343） |
| filesort 对应 | filesort.cc | Sort 节点 + tuplesort（内存/外排同一套） |
| 反向扫描 | `Backward index scan` | Index Scan Backward（btree 反扫） |
| DESC 索引 | 支持 | 支持（还可 NULLS FIRST/LAST） |
| 前缀有序补排 | 无 | **Incremental Sort** |
| LIMIT 截断优化 | 有限 | **Top-N heapsort** |
