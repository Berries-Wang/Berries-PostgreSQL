# PG 查询优化器处理流程（PostgreSQL 18.6）

> 主调用链（全部行号已在 18.6 源码核实）：
> `planner()` → `standard_planner()` → `subquery_planner()` → `grouping_planner()` → `query_planner()` → `make_one_rel()` → ... → `create_plan()` → `set_plan_references()`

```text
 planner                     planner.c:300   入口, planner_hook 扩展点
 └─ standard_planner         planner.c:316   建 PlannerGlobal, 并行安全评估(max_parallel_hazard)
    └─ subquery_planner      planner.c:664   每层 Query 一个 PlannerInfo ★预处理主战场
       └─ grouping_planner   planner.c:1567  分组/窗口/排序/LIMIT 的上层规划
          └─ query_planner   planmain.c:54   扫描+连接 (scan/join) 部分规划
             └─ make_one_rel allpaths.c:175  RelOptInfo 尺寸→路径→连接搜索
       (返回后) create_plan  createplan.c:337 Path→Plan
       (返回后) set_plan_references setrefs.c:288  最终化
```

---

## 阶段一：预处理 / 逻辑优化（subquery_planner，planner.c:664）

目标：**把 Query 变形成等价但"更平坦、更好优化"的形状**。这一步不涉及代价，纯规则驱动（rewrite）。以下按源码执行顺序（行号为调用点，均在 planner.c）：

### 1.1 结构上拉（把子查询拍平）

| 步骤 | 行号 | 实现 | 干什么 / 为什么 |
|---|---|---|---|
| `SS_process_ctes` | :732 | subselect.c:882 | WITH 列表分类：只引用一次且无副作用 → 内联成子查询 RTE；否则规划成 InitPlan/SubPlan |
| `transform_MERGE_to_join` | :737 | prepjointree.c:185 | MERGE 命令的 jointree 变换 |
| `replace_empty_jointree` | :743 | prepjointree.c:412 | `SELECT 1`（无 FROM）补一个哑 RTE_RESULT，后续统一处理 |
| `pull_up_sublinks` | :752 | prepjointree.c:470 | **ANY/EXISTS 子链接上拉为 Semi/Anti Join**（真正转换在 subselect.c:1335 `convert_ANY_sublink_to_join` / :1452 `convert_EXISTS_sublink_to_join`）。上拉后子查询进入连接顺序搜索空间，可被动态规划统一调度 |
| `preprocess_function_rtes` | :760 | prepjointree.c:916 | 函数 RTE 常量简化 + SQL 内联（`inline_set_returning_function`, clauses.c:5094） |
| `expand_virtual_generated_columns` | :768 | prepjointree.c:971 | 虚拟生成列展开（PG18 新特性） |
| `pull_up_subqueries` | :774 | prepjointree.c:1104 | **子查询上拉合并**：`SELECT * FROM (SELECT..) s` 拍平成单层。早一层过滤 = 早少一行，join/索引选择空间立刻变大 |
| `flatten_simple_union_all` | :783 | prepjointree.c:3004 | 简单 UNION ALL 展平为 AppendRel，统一走 appendrel 机制 |

### 1.2 表达式规范化（preprocess_expression，planner.c:1292）

对 targetList（:918）、withCheckOptions、returningList、**jointree 的 WHERE**（:938 `preprocess_qual_conditions`，注意 18 版已从 prepqual.c 迁到 planner.c:1394）、HAVING（:940）、LIMIT/OFFSET（:954-957）、各 RTE 内容（:1002-1071）逐个跑：

- `eval_const_expressions`（clauses.c:2279，调用点 planner.c:1338）——常量折叠、`1=1` 化简、函数简化
- `canonicalize_qual`（prepqual.c:293，调用点 :1345）——布尔条件转隐式 AND 规范形
- `SS_process_sublinks`（subselect.c:2028，调用点 :1365）——剩余 SubLink → SubPlan/InitPlan 节点
- `convert_saop_to_hashed_saop`（clauses.c:2312，调用点 :1360）——PG18 新： ScalarArrayOpExpr（`IN` 常量数组）转哈希加速形态

### 1.3 分组/聚合前处理

- `find_having_conflicts` — planner.c:1099（定义 :1450）：识别不能下推的 HAVING（PG18 新，配合 RTE_GROUP 机制）
- `flatten_group_exprs` — planner.c:1116：GROUP BY 引用回填为底层分组表达式（PG18 GROUP BY 新机制）
- `expand_grouping_sets` — planner.c:1134：GROUPING SETS 展平
- **HAVING→WHERE 迁移** — planner.c:1187-1236：无聚合/易变函数的 HAVING 条件移入（或复制到）WHERE。过滤越早做，行数越早变少——教科书级谓词下推

### 1.4 连接消除（semantic optimization，利用完整性约束）

- `reduce_outer_joins` — planner.c:1244（实现 prepjointree.c:3123）：可证明内侧行总存在/不影响结果时，**LEFT JOIN 降级为 INNER JOIN**（inner join 的约束条件才能自由移动）
- `remove_useless_result_rtes` — planner.c:1253（实现 prepjointree.c:3617）：删 RTE_RESULT、合并单子 FromExpr

> 注：`remove_useless_joins`（消除无用的 left join，analyzejoins.c:110）与 `reduce_unique_semijoins`（analyzejoins.c:1044）在 PG18 已**不在** subquery_planner 里，移到了 `query_planner()` 内部（planmain.c:228/234），因为它们依赖 RelOptInfo 尺寸信息。PG16 起也不再有 `inheritance_planner`，继承表 DML 统一走 appendrel 扩张。

之后 `grouping_planner()`（planner.c:1258 调用）接管；收尾在 :1264-1280：`SS_identify_outer_params` → `SS_charge_for_initplans` → `set_cheapest(final_rel)` 选出最终最优路径。

## 阶段二：物理优化 / 路径搜索

### 2.2 query_planner（planmain.c:54）—— scan/join 核心

```text
 setup_simple_rel_arrays        planmain.c:85    按 rangetable 建 RelOptInfo 索引数组(relnode.c:94)
 add_base_rels_to_query         planmain.c:170   jointree 每个 RTE → build_simple_rel(relnode.c:192)
 build_base_rel_tlists          planmain.c:185   把 tlist/HAVING 里的 Var 分发到各 baserel
 find_placeholders_in_jointree  planmain.c:187
 find_lateral_references        planmain.c:189   LATERAL 依赖收集
 deconstruct_jointree           planmain.c:191   ★拆 jointree: initsplan.c:1135
                                                   每条 qual → distribute_qual_to_rels(initsplan.c:2596)
                                                   单rel条件→baserestrictinfo; 连接条件→joininfo/等价类

```

**等价类（EquivalenceClass）是 PG 优化器的中枢概念**：`a.id = b.id` 这一条件会把 `a.id、b.id` 收进同一个等价类（`process_equivalence`，equivclass.c:179），此后 `ORDER BY a.id` 的有序性可自动传播到按 `b.id` 排序的路径——这就是为什么 PG 的 MergeJoin/索引选择"看起来什么都知道"。

### 2.4 连接顺序搜索（动态规划）

`standard_join_search`（allpaths.c:3461）经典两层循环：

```text
 level 1: {A} {B} {C} {D}            ← 初始 rels, 各自带 pathlist
 level 2: {AB} {AC} ... {CD}         ← join_search_one_level(joinrels.c:73)
 level 3: {ABC} {ABD} ...            ←   由 level2×level1 组合
 level 4: {ABCD}                     ←   最终大表, set_cheapest 得全局最优
```

- 每层由 `join_search_one_level()`（joinrels.c:73）推进：91-138 行做 level-1 × level-1 侧配对；148-198 行做 bushy 计划（两个多表连接结果再连接，避免"深左树"缺陷）；219-256 行兜底生成无连接条件的笛卡尔积
- `make_join_rel()`（joinrels.c:696）：`join_is_legal`（:350）检查连接合法性（外连接顺序约束）→ `build_join_rel`（relnode.c:665）建/复用连接 RelOptInfo → `add_paths_to_joinrel` 生成物理路径
- **表太多时（≥ geqo_threshold=12，guc_tables.c:2224）**切换 GEQO 遗传算法（geqo_main.c:72）：编码连接顺序为"基因"，杂交变异迭代。质量略逊 DP 但不炸 CPU；`geqo_eval`（geqo_eval.c:57）里仍复用 `make_join_rel`，路径生成代码与 DP 完全一致

### 2.5 物理连接路径（add_paths_to_joinrel，joinpath.c:124）

对每一对 (outer, inner) 生成三族路径，全部过 `add_path` 竞争：

| 方法 | 生成函数 | 何时最优 |
|---|---|---|
| NestLoop | `match_unsorted_outer` joinpath.c:1812 | 外层小、内层有索引（参数化路径）或可物化重扫 |
| MergeJoin | `sort_inner_and_outer` joinpath.c:1356 | 两侧需显式排序；一侧已有序可免排（`generate_mergejoin_paths` :1563 枚举 mergeclause 子集） |
| HashJoin | `hash_inner_and_outer` joinpath.c:2220 | 中大表等值连接，内表建哈希表一遍扫外表 |

提交包装：`try_nestloop_path`（:831）/ `try_mergejoin_path`（:1029）/ `try_hashjoin_path`（:1222）。

**代价估算**两段式（先 initial 粗筛、再 final 精算，避免为被淘汰路径浪费精算）：`initial/final_cost_nestloop`（costsize.c:3267/3349）、`initial/final_cost_mergejoin`（:3552/:3837）、`initial/final_cost_hashjoin`（:4160/:4275）。扫描/排序：`cost_seqscan`（:295）、`cost_index`（:560）、`cost_bitmap_heap_scan`（:1023）、`cost_sort`（:2144）、`cost_agg`（:2682）。

### 2.6 上层算子路径（grouping_planner 后半）

`query_planner` 返回 scan/join 结果后（planner.c:1787），按查询语义逐层"包装"上层 Path——每层都枚举多种实现竞争：

```text
 create_grouping_paths  planner.c:3913 (调用:1932)  聚合: HashAgg vs Sort+GroupAgg
                                                        分组集: Rollup→多阶段聚合
 create_window_paths   planner.c:4666 (调用:1950)  窗口: 排序复用/增排序
 create_distinct_paths planner.c:4923 (调用:1970)  DISTINCT: Hash vs Sort vs 直接利用下层有序
 create_ordered_paths  planner.c:5441 (调用:1985)  ORDER BY: 全排序 vs 下层已有序直通
                                                        LIMIT 场景做有界排序(少扫行)
```

最后（planner.c:2001-2264）逐个 Path 补 `LockRows`（:2040）/`Limit`（:2050）/`ModifyTable`（:2243-2259，INSERT/UPDATE/DELETE/MERGE），`add_path` 进 `UPPERREL_FINAL`（:2263），由 subquery_planner:1280 的 `set_cheapest` 定胜者。

## 阶段三：计划生成与最终化

### 3.1 create_plan（createplan.c:337）

把胜出的 Path 树递归翻译成 Plan 树（`create_plan_recurse` :388，按 pathtype 分发）：

```text
 create_plan_recurse
 ├─ create_scan_plan        createplan.c:559    扫描节点: 收集 baserestrictinfo+参数化条件
 │   ├─ create_seqscan_plan      :2910
 │   ├─ create_indexscan_plan    :2999         索引条件落位 fix_indexqual_references(:5121)
 │   └─ (bitmap/tid/... 同族工厂)
 ├─ create_join_plan        createplan.c:1081   连接节点
 │   ├─ create_nestloop_plan     :4341          参数化内层: replace_nestloop_params(:5036)
 │   ├─ create_mergejoin_plan    :4493
 │   └─ create_hashjoin_plan     :4847
 ├─ create_sort_plan        createplan.c:2177   显式排序
 └─ (Agg/WindowAgg/Limit/... 上层节点工厂)
```

关键转换：RestrictInfo 包装剥离（`extract_actual_clauses`，restrictinfo.c:485）、条件排序（`order_qual_clauses` :5420）、伪常量门控（`get_gating_quals` :1002）、tlist 生成（`build_path_tlist` :825）。

### 3.2 set_plan_references（setrefs.c:288）—— 最终化扫尾

- 各层子查询 rangetable 拍平到 `glob->finalrtable`，Var 的 RT 索引全部重排
- 上层节点的 Var 改为指向子计划的输出列（EXEC 参数编号化）
- `PARAM_MULTIEXPR`→`PARAM_EXEC`、AlternativeSubPlan 消解、删除无用 SubqueryScan/Append
- 收集依赖（relationOids/invalItems）供计划缓存失效判断

**没有这一步，执行器拿到的 Plan 里 Var 还指着优化器的中间编号，根本跑不起来。**

## 一次查询的完整时间线（把三阶段串起来）

```text
 SELECT u.name, count(o.id)
 FROM users u JOIN orders o ON o.uid = u.id
 WHERE u.city = 'BJ' AND o.created > '2026-01-01'
 GROUP BY u.name HAVING count(o.id) > 10
 ORDER BY 2 DESC LIMIT 5;

 ① 预处理: 无子链接/子查询可拉; WHERE/HAVING 常量折叠; HAVING 含聚合→不下推
 ② query_planner: users, orders 各建 RelOptInfo; o.uid=u.id 进等价类;
    u.city='BJ' → baserestrictinfo(估计行数= reltuples*选择性)
 ③ make_one_rel: users→Seq+Index(city); orders→Seq+Index(created,uid)
    DP: level2 唯一组合 {users×orders}: NestLoop(idx uid)/HashJoin/MergeJoin 三族竞争
    → 假设 HashJoin 胜出(两表都不小)
 ④ 上层: create_grouping_paths → Sort(按 name)+GroupAgg vs HashAgg 竞争
    create_ordered_paths: ORDER BY count DESC → 需要排序(或 GroupAgg 借排序列)
    LIMIT 5 → 有界排序, 上界传入 cost_sort
 ⑤ create_plan: Path树→Plan树; setrefs 修正变量引用
 ⑥ 执行器拿到: Limit(5) → Sort → GroupAggregate → Hash Join → (SeqScan, SeqScan)
```
