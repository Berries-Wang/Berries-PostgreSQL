# PG 的等值范围行数估算：有没有 MySQL `eq_range_index_dive_limit` 的对应物？

> 基于 PostgreSQL 18.6 源码。相关源码在 `src/backend/utils/adt/selfuncs.c`（选择性估算）与 `src/backend/optimizer/util/clauses.c`。

## 0. 先回顾 MySQL 的机制是什么

```text
 MySQL 对 IN (v1, v2, ..., vN) / 多个等值条件 (同一索引上的 "equality ranges") 的行数估算有两条路:

 ① index dive (索引下潜)                     —— 准确, 但每个 range 要真探测 B 树
     handler ha_innobase::records_in_range(): 对每个值下潜到 B 树边界页, 数页级记录
 ② index statistics (索引统计平均值)          —— 便宜, 但只是 "平均每键多少行"
     来自持久化统计(innodb_index_stats)的 records_per_key

 eq_range_index_dive_limit (默认 200, 设 0 = 永远下潜):
     等值范围数 ≤ limit  → 逐个 dive (准)
     等值范围数 > limit  → 放弃 dive, 改用统计平均值 (快但粗)
 本质 = "精确估算的次数预算": 估算开销与 IN 元素个数成正比, 超预算就降级精度
```

## 1. 直接结论

**PG 没有对应物，而且不需要——因为 PG 优化器在计划期基本不做"索引探测"，行数估算全部来自 ANALYZE 预先算好的统计信息（pg_statistic 的 MCV + 直方图），查内存即可，单个值的估算代价近乎为零，自然不存在"估算次数超预算就降级"的开关。**

- 全源码 grep `eq_range` / index dive：零匹配（PG 无此概念）
- PG 估算 `col = v` 一次 = 在 MCV 数组（≤ statistics_target 个值）里二分查找 + 未命中时直方图插值，**零 I/O**；MySQL 一次 dive = 真 B 树页下潜，**有 I/O**。代价结构不同，取舍点就不存在
- PG 唯一一处在计划期真的"下潜索引"的地方：`get_actual_variable_range`（selfuncs.c:6606），见 §3.5

## 2. PG 对 IN 列表的估算路径（与 MySQL 对照）

```text
 ───────────────────────── MySQL ────────────────────────
 IN (v1..vN) ──▶ range optimizer
                  ├─ N ≤ eq_range_index_dive_limit(200): 每个 vi 下潜 B 树 ★准★慢
                  └─ N > limit: 用索引统计平均行数       ★粗★快

 ───────────────────────── PostgreSQL 18.6 ──────────────
 col = ANY(ARRAY[v1..vN])  (语法糖 IN, 是一个 ScalarArrayOpExpr)
   │
   ▼
 scalararraysel()                    selfuncs.c:1825
   ├─ 数组是 Const → deconstruct_array 拆出全部元素 (selfuncs.c:1948)
   ├─ for 循环【逐元素、无上限】(selfuncs.c:1969-2010):
   │     每个元素构造 "col = vi" 调 eqsel
   │        └─ var_eq_const()         selfuncs.c:303   (PG17 重构)
   │             ├─ vi 命中 MCV → 直接用观测频率        ★准★零I/O
   │             └─ 未命中 MCV → 直方图桶内均匀假设      ★近似★零I/O
   └─ 合并: useOr 时按独立概率 s1 = s1+s2-s1*s2;
            等值时另算不相交和 s1disjoint = Σs2 (元素互异更合理),
            落在 [0,1] 内就采纳 disjoint (selfuncs.c:2012-2015)
 注意: 元素个数没有上限, 估算成本 = N × (二分查找), 不会触发任何降级开关
```

**一句话对比**：MySQL 限制"精确估算的次数"；PG 每次估算本来就便宜，限制的是"统计本身记多细"（见 §3.2）。

## 3. PG 中同性质（精度 vs 开销取舍）的机制清单

虽然没有同名 GUC，但"给估算精度设预算"的思想在 PG 有五个落点：

### 3.1 IN 元素估算：无上限，但有"合并策略"兜底
`scalararraysel`（selfuncs.c:1825）逐元素估算，N 个元素就做 N 次。坑：重复元素多时 disjoint 和会溢出 1.0，被拒绝后回退独立假设（:2012-2015），可能**高估**行数。

### 3.2 精度天花板：statistics_target（★最接近的对应物★）

```text
 default_statistics_target = 100   guc_tables.c:2188 (默认值:100, 上限 MAX_STATISTICS_TARGET=10000, vacuum.h:324)
 每列:  ALTER TABLE t ALTER COLUMN c SET STATISTICS 1000;

 它决定 (commands/analyze.c):
   MCV(最常用值) 个数 ≤ target    analyze.c:2082  num_mcv = attstattarget
                                    实际个数再由 analyze_mcv_list(:2332) 按显著性裁剪
   直方图桶数    ≈ target        analyze.c:2744  num_hist = ndistinct - num_mcv (≤ target+1)
   ANALYZE 目标采样行数 = 300 × target (analyze.c:1940, stats->minrows; 两阶段采样下实际扫描可略多)
```

**这是 PG 版的"eq_range_index_dive_limit 调节"**：MySQL 调大 limit = 允许更多次精确下潜；PG 调大 target = 让每个值的估算更可能命中 MCV、直方图更细。区别：PG 的代价付在 ANALYZE 时（离线），MySQL 付在每次查询计划期（在线）——所以 PG 敢放到 10000，MySQL 的 dive limit 通常不敢设 0。

### 3.3 无统计时的硬编码兜底（类比"index statistics 平均值"的降级方向）

```c
/* src/include/utils/selfuncs.h:34 */
#define DEFAULT_EQ_SEL    0.005      /* col = v 无统计时: 假设 0.5% 行匹配 */
#define DEFAULT_INEQ_SEL  0.3333333  /* col > v 无统计时: 假设 1/3 */
```

触发条件是"统计缺失"（从没 ANALYZE / 列不在采样里），而不是"范围数超限"。`var_eq_const`（selfuncs.c:303）在 MCV 未命中且无直方图时也用它。**200 行的表没 ANALYZE 过，`WHERE k=1` 会被估成 1 行**——PG 估算离谱时第一件事查 `pg_stats` 是否有数据。

### 3.4 执行侧阈值：`MIN_ARRAY_SIZE_FOR_HASHED_SAOP = 9`（PG18 新）

```c
/* src/backend/optimizer/util/clauses.c:2294 */
#define MIN_ARRAY_SIZE_FOR_HASHED_SAOP 9
```

`convert_saop_to_hashed_saop`（clauses.c:2312，预处理阶段被 planner.c:1360 调用）：IN 数组 **≥ 9 个常量元素**且操作符可哈希时，执行器从"逐元素线性比较"切换为"建哈希表查找"（NOT IN 走 negator，:2368-2394）。**同为"按元素个数切换策略"的阈值**，只是管的是执行方式不是估算精度——是 `eq_range_index_dive_limit` 的执行层镜像。

### 3.5 PG 唯一的计划期"索引下潜"：`get_actual_variable_range`

```text
 估算 col > $1 时用直方图二分 (ineq_histogram_selectivity, selfuncs.c:1050; 二分主体 :1080 起)
   二分探到 第一个/最后一个 直方图 bin (比较值在统计边界之外, 说明 ANALYZE 可能已过期):
     get_actual_variable_range()   selfuncs.c:6606
       └─ 找一个以该列开头、非部分的 btree 索引
          └─ get_actual_variable_endpoint: 用 index-only scan 机制真下潜一次,
             取当前真实 min/max 替换直方图端点   (selfuncs.c:1093-1143)
 目的: 修正 "自上次 ANALYZE 后边界已漂移" 的失真 (单调递增列最典型: created > now()-1h)
 全 PG 计划期仅此一处真的打开索引做估算, 且只探两端, 不数行数
```

这正是 MySQL index dive 思想在 PG 的"微量存在"——但 PG 把它严格限定在"直方图端点修正"这一个场景，因为 PG 的哲学是：**估算靠统计快照，而不是计划期实时探测**。

### 3.6 顺带：PG 里"质量 vs 规划开销"的著名阈值在别处
连接顺序搜索：表数 < `geqo_threshold`(默认 12) 用动态规划（准、慢），≥ 12 切遗传算法 GEQO（粗、快）——allpaths.c:3424。和 eq_range_index_dive_limit 是同一个设计模式："**超过预算就换便宜的近似**"，只是管的对象不同（连接顺序 vs 行数估算）。

## 4. 实践对照表

| MySQL 动作 | PG 对应动作 |
|---|---|
| `SET GLOBAL eq_range_index_dive_limit = 0`（永远下潜，规划变慢） | `ALTER TABLE t ALTER COLUMN c SET STATISTICS 1000; ANALYZE t;`（精度付在 ANALYZE，计划期仍快） |
| 持久化索引统计 `innodb_stats_persistent_sample_pages` | `default_statistics_target` / ANALYZE 采样 300×target 行 |
| dive 用的 `records_in_range` | 无（PG 计划期不数行数，仅有端点修正 §3.5） |
| 统计过期 `ANALYZE TABLE` | `ANALYZE` / autovacuum 的 `autoanalyze` 阈值 |
| 看 `EXPLAIN` rows vs 实际 | 同：`EXPLAIN (ANALYZE)` 的 estimated rows vs actual rows（PG13+ 逐节点显示） |
| IN 列表太长被降级粗估 | PG 无降级，但 IN 值不在 MCV 内时走直方图近似；相关列失真用 `CREATE STATISTICS`（扩展统计） |

## 5. 动手验证

```sql
-- ① 看某列 MCV 覆盖(精度天花板的直观化)
SELECT most_common_vals, most_common_freqs, n_distinct
FROM pg_stats WHERE tablename='orders' AND attname='status';

-- ② 提高该列估算精度(= PG 版"调大 dive limit")
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;

-- ③ IN 元素从 MCV 命中到失真的过程: rows 估算随列表变化
EXPLAIN SELECT * FROM orders WHERE status IN ('a','b');          -- MCV 精确频率求和
EXPLAIN SELECT * FROM orders WHERE status IN ('a','b',...200个); -- 命中+直方图近似混合

-- ④ PG18 哈希化执行: 大 IN 看计划里 ScalarArrayOpExpr 的执行变化
EXPLAIN ANALYZE SELECT * FROM orders WHERE id IN (1,2,...,50);   -- ≥9 个元素即哈希查找

-- ⑤ 无统计时的 0.5% 兜底: 建表不 ANALYZE 直接查
CREATE TABLE t AS SELECT g, md5(g::text) FROM generate_series(1,100000) g;
EXPLAIN SELECT * FROM t WHERE g = 42;    -- rows=500 (100000×0.005, DEFAULT_EQ_SEL)
ANALYZE t;
EXPLAIN SELECT * FROM t WHERE g = 42;    -- rows=1
```
