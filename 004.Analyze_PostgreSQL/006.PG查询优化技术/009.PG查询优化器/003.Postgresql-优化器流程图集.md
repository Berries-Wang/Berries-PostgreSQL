## 图 5：动态规划连接搜索（standard_join_search，allpaths.c:3461）

以 4 表 A-B-C-D 为例（每层调 `join_search_one_level`，joinrels.c:73）：

```text
 level 1 (初始 rels, 已有扫描路径)
   {A}  {B}  {C}  {D}

 level 2  ── 两两组合, make_join_rel(joinrels.c:696) 逐对:
   {A,B} {A,C} {A,D} {B,C} {B,D} {C,D}
      每对做三件事:
        ① join_is_legal(:350)?       外连接顺序约束检查
        ② build_join_rel(relnode.c:665)  建中间 RelOptInfo (行数/页数)
        ③ add_paths_to_joinrel(joinpath.c:124)  生成 NestLoop/MJ/HJ 路径

 level 3  ── level2 × level1 组合 (含 bushy: level2 × level2):
   {A,B,C} {A,B,D} {A,C,D} {B,C,D}
                     │
                     │   bushy 计划示例: 148-198 行, 避免深左树
                     │   ((A ⋈ B) ⋈ (C ⋈ D)) 而不是 (((A ⋈ B) ⋈ C) ⋈ D)
                     ▼
 level 4  ── 全集:
   {A,B,C,D} ── set_cheapest ──▶ 全局最优连接 Path
```

**关键性质：每个子集只算一次并缓存（join_rel_list + 哈希，relnode.c:486），指数级的组合空间被"子问题复用"压成多项式级的实际计算量（O(3^N) 级）。**

## 图 9：add_path 支配淘汰规则（pathnode.c:464）

```text
 新路径 P_new 进入 pathlist 时, 与已有路径 P_old 逐一比较:

   P_new 支配 P_old (可删 P_old) 需【同时】满足:
     ① 模糊代价不劣于 P_old   (compare_path_costs_fuzzily, 容差 1%,
        disabled_nodes 作为高阶分量先比 —— enable_xxx=off 的作用机制)
     ② pathkeys 不比 P_old 差  (排序可用性)
     ③ required_outer ⊆ P_old 的参数需求 (参数更少)
     ④ 估行数不多于 P_old
     ⑤ parallel_safe 不低于 P_old

   ── 反之被支配 → P_new 丢弃; 各有胜负 → 两者共存 ──

 为什么不一刀切留最便宜?  因为不同"消费场景"要不同的好:
   最便宜启动路径 cheapest_startup  → 只取前几行的场景(LIMIT/EXISTS)
   最便宜总代价路径 cheapest_total  → 取全部行
   有序/参数化路径                 → 服务上层 MergeJoin/NestLoop 复用
 ⇒ 留下的是 Pareto 最优集, 不是单点最优
```

## 图 11：代价模型速记（costsize.c / cost.h:24-34）

```text
 单位: 顺序读一页 = 1.0 (无量纲, 只有相对意义)

 顺序扫  = 页数 × seq_page_cost(1.0) + 行数 × cpu_tuple_cost(0.01) + quals×cpu_operator_cost
 索引扫  = 启动(树高×random_page_cost) + 行数 × (random_page_cost(4.0)
           + cpu_index_tuple_cost(0.005) + cpu_operator_cost)
           └─ random_page_cost 是 SSD/机械盘差异的第一调节旋钮
           └─ 索引页缓存效应: index_pages_fetched(:907) 用 effective_cache_size 折扣
 NestLoop= 外层代价 + 外行数 × (内层单次重扫代价 + 连接条件 cpu 成本)
 MergeJoin= 排序代价(两侧, 可被下层有序抵消) + 两侧行数 × cpu_operator
 HashJoin= 内表一遍(建表) + 外表一遍(探测) + 内存不足时的 partition 代价
 排序    = cost_sort(:2144): 2×logN 次比较 + (超 work_mem 时) 归并 I/O
 并行    = cost_gather(:446): + parallel_tuple_cost(0.1)×行数 + 启动开销摊销

 所有估算的地基: pg_class.reltuples / pg_statistic (ANALYZE 的产物)
 估算错 → 代价错 → 计划错。先查统计, 再怪优化器。
```
