# PG 查询优化器总览（基于 PostgreSQL 18.6 源码）

> 源码根目录：`src/backend/optimizer/`（自查路径 `000.SOURCE_CODE/002.PostgreSQL-18.6/postgresql-18.6`）
> 关键头文件：`src/include/nodes/pathnodes.h`（PG13 前叫 relation.h）

## 1. 优化器在哪里

```text
 SQL 文本
   │  pg_parse_query (tcop/postgres.c)
   ▼
 Parse Tree (RawStmt)
   │  pg_analyze_and_rewrite
   ▼
 Query 树                       ┌────────────────────────────┐
   │  pg_plan_query ←───────────┤  本目录研究对象: 查询优化器 │
   ▼                            └────────────────────────────┘
 Plan 树 (PlannedStmt)
   │  ExecutorStart / ExecutorRun
   ▼
 执行器 (volcano 模型, 逐节点拉取)
```

- `pg_plan_query()` — `src/backend/tcop/postgres.c:883`，调用 `planner()` 进入优化器
- 优化器输入：`Query` 树（语义词法已归一）；输出：`Plan` 树（执行器可直接物化的物理算子树）

## 2. 一句话理解 PG 优化器

**先用逻辑重写把 Query 变成"等价但更好优化"的形状，再用动态规划在"路径空间"里按代价模型搜出最便宜的 Path，最后把 Path 翻译成 Plan。**

三个阶段（对应 `subquery_planner` 的骨架）：

```text
 阶段一  预处理 / 逻辑优化        子链接上拉、子查询合并、外连接消除、常量折叠...
 阶段二  物理优化(路径搜索)       扫描路径 + 连接顺序 + 物理算子 + 上层算子, 全部以 Path 形式竞争
 阶段三  计划生成 / 最终化        最优 Path → Plan, 变量回写引用修正
```

## 3. 核心概念：Path 与 Plan 分离

PG 优化器最重要的设计：**搜索阶段只操作轻量的 Path，确定胜者后才生成重量级的 Plan**。

| 结构 | 定义位置 | 作用 |
|---|---|---|
| `PlannerGlobal` | pathnodes.h:95 | 跨子查询共享的全局状态（最终 rtable、initplans 等） |
| `PlannerInfo` | pathnodes.h:216 | 单层 Query 的规划状态（每层子查询一个） |
| `RelOptInfo` | pathnodes.h:883 | 一个关系（基表/中间连接结果）的"报价单"：行数、页数、pathlist |
| `Path` | pathnodes.h:1753 | 实现同一结果的一种方式（估算代价，无执行细节） |
| `JoinPath` | pathnodes.h:2198 | NestLoop/MergeJoin/HashJoin 三种连接 Path 的公共基类 |
| `RestrictInfo` | pathnodes.h:2699 | 条件表达式的包装（选择性、是否外连接延迟等决策信息） |

```text
 RelOptInfo(users) 的 pathlist 里躺着多个 Path, 互相竞争:
   SeqScan        cost=0.00..3584.00
   IndexPath      cost=0.43..8.31     (谓词有索引可用时)
   IndexPath(参数化) cost=0.29..0.62  (做嵌套循环内层)
   BitmapHeapPath cost=4.21..220.00
   add_path() (util/pathnode.c:464) 负责淘汰被支配的路径 → 只留"各有优势"的少数几个
```

为什么这样设计：同一关系在不同连接角色（驱动侧/被驱动侧、需要有序/无序）下最优路径不同，所以**不能只留一个最便宜的，要留 Pareto 最优集**。

## 4. 代价模型

代价 = 页 I/O + CPU 的加权和，单位是"顺序读一页 = 1.0"（无量纲，只有相对意义）。

```text
 常数定义  src/include/optimizer/cost.h:24-34, 全局变量初始化 costsize.c:130-139

 seq_page_cost          = 1.0     顺序读一页
 random_page_cost       = 4.0     随机读一页 (机械盘经验值; SSD 常调 1.1)
 cpu_tuple_cost         = 0.01    处理一行
 cpu_index_tuple_cost   = 0.005   索引项处理一行
 cpu_operator_cost      = 0.0025  一次操作符/函数求值
 parallel_tuple_cost    = 0.1     worker 间传递一行
 effective_cache_size   = 524288 页  索引缓存估计 (消费点 index_pages_fetched, costsize.c:907)
```

两个铁律：
1. **一切决策都是估算的函数**——统计信息（pg_class.reltuples、pg_statistic 直方图/MCV）错，计划就错。`ANALYZE` 是优化器的粮食。
2. **代价只有相对意义**——`EXPLAIN` 显示的 cost 不是毫秒，是模型内部记账单位。

## 5. 与 MySQL 优化器粗粒度对照

| 维度 | PostgreSQL | MySQL |
|---|---|---|
| 搜索算法 | 动态规划（自底向上，2^N 空间换时间）；≥12 个连接时切遗传算法 GEQO | 贪心 + 深度优先（determine_switch_order/`best_access_path`，多表时靠 heuristic，8.0 有 cost 模型重写） |
| 中间表示 | Path（显式、可枚举、Pareto 集合） | 无显式 Path 层，直接在 JOIN 对象上比较 |
| 物化下推 | 优化器内置（参数化内层、Memoize 节点） | 8.0 有派生表条件下推，历史较弱 |
| 代价单位 | 无量纲（seq_page_cost=1.0） | 早期"磁盘寻道数"，8.0 起也是抽象 cost |
| 可干预 | `enable_xxx` GUC、`pg_hint_plan` | hint 语法内建（`FORCE INDEX` 等） |
| 扩展点 | planner_hook / set_rel_pathlist_hook / FDW | 存储引擎层抽象，优化器扩展点少 |

结构差异的根源：PG 选择"**空间换质量**"（DP 保证连接顺序全局最优），MySQL 传统上"**快出计划**"（海量连接时不炸 CPU）。GEQO 是 PG 在表多时向"快"的妥协。

## 6. 附：GUC 是什么（Grand Unified Configuration，"大一统配置"）

全系列文档反复出现的 GUC = PG 的**配置参数体系**（`work_mem`、`random_page_cost`、`enable_seqscan`、`geqo_threshold`……都是 GUC）。名字来源：把散乱的配置入口统一成一套机制。

```text
 实现位置 (源码自带解释: utils/misc/README:6 "The GUC (Grand Unified
 Configuration) module implements configuration variables..."):
   src/backend/utils/misc/guc.c         ~7000 行, 引擎: SET/SHOW 解析、合法性检查、
                                         优先级仲裁、钩子调用
   src/backend/utils/misc/guc_tables.c  ~5400 行, 参数定义表: 每个参数一条
   src/include/utils/guc.h              对外接口 + GucContext/GucSource 枚举

 一个 GUC 参数的定义长这样 (guc_tables.c:2224):
   {"geqo_threshold", PGC_USERSET, QUERY_TUNING_GEQO,   ← 名字/上下文/分类
      "Sets the threshold of FROM items beyond ...",     ← 文档字符串
    GUC_EXPLAIN},
   &geqo_threshold,   12, 2, INT_MAX,                    ← 绑定的C全局变量/默认/最小/最大
   NULL, NULL, NULL                                         ← check/assign/show 钩子
```

三层关键设计：

1. **上下文（GucContext，guc.h）**——这个参数**谁能改、什么时候改**：

   | 上下文 | 含义 | 例子 |
   |---|---|---|
   | `PGC_INTERNAL` | 写死不可改 | `block_size` |
   | `PGC_POSTMASTER` | 仅启动时 | `shared_buffers`、`max_connections` |
   | `PGC_SIGHUP` | 改完 reload 即可 | `autovacuum` 系列 |
   | `PGC_BACKEND` | 会话启动时定死 | `lc_messages` |
   | `PGC_SUSET` | 超级用户会话内可改 | `log_min_duration_statement` |
   | `PGC_USERSET` | 任何人随时可改 | ★优化器全家：`work_mem`、`enable_seqscan`、代价参数 |

2. **来源优先级（GucSource）**——一个参数能被 postgresql.conf、命令行、`ALTER SYSTEM`、`SET` 多处设置，谁说了算：命令行 > 配置文件 > 会话 SET > 函数 SET 子句；来源记录还支持 `RESET` 回到正确的层。

3. **与 C 代码的绑定**——GUC 参数直接绑到 C 全局变量。本文档引用的 `costsize.c:130-139` 那批代价变量（`seq_page_cost` 等）**本身就是 GUC 的存储变量**（参数定义在 guc_tables.c:3883 起），所以 `SET random_page_cost = 1.1` 后优化器下一句 SQL 立刻生效——没有中间层。

```sql
-- 查看/设置
SHOW work_mem;  SET work_mem = '64MB';
SELECT name, setting, unit, context, source, boot_val
  FROM pg_settings WHERE name LIKE '%cost%';   -- 视图定义: system_views.sql:604
```
