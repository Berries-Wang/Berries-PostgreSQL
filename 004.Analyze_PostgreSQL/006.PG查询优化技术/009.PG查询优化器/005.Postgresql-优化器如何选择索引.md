# PG 优化器如何选择索引（PostgreSQL 18.6，indxpath.c + costsize.c 联动）

> 核心源码：`src/backend/optimizer/path/indxpath.c`（匹配与生成，~8000 行）、`costsize.c`（估价）、`pathkeys.c`（有序性）、`predtest.c`（部分索引证明）。
> 一句话：**"选索引"不是一个决定，而是四步漏斗——能匹配的先匹配，生成多种路径，按代价模型打分，最后在 add_path 竞争里与 SeqScan 同台淘汰。**

## 1. 索引选择发生在流水线的哪一步

```text
 query_planner (planmain.c:54)
   └─ make_one_rel (allpaths.c:175)
        └─ set_base_rel_pathlists (:337) ─ set_rel_pathlist (:473)
             └─ set_plain_rel_pathlist (allpaths.c:772)
                  ├─ create_tidscan_paths      tidpath.c:498
                  ├─ create_seqscan_path       pathnode.c:986   ← SeqScan 也在竞争
                  └─ create_index_paths        indxpath.c:240   ★本文主战场
                       (生成的每条路径 add_path 进 rel->pathlist 竞争)
```

前置依赖：**索引的物理信息早在 query_planner 建网阶段就备好了**——`get_relation_info`（plancat.c:117）读 pg_index/pg_class 等系统目录，为每个索引建 `IndexOptInfo`（列、opfamily、谓词、页数/行数估计 :480-483）；表级行数/页数/可见比例由 `estimate_rel_size`（plancat.c:1075，调用点 :205）填进 RelOptInfo。**目录里有什么、统计算出什么，优化器就知道什么。**

## 2. 第一步：条件匹配——哪些谓词能"喂给"索引

```text
 create_index_paths (indxpath.c:240)  逐索引处理, 先过部分索引闸门:
   │  有谓词且 predOK=false (查询条件蕴含不了索引谓词) → 跳过   :271
   │  (predOK 由 check_index_predicates :3942 预计算, 调 predtest.c:152)
   │
   ├─ 线① 限制条件(→非参数化):  match_restriction_clauses_to_index :2466
   │      └─ get_index_paths :716 → 普通路径直接 add_path, 位图素材攒进链表
   ├─ 线② 松散连接条件(未并入等价类的): match_join_clauses_to_index :2482
   ├─ 线③ 等价类连接条件:               match_eclass_clauses_to_index :2516
   │      线②③ → consider_index_join_clauses :437 → 参数化索引路径 (§4)
   │
   │  匹配原子操作(三线共用): match_clauses_to_index :2554
   │    └─ match_clause_to_index :2587
   │         └─ 对【每一列】独立尝试 (for indexcol 0..nkeycolumns, 无前缀硬规则)
   │              └─ match_clause_to_indexcol :2711
   │                   ├─ 普通算子: 查 opfamily (跨类型算符也认, 如 int4 索引配 int8 参数);
   │                   │    常量侧不得含易变函数 (:2947/:2976 contain_volatile_functions)
   │                   ├─ match_boolean_index_clause :2817   布尔列
   │                   ├─ match_saopclause_to_indexcol :3135  IN 列表 (ScalarArrayOpExpr)
   │                   └─ NULL 条件、RowCompare、表达式索引精确匹配、
   │                      LIKE 'abc%' 经索引支持函数转范围条件 (x>='abc' AND x<'abd')
   │
   ├─ 工厂: create_index_path (pathnode.c:1052; 调用点 indxpath.c:969/:989/:1022/:1039)
   └─ 位图收尾: generate_bitmap_or_paths :1629 (OR 组合) + choose_bitmap_and :1785 (代价择优)
```

**匹配的硬规则**（为什么"有索引却用不上"多半在这一步）：

| 能匹配 | 不能匹配 |
|---|---|
| 索引**任意列**上的 `= / < / > / BETWEEN`（非前导列见下方注意） | 算符不在索引列的 opfamily 中（类型不兼容且无跨型算符） |
| `col IN (...)`（SAOP）、`col IS NULL`（btree 索引本身含 NULL 项，`amsearchnulls`，:2763） | `col LIKE '%abc'`（前导通配，推不出前缀范围） |
| `col LIKE 'abc%'`（C 排序或 `*_pattern_ops` 索引，经支持函数转范围） | 条件含**易变函数**（:2947/:2976 显式检查） |
| 表达式索引：条件与索引表达式匹配 | 条件是 `f(col)` 但索引建在 `col` 上（反之亦然） |
| 部分索引：查询谓词能**蕴含**索引谓词（`predicate_implied_by`，predtest.c:152） | 蕴含证明失败（如索引 `WHERE status='pending'`，查询无此条件） |

> **注意：PG 没有 MySQL 式"左前缀"硬规则**。`(a,b)` 索引对 `WHERE b=5` 同样会匹配并生成 IndexPath——非前导列条件作为索引内过滤，扫描范围仍是**整个索引**（pathnodes.h:1842 IndexPath 注释："An empty list implies a full index scan"），代价高、通常输给 SeqScan。真正要求前缀的是**边界定位与排序复用**（ORDER BY 用索引免 Sort、btree 两端定位）。这与 MySQL 的 leftmost rule 是本质差异。

## 3. 第二步：生成多类索引路径（含 Bitmap 组合）

```text
 对每个匹配成功的索引, 最多生成四类:

 ① IndexPath (普通 IndexScan)          正向/反向 (build_index_pathkeys 供排序复用)
 ② IndexPath (IndexOnlyScan)           check_index_only (:2228): 需要的列全在索引里
                                        + 依赖 visibility map (代价见 §5 allvisfrac)
 ③ BitmapHeapPath (可多索引组合)      create_bitmap_heap_path (indxpath.c:347/:414)
 ④ 参数化 IndexPath                     内层为 NestLoop 服务 (§4)

 OR 条件 / 多索引组合:
   generate_bitmap_or_paths (:1629, 调用点 :322/:330)
      └─ build_paths_for_OR (:1092)   每个 OR 臂单独找索引路径 (不求全命中)
   choose_bitmap_and (:1785)       把位图素材按代价择优组合:
        ├─ AND (BitmapAnd): 多索引条件交集, 两个索引各扫一遍再合并
        └─ OR  (BitmapOr) : WHERE a=1 OR b=2 → 两个索引各出位图求并
   为什么组合: 两个"各命中 10%"的索引 AND 后可能只命中 0.5%,
              比单索引命中 10% 再回表过滤便宜
```

## 4. 第三步：连接场景——参数化索引路径

```text
 WHERE small.tiny_col = big.col
 NestLoop (match_unsorted_outer, joinpath.c:1812):
   outer = small (100 行)
   inner = big 上的【参数化 IndexPath】: indexcol = $0   ← $0 = 外层当前行的 big.col
        (线②/③ 的连接条件经 consider_index_join_clauses :437 匹配生成;
         required_outer={small}, 探测次数由 get_loop_count :909 估算)
        执行时每来一行外层值, 就做一次索引定位 (createplan.c:5036 replace_nestloop_params)
 ⇒ "小表驱动 + 内层索引"不需要人肉改写, 优化器在路径层自动组合
 同一索引会同时留下: 普通版(cost=全表按索引扫) + 参数化版(cost=单次探测定位的循环代价)
   — 各服务不同连接角色, 由 add_path 分场景保留
```

## 5. 第四步：代价打分——cost_index 解剖（costsize.c:560）

```text
 cost_index(path) 的骨架:

 ① 行数:  tuples_fetched = clamp_row_est(选择率 × 表行数)      :646
          选择率不是 cost_index 自己算的: 由 amcostestimate (btree→btcostestimate)
          对索引条件逐条估算 (:628-631 调用点, 内部用 MCV/直方图;
          统计失真→行数错→索引选错, 见 004 文档)

 ② 页数:  pages = index_pages_fetched(tuples_fetched, ...)       :908
          核心: 同一堆堆页会被反复访问, 用 Mackert–Lohman 公式(1989, :874 注释
          引论文)建模缓存吸收效应:
              PF ≈ 2·T·Ns / (2·T + Ns)   (缓存装得下整表时的分支 :937)
              T=表页数, Ns=预计取回行数, b=可用缓存页
              (b 由 effective_cache_size 按全查询 total_table_pages 分摊, :889 注释)
          ⇒ effective_cache_size 调大 → b 大 → 重复访问更多被吸收
            → 随机页代价低 → 索引/位图更可能赢
          参数化路径被外层反复探测 (loop_count>1) 时代价按探测次数折算摊薄 :680-723

 ③ 空间局部性 (correlation, -1..1):
          correlation=1   (索引序≈堆序, 如自增主键): 几乎顺序读, 页数≈最小
          correlation=0   (随机): 全按 random_page_cost 计
          实现: 在"全随机 max_IO_cost"与"全顺序 min_IO_cost"之间按 correlation²
                插值 (:795-797): run += max_IO + corr²·(min_IO-max_IO)
          (uuid 主键 correlation≈0 → 同样命中 10%, 代价可比自增键高数倍!)

 ④ IndexOnlyScan 专属: 页数 × (1 - allvisfrac) 折扣               :696
          allvisfrac = visibility map 中全可见页比例 (plancat.c:205 填充)
          ⇒ 刚 UPDATE/DELETE 过的表 IOS 变贵; VACUUM 后 IOS 更可能被选

 ⑤ 代价合成:
          总代价 ≈ 页数×(random_page_cost 或 seq_page_cost)
                   + tuples_fetched×(cpu_index_tuple_cost + cpu_operator_cost + 回表 cpu_tuple_cost)

 与 SeqScan 的对决本质上是一道算术题:
          索引扫代价 ≈ N页随机读(4.0/页) + CPU ; 全表扫 ≈ 全部页×1.0 + 全表行×CPU
          命中率超过某个比例(经验 ~5-10%, 随 correlation 与缓存变化) → SeqScan 胜出
```

## 6. 第五步：竞争、保留与 GUC 干预

**add_path（pathnode.c:464）不只留最便宜的**——留 Pareto 集：

```text
 留下来的典型阵容:
   cheapest_total    SeqScan          cost=0..358   (取全部行最便宜)
   cheapest_startup  IndexPath        cost=0.43..   (最快出第一行: LIMIT/EXISTS 场景)
   有序 IndexPath     cost=0..380     (比 SeqScan 贵, 但免掉 Sort → 服务 ORDER BY/MergeJoin)
   参数化 IndexPath   cost=0.29..     (做 NestLoop 内层最便宜)
 判定"有序"是否可用: build_index_pathkeys (pathkeys.c:740) 生成索引的有序性,
   上层用 pathkeys_count_contained_in (:558) 检查是否覆盖 ORDER BY
```

**GUC 干预的实现机制**（呼应 000 文档 §6：enable_* 本身是 costsize.c 的 GUC 存储变量，定义 guc_tables.c:803 起）：

```text
 enable_indexscan/indexonlyscan/bitmapscan/seqscan   costsize.c:145-148 (默认 true)
 关闭 ≠ 禁止, 而是罚分: 相关路径代价 += disable_cost (1.0e10, costsize.c:141)
   → 仍会作为"最后的手段"参与, 只会输给一切未禁用路径
   → add_path 比较时 disabled_nodes 作为最高优先分量 (pathnode.c:496 一带)
 真正影响"贵贱"的 GUC: random_page_cost(SSD 调 1.1 常见) / effective_cache_size /
                       cpu_index_tuple_cost
```

## 7. "优化器不走我的索引"速查（优化器视角的原因归类）

| 现象 | 根因环节 | 源码落点 |
|---|---|---|
| 走了 SeqScan | 代价：命中率过高 / correlation≈0 / random_page_cost 太大 / 非前导列只能全索引扫描 | cost_index :560 |
| 索引存在但计划里没有 IndexPath | 匹配失败：易变函数 / 蕴含证明失败 / 算符不在 opfamily | match_clause_to_indexcol :2711、:2947、predtest.c:152 |
| 用了 Bitmap 而非普通索引扫 | 多条件组合 or 命中率中等（回表乱序代价高，位图先排序 TID） | choose_bitmap_and :1785 |
| IndexOnlyScan 没出现 | 需要的列不全在索引 / allvisfrac 太低 | check_index_only :2228 |
| ORDER BY 没用索引 | 索引序与 ORDER BY 不完全匹配（前缀/方向/NULLS） | build_index_pathkeys :740 |
| 行数估错连带选错索引 | 统计过期 / 列相关（用 CREATE STATISTICS） | estimate_rel_size plancat.c:1075 |
| 条件明明能下推却没索引 | 检查是不是语义上不能下推（外连接内侧、易变函数） | distribute_qual_to_rels initsplan.c:2596 |

更全面的"不走索引"场景清单见上级目录 [../006.Postgresql-优化器不走索引的情况.md](../006.Postgresql-优化器不走索引的情况.md)。

## 8. 影响索引选择的手段汇总

```text
 ① 统计侧(最优先): ANALYZE / 提高列 statistics_target / CREATE STATISTICS 扩展统计
    —— 估准了, 代价模型自然选对 (一切选择都是估算的函数)
 ② 代价侧: random_page_cost(SSD↓) / effective_cache_size(调大→索引页读更便宜)
 ③ 强制侧: enable_seqscan=off 罚分逼出索引计划 (调试用, 别上生产);
           pg_hint_plan 扩展
 ④ 索引设计侧: 前导列放等值条件列 / 部分索引收窄 / 覆盖索引助 IOS / 表达式索引对齐查询写法
 ⑤ 语句侧: 改写为能匹配前导列的等值条件; IN 列表(PG17+ 原生 SAOP 索引扫, :3135)
```

## 9. 动手验证

```sql
-- ① 看一个索引为什么贵/便宜: 对比 correlation 与代价构成
CREATE TABLE t(i serial PRIMARY KEY, u uuid DEFAULT gen_random_uuid(), v int);
INSERT INTO t(v) SELECT random()*100 FROM generate_series(1,200000);
CREATE INDEX ON t(u);  CREATE INDEX ON t(v);
ANALYZE t;
SELECT attname, correlation FROM pg_stats WHERE tablename='t';
-- 同样 ~12% 命中率, 只差 correlation: 自增键走索引扫, uuid 键乱序走位图/全表
EXPLAIN (ANALYZE) SELECT * FROM t WHERE i < 25000;
EXPLAIN (ANALYZE) SELECT * FROM t WHERE u < '20000000-0000-0000-0000-000000000000';
EXPLAIN (ANALYZE) SELECT * FROM t WHERE v = 7;       -- 命中 ~1%: 索引/位图
EXPLAIN (ANALYZE) SELECT * FROM t WHERE v < 60;      -- 命中 ~60%: SeqScan 胜出

-- ② 同一查询, 调代价旋钮看计划翻转
SET enable_seqscan = off;  EXPLAIN SELECT * FROM t WHERE v < 60;  -- 罚分逼出索引计划
SET enable_seqscan = on;

-- ③ 有序性保留: 贵的索引路径因免 Sort 而复活
EXPLAIN SELECT * FROM t WHERE v < 70 ORDER BY i DESC LIMIT 10;

-- ④ 参数化路径: 连接内层自动用索引
EXPLAIN SELECT * FROM t JOIN (VALUES (1),(2),(3)) AS k(v) ON t.v = k.v;
-- 计划: 内层 Index Scan using t_v_idx, Index Cond: (v = k.v) ← 参数来自外层当前行
```
