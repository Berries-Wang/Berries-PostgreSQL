# GROUP BY 与 DISTINCT（对应 MySQL 009 篇）

## 结论先行

- "distinct 和 group by 哪个快"在 PG 里的答案：**都由优化器统一改写成聚合/去重节点，语义等价时性能相同**——PG 从不隐式排序（与 MySQL 8.0 之后的行为一致）。
- PG 的两个执行策略：**HashAggregate**（不要求输入有序）和 **GroupAggregate**（要求输入按分组键有序——有序可来自索引，即你笔记里"流式聚合"）。
- **重要差异：PG 没有松散索引扫描（Loose Index Scan）也没有 Skip Scan**——MySQL `Using index for group-by` 一步跳组的能力，PG 要用**递归 CTE 模拟**（本篇给出模板）。

## 概念：两种聚合策略

```text
 HashAggregate (默认偏好)                    GroupAggregate
 ┌───────────────────────────┐              ┌───────────────────────────────┐
 │ 逐行来, 按分组键哈希入桶      │              │ 要求输入已按分组键有序:           │
 │  (1,1,1,2,2,3) 顺序无所谓    │              │   索引序流(免Sort) 或 Sort 节点   │
 │        │                    │              │   → 组边界处收尾聚合, 流式输出    │
 │  组数少+估得准 → 内存够       │              │ 优点: 内存 O(组数) 可控,         │
 │  work_mem 不够 → 溢出磁盘     │              │       支持 DISTINCT 聚合/有序输出 │
 │  (PG13+ 多阶段外排归并)      │              │ 缺点: 无索引时多一次全量 Sort     │
 └───────────────────────────┘              └───────────────────────────────┘
 选择者: planner.c 的 can_hash 决策 (:4494 can_hash && gd->any_hashable),
         代价由 cost_agg (costsize.c:2682) 对比; 估算组数 estimate_num_groups (selfuncs.c:3462)
```

**为什么 HashAggregate 无序也能分组**：分组语义="相同键的行聚在一起聚合"，哈希表把相同键自然映射到同一桶——它买的是内存，省的是排序。GroupAggregate 买的是"有序输入"，省的是内存。组数巨大（哈希表放不下）时 GroupAggregate+Sort 反而赢——这就是优化器按 `work_mem` 估算取舍的原因。

## SQL 示例

```sql
-- ① 有索引 → 索引即序 → GroupAggregate 免排序 (对应你笔记"流式聚合"):
EXPLAIN SELECT seller_nick, count(*) FROM trade_info GROUP BY seller_nick;
-- GroupAggregate  ← 前面有 Index Scan using idx_seller (流式)

-- ② 无索引 → HashAggregate:
EXPLAIN SELECT status, count(*) FROM t GROUP BY status;
-- HashAggregate (无 Sort 节点)

-- ③ DISTINCT: 同一套机制
EXPLAIN SELECT DISTINCT seller_nick FROM trade_info;
-- Unique on Index Scan (有序, 流式去重) 或 HashAggregate (无序)

-- ④ DISTINCT ON (PG 特有): 每组取第一行
SELECT DISTINCT ON (seller_nick) seller_nick, created, amount
FROM orders ORDER BY seller_nick, created DESC;   -- 每卖家最新一单

-- ⑤ PG 没有松散索引扫描: 递归 CTE 模拟 "每组只取一个键":
WITH RECURSIVE t AS (
  (SELECT min(seller_nick) AS nick FROM trade_info)
  UNION ALL
  SELECT (SELECT min(seller_nick) FROM trade_info WHERE seller_nick > t.nick)
  FROM t WHERE t.nick IS NOT NULL
)
SELECT nick FROM t WHERE nick IS NOT NULL;
-- 每组一次索引定位(btree 向右跳), 扫描量 ∝ 组数而非行数 ← MySQL "Using index for group-by" 的 PG 手工版
```

## 原理：为什么"有索引就质变"（与你笔记同构）

```text
 有索引:  索引按分组键有序 ──▶ GroupAggregate 流式: 每组内存 O(1), 总扫描=索引页数
 无索引:  两种都要"看见所有行":
           HashAgg: 哈希表 O(组数) 内存; 溢出时写临时文件再归并 (nodeAgg.c:422 agg_refill_hash_table)
           GroupAgg: Sort 全量物化 (O(N logN) + 可能落盘)
 ⇒ 第一优化方向永远是: 给分组列建索引 (和你笔记结论一致)
 ⇒ 第二方向: 组数可控时信任 HashAggregate; 组数失控(百万级组)时考虑预聚合/物化视图
```

**溢出机制**（PG13+）：HashAgg 运行中超过 work_mem 触发 spill——已聚合的分区落盘（`hashagg_spill_init` nodeAgg.c:435），结束后逐分区重新聚合归并；`EXPLAIN ANALYZE` 会显示 `Disk Usage`。

## 与 MySQL 对照

| | MySQL 8.0 | PG 18.6 |
|---|---|---|
| 有索引分组 | 松散索引扫描 `Using index for group-by`（跳组，扫描∝组数） | GroupAggregate + 索引序（**逐行扫索引**，靠流式省内存，扫描仍∝行数） |
| 缺前缀列跳扫 | Skip Scan（8.0.13+） | **无**（递归 CTE 模拟） |
| 无索引分组 | 临时表(+旧版 filesort) | HashAggregate（内存哈希+可溢出） |
| 隐式排序 | 8.0 起不再隐式排序 | 从不隐式排序 |
| DISTINCT vs GROUP BY | 无索引时 distinct 略优 | 优化器统一改写，无差别 |
| 每组取首行 | 窗口函数 | **DISTINCT ON**（更直接） |
