# 覆盖索引与延迟关联（对应 MySQL 001 篇：延迟关联）

## 结论先行

- **PG 里"回表"= 索引扫描后按 TID 取堆元组**（PG 没有聚簇索引，堆是无序的，所有索引叶子存的都是 TID——这点和 InnoDB 二级索引一样，但 PG 连"聚簇索引"也没有）。
- **覆盖索引在 PG 里是正式能力：Index Only Scan（IOS）**——查询列全在索引里且页"全可见"时，完全不碰堆。MySQL 是隐式（`need_to_access_clustered=false`），PG 是显式的执行计划节点。
- **延迟关联在 PG 依然成立**，且因为 IOS 的存在效果更好；但 PG 有更好的解法：**keyset 分页（seek method）** 和 `INCLUDE` 列。

## 概念

```text
 PG 的堆与索引 (对照 InnoDB: 聚簇索引+二级索引)
 ┌───────────────────────────────────────────────────────┐
 │ 堆(表文件): 页0 页1 页2 ... 页N      ← 行无物理顺序        │
 │   每行: 元组头(xmin/xmax...) + 数据 + TID=(页号,行号)     │
 │                                                        │
 │ B-tree 索引 idx(a): 叶子 = (键a, TID) ──按 a 有序          │
 │   索引扫描 = 树上定位 → 拿 TID → 去堆取整行 ←【这一步就是  │
 │   MySQL 说的"回表", 代价 = 堆页数 × random_page_cost】    │
 └───────────────────────────────────────────────────────┘
```

## SQL 示例（沿用你 MySQL 001 篇的订单表）

```sql
-- 表: trade_info(tid bigint pk, seller_nick text, created timestamptz, jdp_response text, ...)
CREATE INDEX idx_seller_created ON trade_info (seller_nick, created);

-- 深度分页, PG 版写法:
SELECT * FROM trade_info
WHERE seller_nick = $1 AND created BETWEEN $2 AND $3
ORDER BY created
LIMIT 10 OFFSET 100000;
-- Index Scan 用 idx_seller_created 按序走, LIMIT 到 100010 行才停——
-- 与 MySQL 一样: 前 10 万行每行都付了一次"堆取"(随机读), 全部扔掉

-- 方案A 延迟关联 (和 MySQL 同款思路, 子查询走 Index Only Scan):
SELECT t.*
FROM trade_info t
JOIN (SELECT tid FROM trade_info
      WHERE seller_nick = $1 AND created BETWEEN $2 AND $3
      ORDER BY created LIMIT 10 OFFSET 100000) AS page ON page.tid = t.tid;
-- EXPLAIN 应看到子查询 "Index Only Scan using idx_seller_created" + 外层 10 次堆取

-- 方案B keyset 分页 (PG/MySQL 通用且最优, 游标式翻页):
SELECT * FROM trade_info
WHERE seller_nick = $1 AND created BETWEEN $2 AND $3
  AND (created, tid) > ($last_created, $last_tid)   -- 行构造器比较, (created,tid) 唯一化
ORDER BY created, tid
LIMIT 10;
-- 每页都是"定位+顺序取10行", 没有OFFSET 这个概念, 第N页和第1页一样快

-- 方案C 声明式游标 (应用分页的替代: 服务端游标跨请求持有位置)
DECLARE cur CURSOR FOR SELECT * FROM trade_info WHERE seller_nick=$1 ORDER BY created;
FETCH 10 FROM cur;  -- 反复 FETCH, 无重复扫描
```

## 为什么能这么优化（原理）

### 原理一：Index Only Scan 为什么能"零堆访问"

```text
 普通IndexScan:  索引(按序) ──TID──▶ 堆取整行 ──▶ 执行器过滤/返回
                         ▲ 每行一次随机IO (100010次!)

 IndexOnlyScan:  索引(按序) ──▶ 索引元组本身就含查询列
                     │
                     ├─▶ 查【可见性映射 VM】: 这页是否"所有事务都已提交且可见"?
                     │      (visibility map, VACUUM 时置位, access/heap/visibilitymap.c)
                     │
                     ├─ 全可见 → 直接返回, 堆一次都不碰 ✅
                     └─ 不全可见 → 退化取堆 (EXPLAIN 里的 "Heap Fetches")
```

- VM 检查在执行器里：`IndexOnlyNext`（executor/nodeIndexonlyscan.c:62），`VM_ALL_VISIBLE` 判断在 :162。
- **为什么必须查 VM**：PG 是 MVCC，一行"对我可见吗"要看堆上的 xmin/xmax；只有 VACUUM 确认"这页所有行对任何事务都可见"后，才能放心只看索引（书 §12.5.3 VACUUM 优化的一个意义）。
- **推论**：大量写后的表 VM 常不全可见，IOS 会退化——`VACUUM` 或让 autovacuum 跑一跑，Heap Fetches 会归零。这是 MySQL 没有的运维耦合点。
- INCLUDE 列（PG11+）：`CREATE INDEX ON t (a) INCLUDE (b)`——b 进索引参与覆盖、但不参与键排序/分隔符，键更短页更密。

### 原理二：延迟关联/LIMIT 提前终止省在哪

```text
 原SQL:   索引序扫描 100010 行 ──每行堆取(随机IO×100010)──▶ ExecLimit 扔掉前10万
 延迟关联: 子查询 IndexOnlyScan 100010 行(零堆取, 只有索引页顺序读, 页密便宜)
              └▶ 外层 join 只对最终 10 个 TID 做堆取(随机IO×10) ✅
 LIMIT 截断点: ExecLimit (executor/nodeLimit.c:40) 每收一行计数, 够了就向上传播"结束",
              扫描节点下次 fetch 即返回空——索引序扫描天然"取够即停"
```

三条收益与 MySQL 001 篇完全同构：①LIMIT 在覆盖索引上截断；②堆取 100010→10；③索引页小页密。差异只有一个：PG 的"覆盖"是看得见的计划节点（IOS），堆取是否真的被省掉，看 `EXPLAIN (ANALYZE, BUFFERS)` 里的 `Heap Fetches: 0`。

## 源码锚点

| 环节 | 位置 |
|---|---|
| IOS 执行节点 | `IndexOnlyNext` executor/nodeIndexonlyscan.c:62；VM 判断 :162 |
| VM 维护 | access/heap/visibilitymap.c（VACUUM 置位） |
| LIMIT 截断 | `ExecLimit` executor/nodeLimit.c:40 |
| 索引扫描代价（堆页×random_page_cost） | `cost_index` optimizer/path/costsize.c:560 |
| planner 怎么挑 IOS | `create_index_paths` optimizer/path/indxpath.c:240（判断查询列是否被索引覆盖） |

## 与 MySQL 对照

| | InnoDB | PG 18.6 |
|---|---|---|
| 覆盖判断 | `build_template` 设 `need_to_access_clustered=false` | planner 静态判断 + 执行时 VM 校验（双重） |
| "回表" | 二级→聚簇索引 | 索引→堆（本质相同，但 PG 一视同仁） |
| 覆盖是否可见 | EXPLAIN Extra `Using index` | 计划节点名 `Index Only Scan` + `Heap Fetches` 计数 |
| 深度分页解法 | 延迟关联 | 延迟关联 / **keyset** / 游标（后两个更优） |
| INCLUDE 列 | 无（主键自动附加） | 有（PG11+，且不参与排序） |
