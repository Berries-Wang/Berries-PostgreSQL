# 优化器不使用索引的情况（对应 MySQL 008 篇）

## 结论先行

你 MySQL 008 篇的核心认知在 PG **逐字成立**：优化器不是"有索引就用"，而是代价比较。PG 的两个代价公式（`cost_seqscan` costsize.c:295、`cost_index` costsize.c:560）精确对应你笔记里"每行 1 单位 vs 按页分摊"的量纲差：

```text
 SeqScan  = 页数 × seq_page_cost(1.0) + 行数 × cpu_tuple_cost(0.01)      ← 顺序读整表
 IndexScan = 索引页代价 + 【堆页数 × random_page_cost(4.0)】 + cpu        ← 堆页是随机读!
             ▲ 堆页数不是"行数": 用 index_pages_fetched 模型估算行在堆上的聚集度,
               并考虑 effective_cache_size 的缓存命中 (costsize.c:889)
 ⇒ 选择性越好(匹配越少), 堆页数越少, 索引越赢
 ⇒ 匹配行占 5%~30% 的"中间地带": 位图扫描登场 (004 篇)
```

## 场景逐条（MySQL 五场景的 PG 版）

### 场景一：回表太贵——选择性差的大范围查询（同款）

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'paid';  -- status 有索引但 80% 行满足
-- 期望: Seq Scan。若它选了索引 → 统计过期, 先 ANALYZE
```

### 场景二：违反最左前缀（同款，且 PG 没有 Skip Scan）

```text
 索引 (a,b): WHERE b=1 → 不能定位区间 (b 在每个 a 分段内才有序)
 ⚠️ MySQL 8.0 有 Skip Scan 兜底, PG 18.6 【没有】(社区有 patch 未合入)
 PG 替代: 建倒序索引 (b,a) / 把 b 加入索引 / 部分索引
```

### 场景三：列上套函数 / 类型不匹配（PG 解法更多）

```sql
-- 列上函数 → 与 MySQL 同样不能用普通索引:
WHERE lower(email) = 'a@b.c'              -- idx(email) 无效
-- PG 解法① 表达式索引 (书 §11.4.1, MySQL 8.0 才有函数索引):
CREATE INDEX ON users ((lower(email)));
-- PG 解法② 改写成区间条件 (同 MySQL):
WHERE created >= '2024-01-01' AND created < '2024-01-02'

-- LIKE 前缀匹配: 与 MySQL 不同, PG 默认 collation 下 LIKE 不走 btree!
WHERE name LIKE 'ABC%'    -- 非 C collation: 不能用普通 btree 索引
-- 解法① 模式运算符类 (字符序只看前缀字节):
CREATE INDEX ON t (name text_pattern_ops);   -- pg_opclass.dat:155
-- 解法② 列用 C collation 建表/建索引
-- '%ABC%' 两家都不能用 btree (可用 pg_trgm GIN, 见 008 篇)

-- 类型: PG 比 MySQL 严格——text 列 = 整数直接报错(不会隐转后扫全表);
-- 数值家族跨类型(int=bigint)有跨类型运算符族, 仍可走索引。
```

**为什么 LIKE 'ABC%' 在 PG 需要 pattern_ops**：btree 的比较语义由"运算符族"决定；默认 text collation 的排序规则（本地化字母序）与"逐字节前缀"不同构，`LIKE` 无法翻译成 `>= 'ABC' AND < 'ABD'` 这样的范围。`text_pattern_ops` 提供逐字节排序的 opfamily，planner 就能把前缀翻译成范围条件（翻译逻辑在 utils/adt/like_support.c 的索引支持函数里）。

### 场景四：统计信息过期（同款）

```sql
ANALYZE orders;                       -- 采样重估 (commands/analyze.c:1199 acquire_sample_rows)
SHOW default_statistics_target;       -- 每列直方图/MCV 桶数, 默认 100 (guc_tables.c:2188)
-- 复杂分布(倾斜/多峰)可对列调大: ALTER TABLE t ALTER COLUMN c SET STATISTICS 500;
-- autovacuum 会在变更量超阈值时自动 ANALYZE (书 12.5.3)
```

### 场景五：开关被关（同款）

```sql
SHOW enable_seqscan; SHOW enable_indexscan; SHOW enable_bitmapscan;  -- 005 篇
```

### 场景六（PG 特有）：相关列——单列统计的盲区

```text
 WHERE city='杭州' AND age=25:  两列统计独立相乘 → 选择性被低估
 → 行数估小 → 错选嵌套循环/错误索引
 解法: 扩展统计 CREATE STATISTICS (008 篇详解)
 诊断: EXPLAIN ANALYZE 里 rows 估算 vs actual 差数量级 = 统计问题
```

## 排查工具链（PG 版）

| 工具 | 用法 |
|---|---|
| `EXPLAIN (ANALYZE, BUFFERS)` | rows vs actual rows、Buffers: read(堆随机读)、节点类型 |
| `ANALYZE` / `VACUUM ANALYZE` | 刷新统计后复测 |
| `SET enable_*=off` 组合试验 | 反推优化器代价构成（005 篇） |
| `pg_stat_user_indexes.idx_scan` | 长期为 0 的索引 = 候选清理对象 |
| `pg_hint_plan` | 最后手段（005 篇） |
